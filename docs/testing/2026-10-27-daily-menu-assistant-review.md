## 2. 本轮发现及修复

| 问题 | 用户感受/风险 | 已落实的修复 |
| --- | --- | --- |
| 修改口味、搭配等条件后，旧菜单被置为需要重生成，保存受阻 | 眼前的菜还能看见，却被要求先换一套 | 设置与已生成菜单解耦；下次主动生成才应用新选菜条件；保存验证眼前菜单快照、权限与版本，不按新条件重筛 |
| 先改下次设置，再让助手只改人数、保留菜或换一道，可能触发整餐重排 | 一句小调整造成整餐变化 | 只改人数/保留菜复用已有菜单；单菜替换只动对应菜位；旧策略菜单也覆盖，人数不缩放食材 |
| 保存还提供另选日期/餐次 | 保存目标不直观，容易误以为首页日期改变了 | 移除另存入口和选择器；保存页面当前日期餐次；已有记录保留一次真实替换确认；旧的未决请求仍核对原目标 |
| 正常执行检查点被当作待确认/待恢复 | 助手实际在办理，页面却让用户再处理一次 | 统一执行状态判定，自动继续获取原请求结果；不会重发模型问题或重复保存 |
| 返回首页读取旧助手日志；或助手刚好在两次读取之间完成 | 菜单已经更新，首页仍旧菜或旧警告 | 只读查询同账号、同餐次已知请求；依据完成回执同步最新菜单版本后再清理日志；回读失败保留只读线索 |
| 部分完成后，失败恢复的原复合指令仍留在输入框 | 用户再次发送可能重复已经成功的保存 | 清理未主动编辑的原复合指令，保留新输入；原请求与版本保护不丢失 |
| 营养回复与保存回执仍有“未记为已吃 / 保存不算已吃”的旧信号 | 与“保存即记录”冲突 | 提示规则、工具说明统一记录口径；日历回执使用 `reviewBasis=calendar_records`、`reviewFromDate=目标日期`，不保存会随跨天过期的第二个状态布尔值 |
| 保存设置期间换账号/餐次，迟到响应可能干扰新页面 | 新页面状态被旧操作影响 | 保存绑定原 store、账号和页面；迟到结果不得在新餐次继续保存或改界面 |

保留的限制都是实际业务保护：未知结果先查原请求，真实覆盖确认一次，真正失败保留菜单和输入，不伪报成功。正常修改条件不再制造这些恢复提示。

### 执行过程与计数口径

第一轮中 1、3、5、9 曾停在正常检查点；后台后来完成。这个状态同步缺陷被实际发现并修复，不能把当时的检查点当作模型最终失败。

2、4、10 最初在进入模型前被本地 HTTP 409 拒绝，外部调用为 0。修复并核对原请求已结束后，仅补齐这三个原问题。实际送达模型顺序为 **1、3、5、6、7、8、9、2、4、10**。问题内容和场景总数没有增加。第 6 项初次快照比较还受前一项购物写入完成时序影响，因此以最终回执和实际数据库事实判断，没有将该瞬间计作“查看操作写了数据”。

原问题 1/3/5/6/7/8/9 合计 14 次模型 HTTP 尝试；补齐 2/4/10 使用 1/2/1 次，总计 **18/20**。模型工具往返也算 HTTP 次数，失败也进入同一份原子预算账本。最终只读获取 10 个原 turn，均为 `completed`，未再调用模型。

## 5. 当前仍值得优化的体验

1. **结果话术更像用户收到的结果。** 有些成功回复只有“已更新本餐 / 已完成”，另有生成完成后仍使用将来时的尾句。下一轮应优先从真实操作回执生成一行简短说明，例如“已换好素菜，荤菜没动”“已保存到今天晚餐”；具体菜品继续由卡片呈现，不重复堆文本。
2. **营养完整度仍是主要数据短板。** 本次公开本地快照 5,407 道菜中，1,550 道可完整计算，占 **28.7%**；3,857 道只有部分可计算。不能把部分小计显示成整道菜总值，也不能把“适量”强行补成克数。该比例是当前验收快照的统计，不是本轮重新查询线上得到的数字。
3. **购物“已购”和真实购买仍是两回事。** 当前一键按钮是全部标记已购，没有商家下单能力。未来扩展应让用户少复制、少搜索，但不能把打开商家页面包装成下单成功。
4. **发布验收仍需设备与网络场景。** 本地逻辑已走通，下一轮发布前重点看跨天切换、聊天后返回首页、断网后读取结果、覆盖取消、输入中切后台和键盘遮挡。无需重新设计整套视觉。

## 6. 功能拓新建议

以下是设计建议，尚未自动实现；应按用户收益逐项推进。

| 优先级 | 功能 | 第一版建议 | 验收口径/前提 |
| --- | --- | --- | --- |
| P1 | 助手语音输入 | 复用已有录音/转写基础能力，按住说话或点击录音，转为输入框文字，允许改字后发送 | 录音权限拒绝仍可打字；取消不发送；切后台/账号/日期不串内容；不能识别完成就自动保存或采购；正式启用前验证服务额度与设备支持 |
| P1 | 热量与营养覆盖补全 | 优先补高频食材营养、可靠单位换算与可确认的配方用量，不以一次补齐全部数值为目标 | 按整道菜汇总、整数卡路里；未知留空；人数只分摊；提升完整菜品覆盖率，同时跟踪数据错误率与可解释性 |
| P1 | 购物价格估算 | 在现有参考价能力上补可靠覆盖，显示报价日期和可估算部分合计 | 有对应材料、规格和数量才估；缺价/适量不按 0 元；实际支出仍与估算分开；不用低覆盖小计冒充整单预算 |
| P2 | 更顺手的采购跳转 | 先完善排版清楚的复制清单，再验证受支持的商家搜索/跳转；只有平台提供稳定合法能力时再考虑带清单跳转 | 明确到达的是搜索页、商品页还是购物车；不能承诺自动下单；接口、平台规则和用户授权须在实施时确认 |
| P2 | 做饭过程辅助 | 复用已有整餐做法，提供当前步骤定位、用户主动启动的计时与完成勾选 | 没有可靠时长不猜；不影响日历统计；退出重进保留当前做饭进度即可，不再增加一套饮食状态 |
| P2 | 家中已有食材少买一点 | 购物清单中允许对本次采购排除已有调料/食材，并记住明确选择 | 不自动猜库存；不删除配方里的材料；不会把临时不购买误学成长期忌口 |
| P3 | 家庭协同清单 | 在个人流程稳定后，再评估共享一个采购清单、同步勾选 | 必须有明确邀请、权限与冲突处理；收益确认前不引入复杂家庭账号体系 |

推荐推进顺序：**先交付本轮稳定性修复并完成设备验收 → 语音输入与高频营养数据补全 → 价格估算覆盖 → 商家跳转与做饭辅助。** 同一阶段只选少量明确问题，避免新增入口重新挤满首页。

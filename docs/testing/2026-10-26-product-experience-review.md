## 任务与边界

- 基线：`2ee6397a5d86f05637bec80ec077212a0e7789b2`，正式仓库当前分支。审查小程序与配套业务实现，不把独立网页当成微信账号数据镜像。

## 可观察的验收条件

1. 首页、助手、日历读取同一餐次语义；跨天返回、旧响应、取消和重试不错误覆盖记录。
2. 由餐次记录进入整餐做饭模式时，优先显示保存的配方；菜库下架或新配方更新不导致这份历史内容丢失或悄悄变成新内容。普通菜品详情仍属于当前菜库入口。
3. 采购、回顾和营养展示遵守固定配方与真实空值；用户操作有明确入口、反馈和恢复路径。
4. 一级页、二级页和常用弹层的字号、轻字重、分隔线、按钮语义一致；声明检查与实际渲染证据分开。
5. 确认的问题先复现，再修复并运行受影响回归；最终差异不混入无关修改。

## 状态与验证约定

- 读取成功显示已验证目标的数据；失败保留可理解的重试或返回入口，不把权限错误伪装成成功。
- 异步返回必须仍属于当前账号、目标和页面代次；切换账号、离开页面、较新请求启动后丢弃过时结果。
- 保存等写入以服务端回执为准；未知结果沿用原请求恢复；取消不新建写入；部分成功不重做已成功动作。
- 历史快照为已保存记录的内容，不据此恢复下架菜到可选菜库；缺失快照才允许受控读取可访问的当前菜谱。

## 发现与修复

### 1. 助手与首页可能显示不同的同一餐

- 日历已有较新的记录时，首页显示该记录，助手仍可能显示旧工作区菜单和人数。
- 部分已采用菜单虽然显示了操作按钮，处理器却直接返回；撤销成功后还可能保留撤销前的人数。
- 采用前的回读若发现日历记录已变化，原路径还可能继续使用较旧工作区；替换确认文案还引用了不存在的餐次字段。
- 现由 `utils/meal-record-view.js` 共用展示判定。存在有效保存回执且版本、日期和餐次一致时才允许修改；仅有日历记录时只读展示。采用前发现更新先刷新目标，不覆盖较新记录。成功撤销同步上下文，仍保留服务端回执和后续本地编辑的边界。
- 验证包含：日历更新后助手重新显示、无工作区的记录、已采用菜单撤销、旧卡片不可写、回读期间更新记录、餐次文字，以及较晚撤销结果不覆盖新编辑。

### 2. 历史整餐做法错误读取当前菜谱

- 原整餐做饭模式已经验证餐次，却重新按菜品 ID 读当前菜库；菜品下架会阻断旧记录，新配方可能悄悄替换历史配方。
- 现在先使用该记录内保存的完整 `recipe`。旧记录缺少完整配方才查询当前可访问菜谱，并提示具体哪些菜使用当前菜谱。
- 账号、页面代次、餐次版本和读取权限检查仍先执行。快照不使下架菜重新进入可选菜库。
- 本轮未改变日历菜品行通往普通菜品详情的导航语义；该详情仍查询当前菜库，不应被解释成历史配方详情。

### 3. 偏好保存失败后，重新进入会丢失待同步内容

- 原来保存失败虽然提示保留本机草稿，下次成功读取服务器却会覆盖草稿。
- 增加账号隔离的待同步草稿、每次保存的身份标识和缓存写入代次。只有对应成功回执清除自己的草稿；重新进入显示“有未同步的偏好，点击保存重试”。不会在普通读取时自动提交。
- 同值保存也计入写入代次，避免“值没变”时被较早发出的读取覆盖。旧保存不能清除新草稿，切账号后回执不写入当前账号。

### 4. 购物清单把内部食材标识显示成规格

- 标准食材的 `normalizedVariant` 同时承担业务身份，前端把 `salt` 一类内部 ID 拼到名称后，造成列表、费用和复制内容难读。
- 新增仅用于显示的可选字段 `variantLabel`。已识别的标准食材 ID 不展示；真实规格如“去骨”仍保留。
- 预览、已保存清单、费用、复制清单共用展示规则。原 `normalizedVariant`、汇总键、报价键、实际支出身份不变，不改原始记录，不需要数据库迁移。
- 使用实际 Java 服务产生并经 Jackson 序列化的 JSON，再交给前端真实展示、价格分组和复制函数验证；数据库访问由受控夹具替代。
- 旧客户端可忽略新字段；新客户端连接旧接口仍兼容。旧缓存/旧回执缺少字段时保留兼容展示，正常刷新取得新清单后更新，不能为清理显示而丢弃待恢复请求。

### 5. 文案、点击范围与文字可读性

- 五处普通恢复按钮统一为“继续查看结果”，原处理器和请求身份不变。
- 替换记录确认改为说明“日历和饮食回顾会随之更新”，移除与现有统一记录规则冲突的“实际用餐记录会保留”。
- 购物费用区改用“待买估算”，继续与实际支出分列。
- 共用日期选择器声明至少 44px 的点击范围；助手本餐要求输入框补统一占位文字颜色。
- 菜单、助手设置和清空清单等禁用控件用底色区分状态，不再整体降低文字透明度。助手消息和设置入场保留位移动效，等待圆环与提示点的循环动画不变。
- 对比度审计原来把多层渐变中的边框色也算成文字背景。修正为按背景层顺序合成，并以不透明覆盖、半透明混色、单层渐变三个回归验证；没有通过删除检查项掩盖问题。该工具仍只是颜色声明抽样，不是像素渲染器。

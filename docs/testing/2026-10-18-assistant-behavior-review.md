当前方向符合产品目标：用户说要求，模型组织简短回答，真实菜品卡片承接查看与操作，明确办理指令直接执行。主要短板在异常情况下能否保持用户意图、准确说明执行结果，而不是缺少更多功能。

## 发现与修复

| 问题 | 用户实际影响 | 本次处理与验证 |
| --- | --- | --- |
| P2：补充指令处理时覆盖独立草稿 | 用户补充“不要辣”后继续输入“还想加一道汤”，旧请求结束时新输入可能消失；重启后会话过期也会只保留“不要辣” | 区分已发送补充与未发送草稿。等待、失败和恢复均保留草稿；会话失效时保留原要求、补充和草稿，不自动重发旧操作。两条原始症状均先复现失败再通过 |
| P2：明确拒绝的新请求误续接到上一轮 | 新请求在接收前被拒绝，旧的已完成对话仍留在界面；补充流程可能据此发送遗漏原目标的新请求 | 补充绑定原请求和服务端 turnId；明确拒绝后停止自动续接，将原要求与补充留在输入框。回归验证不会产生第三次自动请求 |
| P2：Python 提前吞掉错误参数，Java 无机会纠正 | 缺餐次、错误餐次或未授权菜品编号，在 Python 已被转成“暂不可用”；上一轮 Java 单层测试不能覆盖这个跨服务缺口 | Python v2 返回仅内部使用的错误信号，由 Java 在原四次调用、30 秒期限内最多纠正一次，纠正前无业务写入；模型不能直接生成此内部信号，旧 v1 行为保留 |
| P2：确定失败仍被显示为“结果待核对” | 保存目标已变化或操作已过期，任务已明确不可重试，父对话却一直等待，用户反复核对也无法结束 | 使用实际任务终态结束当前步骤；没有已完成操作时标记失败，有已完成操作时保留真实回执并标记部分完成；后续步骤停止，不再确认同一失败任务 |

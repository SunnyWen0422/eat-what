# 复制菜谱：保存时创建（2026-10-11）

用户明确选择原产品方案：复制后先编辑草稿，只有保存时才创建“我的菜谱”；取消编辑不会留下副本。

## 当前行为

1. 详情的复制预览只读；“编辑副本”携带来源编号和读取版本进入编辑页，无写入。
2. 编辑页重新读取账号可访问的来源；来源已变化时，先提示用户重新读取，不隐式使用新版本。
3. 未点击保存时，草稿只在当前编辑页内。取消、返回、关闭或账号/服务来源切换均不创建副本。
4. 点击“保存到我的菜谱”后，`POST /api/dishes/{sourceId}/copy-edited` 提交版本、稳定请求编号、`editCopy: true` 及编辑字段。独立路由强制应用编辑语义；后端校验来源可访问性和版本，在一次事务中插入最终副本并保存质量证据和回执；不采用先复制再更新。
5. 未修改的结构化用料、丰富步骤、步骤图、技巧、菜品图和来源保留。修改配方事实后，对应核验声明变为待核实，保留来源血缘，不能沿用已核验人数或用量。
6. 保存结果未知时，编辑冻结并保留原请求；重进仍核对同一保存。返回编号缺失、无效或错误地指回源菜，也按结果尚未确认处理，避免再次创建。
7. 旧客户端不提供 `editCopy` 时，原复制契约保持兼容；该新字段为 null 时不参与序列化，已有回执哈希不改变。历史未确认复制按原请求恢复后进入副本编辑，不自动追加更新。
8. 既有“配餐（side）”分类贯通新增、个人编辑、复制和菜谱筛选，不再把配餐静默改成荤菜。
9. 结构化对象材料与步骤显示为可读行，例如“鱼 1条（去鳞）”“蒸熟”；编辑页不显示 JSON、步骤图片 URL 或来源元数据。数量缺失时只保留名称，不猜克数。未修改这些行时，提交仍使用原 JSON，保留未知数量、步骤图片和额外资料。

## 发布要求

新小程序保存草稿依赖本次后端 `/copy-edited` 行为。后端与小程序应按配套版本交付，后端先上线后再更新前端。旧后端缺少新路由时返回 404，前端保留输入并说明保存失败，不回退旧 `/copy` 造成修改丢失或假成功。历史旧请求仅使用原路由核对既有结果。当前用户暂停前端上线，本次保持本地开发，不自动部署。

# 统一餐次记录：本地验收与发布边界

日期：2026-10-25。基线：`7e1d550a93df164aeb1fd3290d04d380eb9436d9`。本记录覆盖本次提交的改动与本地验收；未执行线上发布。

## 用户确认的规则

保存到日历即成为餐次记录，不再要求确认“吃过”。未来菜单立即显示在日历，到北京时间对应日期才计入默认饮食回顾。草稿不计入。统计表达为餐次记录与配方参考营养，不宣称个人实际摄入。

首页同一天保留当前餐；新一天返回首页展示今天，昨日草稿和未知请求保留原日期归属。主动从日历查看历史日期仍可使用。移除“保存计划与周回顾”复合入口和其常驻提示；保留真实写入的版本、账号、请求恢复保护。

## 实现与数据口径

- `recipe_records` 为唯一可写餐次来源。首页读取保存记录，日历、回顾、助手及近期避重共用它；未来记录不进入截至今天的回顾及近期记录。
- 内部 `MealConsumption`、`actualDetails`、`recentActual` 等旧字段名只是只读传输适配，不再代表独立的实吃业务状态。适配状态固定为 `recorded`，来源为 `calendar_records`。
- 旧 `PUT /api/meal-consumptions/...` 返回 410，提示到日历修改；不会继续写第二份状态。
- 报告计算版本为 `calendar-records-v1`，移除计划执行对照。按账号、日期和餐次去重，删除及编辑后重新计算。
- 仅修改记录名称/人数时保留原菜品快照，包括已下架菜、自由填写内容及历史营养；不使用当前菜库覆写旧内容。复制到其他餐次携带来源日期、餐次和版本，由服务端读取当前账号拥有的原快照；来源已变则拒绝，旧请求重试先读取原回执。
- 食谱分量固定，人数不乘菜量；缺失营养不填假总值，显示能量取整。

## 以后上线时的顺序（本轮未执行）

这是一次配套变更，不能只发布新版小程序或只覆盖服务包。旧客户端的独立“吃过”写入口将停止支持；新旧 UI 不承诺混用。

1. 另行确认生产发布目标和窗口，先核对运行服务、数据库和客户端版本。备份完整数据库、Java/Python 包及配置，并记录哈希、旧回滚版本和恢复方式。现有原始记录不得覆盖后再补备份。
2. 进入维护窗口，停止 Java/Python 中的写入及后台任务。确认没有并发写入，再通过明确的数据库名、端口和环境变量执行 `scripts/unify_meal_records.py` 的预演；该脚本只访问明确的回环数据库，不自动加载项目凭据。
3. 检查预演审计，再用**另一个新备份目录**执行 `--execute --application-stopped`。脚本将原始记录先备份，再归并；同槽采用较新的日历修改/删除或旧实吃更正。旧明确没吃转为删除，旧撤销实吃不删除原菜单。自定义名称、历史菜名、份量和可用营养保留；不从现库推造旧值。
4. 归并和内部迁移日志事务提交后，将旧表重命名为 `meal_consumption_archive_v1`；`meal_record_migration_state` 仅记录一次性迁移完成状态和哈希，不是新的餐次状态。确认状态 `complete`、唯一槽位、原始/有效数量与审计相符，收藏/采购内容不变。
5. 如在提交后、归档前中断，脚本仅在归并后快照哈希完全一致时续做归档，不重复覆盖记录；发现其他写入则停止人工核查。若已经归档且日志匹配，重复执行返回 `already_complete`。
6. 配套启动本版 Java 与 Python，再发布匹配的小程序。验证 `recordPolicy=calendar-records-v1`、今天保存立即入统计、未来日期边界、编辑/删除回顾变化、助手只读与保存、购物清单及跨账号；本次真实模型预算不能从历史授权推断。
7. 回退必须保持服务、数据和客户端语义一致。开放写入前可按完整备份恢复；开放写入后先保存新记录、按账号/日期/餐次做差异对照，不能直接用旧备份覆盖新记录。

生产迁移前还需完整备份和真实数据审计；本地合成样例不能证明生产每一行的转换结果。

## 最终复核与修复

独立只读复核发现两项问题，均已复现并修复：

1. **显示日历新菜但保存引用旧工作区。** 日历快照现在明确只读，`canConfirm=false`，不会打开旧草稿保存确认，也不会误报“当前菜单有修改”。主动重新安排才转回可编辑草稿；显示、保存来源和已有记录各自绑定。
2. **历史记录 11 道菜误触生成上限。** 读取历史记录不再把全部菜数强送入最多 10 道的生成配置；已有内容完整显示，配菜摘要按实际记录展示。生成规则保留原上限，不把合法历史记录判成离线。

两项回归先失败再通过；证据为 `review-red.log`、`review-green.log`。最终前端回归为 `ui-accepted.log`（130/130）。另补充历史自由文本复制回归、来源版本冲突和真实 MySQL 复制验证；`copy-record-green2.log` 通过，真实库结果在 `mysql-acceptance4/`。

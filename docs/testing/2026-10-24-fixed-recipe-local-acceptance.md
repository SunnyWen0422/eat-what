日期：2026-10-24。范围为当前开发分支、小程序及相关后端，附带公开网页兼容检查。仅使用本次新建的本地 MySQL、Java、FastAPI 和模拟模型；没有访问生产、调用外部模型、推送或部署。

**最终状态：本次本地验收通过。** 最终服务包的 7 个接口阶段全部完成，主验收统计 21,809 次 HTTP 请求；助手另通过 5 次本机模拟模型 HTTP 调用完成真实服务串联。这是本地接入与测试结果，不是生产发布完成证明。

## 验收口径

- 同一道菜以食谱所列材料和用量为标准，不随用餐人数放大。步骤和整菜营养同样不变。
- 明确人数后才能提供整菜营养除以人数的均分参考；这不等于个人实际摄入。
- “适量”保留空数值；无法完整计算的整菜营养保持空值。可选食材变更会重算该配方。
- 首页和助手只调整人数、未改变菜数和其他选菜条件时，保留有效的原菜单。改变自动搭配菜数、忌口等条件时，仍按新条件处理；过期菜单不能因为改人数而恢复有效。
- 日历安排与实际吃过分别记录。营养回顾使用实际记录当时的整菜营养快照及覆盖范围；不把缺失项当成零，也不根据今天的菜库补造历史营养。

## 本次发现并修复的问题

1. **助手仅修改人数却重新抽菜。** 真实接口测试复现后，增加回归再修复：人数单独变化不触发随机重选，保留已有菜品、内容版本和轮换状态。助手撤销仍恢复原人数与菜单；明确条件校验没有放宽。
2. **首页修改人数仍要求重排。** 对有效菜单采用相同分食语义，并推进方案版本、保留历史快照，避免界面把尚未保存的新人数误认为已写入日历。改变菜数或原菜单已经失效时仍要求重新安排。
3. **测试服务启动时的能力协商未就绪。** 首轮助手失败时未进入模型步骤；增加有限的真实能力就绪检查后才提交一次业务请求，超时明确失败，不自动重发业务回合。
4. **手选早餐被重新套用自动推荐范围。** 独立复审发现后增加失败回归并修复：单独改人数保留服务端记录的手选来源，同时仍执行当前归属、菜谱版本及硬限制校验。手选非早餐标签的菜→改人数→保存→撤销、菜谱已变化时拒绝，均已通过回归。

前轮还修复了固定策略缓存隔离、购物来源不随人数拆分、购物外键指向旧备份表、标准数据精度及内容版本、个人编辑结果不明时的草稿恢复等问题。相关变更沿用各自的回归证据。

- 本次是结构、计算与业务链路的技术验收，不等于逐道人工试做或逐条营养实验测定。

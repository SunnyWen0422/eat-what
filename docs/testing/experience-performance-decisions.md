选择**只优化任务排队的发现路径**：在创建任务的原事务中发出身份事件，事务成功提交后立即唤醒既有有界 `pending()` 选择，再向原两线程/八排队位执行器提交。通知不赋予新任务越过既有持久等待顺序的权限；worker 仍执行原 guarded claim。保留250ms持久轮询处理拒绝、通知丢失、重启与过期 lease。没有加线程、连接、数据库索引或新缓存；没有改候选扫描、排序、快照、准确总数、256批次上限、游标、硬忌口、保留菜、确认与按taskId取消。

不选跨请求候选缓存：没有可靠的全局数据版本失效键，且会引入跨账户/快照风险。不选增大执行器或连接池：这会掩盖真实容量。扫描和规划重复计算留作剩余瓶颈，不能为追求门槛把多项优化混到同一次比较。

## 负载合同

`bench(runtime, concurrency, seconds, user_mode='two-shared')` 支持 `two-shared` 与 `per-worker`。前者固定验证两个账号（c1实际只有一个活跃账号），后者在当前 owned runtime 的新数据库创建/核验1、10或25个合成账号，再逐一调用认证资料接口核验身份；不以签发不存在用户的JWT代替人口。

`--comparison-duration equal` 默认让基线与候选使用相同时长；`legacy-20s` 明确仅历史诊断，不允许前后改善结论。正式两种用户模型分别运行6665/50000 × 1/10/25，每场300秒、每候选模型独立1800秒；基线时长独立，不计入候选门槛。每场同为10秒预热、50ms客户端节奏，冷启动单列。任一worker恢复失败/提前退出，整场不计持续门槛。完整失败、样本和日志保留。

目标不变：普通及复杂列表 p95≤300ms，非模型整餐 p95≤1000ms，无故障错误率<1%，结束残留worker/活动任务/owned进程为0。未达时报告实测容量与剩余瓶颈，不改变门槛。

正式矩阵绑定每场实际源码、JAR、构建回执、配置和数据指纹，采集 p50/p95/p99、错误、队列、SQL、堆与GC；运行中不改源码或并行重型构建。

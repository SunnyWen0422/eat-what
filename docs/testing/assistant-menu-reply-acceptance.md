## 真实模型：20/20次HTTP尝试

仅读取批准的本机供应商配置；Java、Python、数据库、账号、菜谱均为隔离合成资源，未访问线上用户数据。失败占额度，达到20即停。

|任务|观察结果|
|---|---|
|生成一荤一素一汤|实际组成正确，真实可访问菜谱，简短权威反馈|
|替换第二道|只换目标菜，其他菜保留|
|只查看本餐|未改菜单或落库；仍可能返回固定事实摘要|
|比较两道菜用时|先因模型用菜名作引用而回退，修正提示后得到自然且有依据的比较；另一对菜正确差值曾被拒，已补确定性差值验证和原症状回放，但最后这处未再发真实比较请求|
|仅本餐不吃鸡蛋|实际菜单不含鸡蛋，长期偏好不变；不合规解释回退。已阻止把完成的本餐调整说成“确认后才写入”|
|保存到明天晚餐|首次供应商超时；重试后预览正确，确认后保存到正确日期/餐次，未新增实吃|
|采购刚保存的餐|单独预览/确认，核对餐次来源、版本与实际条目；未知价格、份量不编造|
|简单一点|澄清每道菜最多几分钟，没有擅设时间或改菜单|
|香菜和葱分别排除|首次缺完整菜单ID而失败，原餐保留；补合同提示后最后2次请求完成两项独立过滤，长期偏好不变|

20次中1次供应商HTTP失败；其他响应不等于全部效果合格。单次供应商等待中位数2.83秒、最大10.48秒，仅为本样本观察，不是生产性能承诺。完整失败、回退、修复和重试记录均保留。

示例真实回复：“清炒西兰花更省时，约10分钟；香菇鸡丁约20分钟，差10分钟。” 同时保留真实菜单卡。没有把模型文字作为菜单修改、日历保存或采购成功的依据。

**自然表达尚不能认定普遍无需编辑。** 模型仍可能填错claims、把原料数组填成文本，或增加未支持说法，触发保守回退。不能用业务成功冒充自然回答合格；重复调试样本也不能算普遍用户完成率。没有真实参与者，用户重述/额外点击的研究指标未测量。

## 四条真实服务隔离流程

供应商输出为受控替身，Java → Python → MySQL及落库真实执行；不证明模型意图理解率，也不代替实体点击验收。

1. 已有食材定餐 → 保留第一道 → 换素菜：菜单、锁定和已有食材保留。
2. 二菜比较 → 真实卡 → 选入本餐：自然解释保留，比较不改餐，选入仅替换目标。
3. 临时鸡蛋排除 → 合法完整菜单：本餐过滤落地，长期偏好及日历/采购/实吃数量不变。
4. 调整人数 → 日历确认 → 原确认重复核对 → 采购独立确认：只保存一次、餐次正确、采购新增、实吃不变。

前三条通过；第四条验收提案最初漏传合同要求的完整菜单ID，改正后只重跑第四条并通过，未全量重跑。

## 兼容、回退与执行取舍

- 新回答开关 ASSISTANT_V4_NATURAL_REPLY_ENABLED=true，模板默认关闭；Python能力探测必须支持 meal_reply.v1。旧服务404、关闭或回答不合规时沿用原助手，卡片/确认/历史保留。扩展要求还需既有 ASSISTANT_V4_EXTENSIONS_ENABLED 和界面协商；本轮隔离启动明确开启，生产和根项目API未改。
- 关闭新回答不会撤销已完成业务，也不换请求ID重试未知结果。语音仍提示暂不可用。
- 有限回答依据优先最近查询对象，未入解释的菜仍在真实菜单中。缓存只复用有新鲜权威版本的当前餐，其他读取不缓存；牺牲部分提速以免用旧事实。
- 多食材原话无法可靠拆分则澄清，合法结构化列表照常执行；未支持单位或措辞可保守回退。保留A/F、图片来源、复制保存才创建、缺价为空及计划不算实吃。
- 按用户要求保留正式本地分支和证据，不套用全量重测、清理工作树、推送或上线流程。

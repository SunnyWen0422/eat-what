# 统一餐次记录与跨日首页

## 已确认的规格与目标

用户于 2026-10-25 确认：保存到日历即记录；未来日期的菜单立即显示在日历，到对应日期才纳入默认饮食回顾。取消让用户另行区分“计划”“吃过”的流程。首页同日保留当前餐，跨北京时间自然日再次进入时默认今天。移除首页复合任务入口及重复提示。

## 架构与边界

- `recipe_records` 是唯一可写餐次事实，仍按账号、日期、餐次唯一。草稿不计统计。
- 旧 `meal_consumption` 仅在一次性迁移时读取、归档；旧的标记吃过接口停止写入。内部旧 DTO 名称可保留作传输适配，不再代表第二种业务状态。
- 迁移保留原始行和选择依据；同槽位采用较新的用户修改，旧实吃更正可覆盖早期菜单；明确没吃转为删除，撤销实吃不删除原菜单。较晚的菜单修改或删除优先。收藏、购物清单及其手动修订不改。
- 回顾以北京时间今天为上界，未来菜单不计数、不计营养；编辑和删除后直接从同一来源重算。
- 固定整道菜配方数量、不随人数放大；不补造未知营养，不将配方参考量称为个人实际摄入。
- 小程序、Java、Python 助手契约协同调整；独立网页的浏览器本地数据不迁入账号。
- 本次只实施、验证本地；不操作线上，不调用真实外部模型，不使用控制电脑功能。

## 状态约束

| 事件 | 处理 |
| --- | --- |
| 保存成功 | 以服务端回执刷新日历和当前餐；统计实时读取记录，不再二次确认吃过 |
| 确定失败 / 取消 | 保留输入和原记录，不增统计 |
| 结果未知 | 同一请求查询/重试，不另发新写入；只在对应餐展示恢复操作 |
| 覆盖冲突 | 保留版本校验，只对实际覆盖确认 |
| 新一天进入首页 | 切到今天的工作区；昨日草稿、回执继续归昨日 |
| 显式历史导航 | 尊重选择日期，不强制回今天 |
| 切账号 / 晚到响应 | 沿用账号、工作区、请求归属检查 |
| 部分完成旧复合任务 | 保留后台回执，但不再作为首页日常入口或警告 |

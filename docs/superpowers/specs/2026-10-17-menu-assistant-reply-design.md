# 菜单助手：自然回答与快捷定餐设计

日期：2026-10-17。基线：`57917354e8dcbd4cccd04bceee83178ec9f4f47d`。状态：待执行的设计；不是已实现、模型已验收或上线声明。

## 用户目标

模型服务的目的，是让用户更快、更方便地按个人条件定好菜单。成功不是话说得更多，而是用户少重复条件、少翻页面、能理解为什么选这些菜并直接调整、保存和采购。

用户已明确：回答由模型自然组织，简洁但不死板；菜品卡片、图片和快捷操作必须保留。此次同时解决固定摘要、有限的菜品比较、模糊临时要求、低效工具循环四项问题，并单独验证真实模型效果。不要扩展成通用聊天、营养顾问或无关内容生成器。

## 取舍

不采用“只换提示词”：Python 的 `final_output` 和 Java 的查询回复生成都会替换模型原话，必须协调改造。

不采用“原样放行所有模型输出”：不让模型控制图片地址、页面路由、身份、版本、写入成功或确认按钮。

采用“模型解释 + 后端事实卡片 + 后端业务动作”：模型自然表达建议及取舍；后端解析真实引用、校验条件并执行；确定的保存结果继续使用简短回执，不额外调用模型润色。

## 用户可见结果

| 场景 | 应有体验 | 不应出现 |
|---|---|---|
| 家里有番茄和鸡蛋，安排这餐 | 根据当前人数和搭配给出可执行菜单，简短说明如何用上食材，附菜品卡 | 只返回搜索命中列表；声称数量一定够；反复问已有的人数 |
| 这两道哪个快 | 对两道真实菜的已有用时直接比较，卡片可查看；缺少任一用时就说明无法确定 | 自行补时间、营养和价格；把未选菜加入本餐 |
| 换一道，不吃香菜 | 只影响本餐，明确保留其他菜；存在确定目标时直接调整 | 写入长期偏好；丢掉保留菜；把文字存下却声称已执行 |
| 清淡一点、简单一点 | 有可执行的明确条件时应用；否则用一个问题和至多三个可执行选项澄清 | 任意把“简单”设成十五分钟；用未经核验标签承诺少油低盐 |
| 就用这套，保存到明晚，再准备食材 | 菜单、保存目标、采购预览按步骤连贯展示；分别确认真实写入 | 一个含糊确认覆盖全部操作；先声称已采购；执行后重新问同一问题 |
| 无匹配结果或信息不足 | 一句具体原因和一个可选下一步；不自动放宽硬忌口 | 长篇道歉、内部错误、空泛功能介绍、编造候选 |

表达默认一至三句，目标约 40–120 字；不是固定模板，也不是每次必须提问。总展示解释最多 280 字，推荐理由最多两条。详细食材与做法放卡片及详情页；用户明确追问时针对该问题另答，不重复整套菜单。

一次常规推荐只展示一套主菜单，最多十道菜（沿用现有菜单上限）；比较只支持用户指定的两至三道授权菜，最多两个已有事实维度：用时、食材交集或经过核验的标签。不得将多个菜的用时直接相加并宣称实际做饭总时长。

## 保留边界

- 保留温暖餐桌 A、助手/菜品轻透浮层 F、图片优先和圆角；不重设计其他页面。
- 模型不直接读数据库或执行 SQL，不新增自由工具；已有 11 类读取、草稿动作、两类确认写入和页面交接继续使用。
- 账号/API 隔离、原请求身份、版本冲突、未知结果恢复、迟到结果拒绝与取消语义保持。
- 保存计划不代表实际吃过；复制保存才创建；未知价格/数量保持未知，实际支出零有效。
- 临时要求仅作用当前餐；长期偏好需要原页面明确操作。不能仅把自由文本写进 requirements 后声称已经应用。
- 模型请求每 turn 最多四次、读取最多八次、每批最多四项、动作最多三步，保留现有总期限、租约和取消边界；不靠增加预算解决效率问题。
- 不新增运行依赖或数据库迁移，不修改生产配置，不推送、部署或访问生产数据。网页没有同等私有助手时不顺便增加账号/助手功能。
- 不重跑全量测试或全量负载；只做改动范围的行为检查、必要打包和开发工具验收，不发送真机二维码。
- 历史真实模型额度已用尽。实现可先离线完成，真实模型阶段须取得新的明确预算；未运行则记录未验收，不以模拟通过代替。

## 回答与事实合同

新增内部协商合同 `meal_reply.v1`，与既有 `assistant.v4.1` 共存。后端默认关闭新回答开关；本地验证显式打开。只有 Java 开关、Python 内部能力探测均支持时，才发送新字段。旧 Python/旧客户端保持原回复和卡片，不因新能力缺失关闭整个助手。

Java 组织本轮回答依据，只从本餐授权快照和实际执行的工具结果抽取，携带当前版本与数据缺失情况。依据 key 仅本 turn 有效，重复读取按实体/字段去重，并以较新的权威结果覆盖旧快照。显式空结果不能被旧快照替代。

`AnswerBasis` 包含至多 24 条 `EvidenceItem{key, entityType, entityId, fields, sourceVersion, unknownFields}`；可引用候选至多十道，先保留用户指定菜、当前保留菜和拟执行菜。依据编码最多 8,000 字符，并与当前 readResults 合计不超过既有 12,000 字符事实预算。超限先去重复/无关可选依据，不删硬限制；不足则按现有路径缩小范围或回退。6000 字符上下文上限不提高。

新输出 `AnswerDraft{segments, cardRefs}`：segments 为一至三条 `AnswerSegment{text,evidenceKeys,claims}`，全文合计最多 280 字；cardRefs 为至多十个后端提供的菜品引用 key。claims 只允许引用已有字段的 `field_value`、已知数值的 `less_than/equal` 或食材集合的 `intersection`，字段固定为菜名、类别、cookMinutes、ingredients、已核验标签。不得声明营养、费用、份量充足或写入成功。无事实判断的简短衔接句可无证据；不能借此放入新的事实断言。

Java 逐项核对引用、值、单位、关系和来源范围，纯文本显示，拒绝外链/执行指令。自然语言的语义不能被 JSON、正则或引用检查完全证明；这项剩余风险由受控表达范围、对抗样本和真实模型人工评阅覆盖，不能宣称零幻觉。发现疑似未支撑陈述时整段回退现有事实摘要，不做不可靠的自动改数字。

新自然文字只用于推荐/查询/比较和草稿调整解释。动作执行后重新对照最终菜品与版本；菜单发生变化时不能展示旧理由。日历与采购卡、写入回执、过期预览和部分完成状态始终由后端生成，模型 cardRefs 不能过滤或改变它们。成功、失败、取消状态不使用事先生成的完成话术。

公开 TurnView 继续使用 `reply + cards + status + continuation`，避免迫使旧客户端迁移。只存经过核验的自然文字及现有卡片，不把供应商原始结果、推理或完整证据包放入聊天历史或日志。

## 临时要求与连续上下文

明确的“不吃某食材”、人数、明确最大用时，映射到现有结构化条件，经服务端校验后应用。模糊要求不猜数值；新增受协商保护的 `meal_requirement` 澄清类型，前端声明 `meal_requirements_v1`，选项由后端根据现有条件词典和当前餐产生，最多三个，沿用有效期与版本校验。

规则：`less_oil` 只有存在可用且证据满足的标签条件时提供该选项，否则说明无法代为控制实际油量，并让用户选择已有的菜品筛选条件或修改本餐要求；`simple` 可以让用户明确选择“限制用时”后输入分钟数，不能自动设定；`dish_reference` 多个可能目标时让用户选菜，不根据模型的高置信度擅自改菜。只有可执行、已应用的条件才说已调整。

近期焦点从已有会话卡片、当前菜单、实际回执与用户澄清选择构造，不新增跨账号长期记忆。用户明确说全部重来、切餐、改目标时更新焦点；未确认预览不代表用户已选择菜单。

## 工具效率

工具结果已足够就结束。生成菜单优先一次均衡候选查询；已知当前餐不重复读；比较只补缺少的详情。使用规范化参数与来源版本记录本 turn 的查询签名，完全重复读取复用本 turn 结果并返回 tool_result，不再次访问数据库；版本改变则重新查询。分页 cursor 不同不视为重复。工具循环及输出校验失败也消耗现有轮数，不暗中重试供应商。

不默认增加“润色”或“模型审核”调用。前三次可查询，第四次必须收束；全部失败回退明确反馈与可用卡片，不能声称任务完成。

## 结果判定

离线固定 24 个正常场景、12 个异常/对抗场景，外加四条完整用户流程。正常样本覆盖明确生成、食材定餐、换菜保留、比较、模糊要求、跨步骤保存采购；异常覆盖缺字段、虚构引用、旧版本、注入、取消与结果未知。

硬门槛：选菜/权限/确认/版本断言全部通过；无虚构菜品、自动放宽硬忌口、临时条件污染长期偏好、重复写入或伪造回执；必要卡片及按钮不丢失。不能用平均体验分掩盖其中任何失败。

真实模型建议在另行批准最多 20 次 HTTP 请求后，先跑六个代表任务并预留重试/修复额度；达到额度或期限即停，不保证六个全部完成。每条记录实际请求数、工具数、总等待、完成事实、是否重复问已有条件、是否需要用户重述，以及简洁/自然/相关三项人工评价。报告分母为实际完成样本数；目标完成率不低于 80%、80% 回答无需编辑即可使用，且硬门槛零违规。这是小样本工程验收目标，不是普遍用户完成率。

本轮核心指标是任务是否完成、用户多做了几步、回答是否有用；字数、调用数和等待作为辅助，不以堆内容或提高评分为目标。

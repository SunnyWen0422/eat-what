# EatWhat 后续优化方向：省心、完整、稳定

日期：2026-10-26。状态：用户已授权开始边审查边改造，当前执行阶段 0 的本地验证与阶段 1 的核心流程；本文不代表所有阶段已完成或已获上线授权。

## 1. 目标与已确定的取舍

让用户用更少的操作完成“安排一餐 → 保存记录 → 准备食材 → 查看做法 → 回顾饮食”，并能放心退出、返回和继续。

用户已经明确：后续优先改善使用体验，为用户做减法，同时保持服务完整、稳定、简单；现有视觉风格经过整体调整，继续作为基线。配色、字体、卡片和动效只在出现可读性、触控或操作问题时局部修正。

本方案建议采用**沿现有使用路径逐段优化**的方式。它可以每轮交付一个可验证的体验收益，沿用已有页面和业务能力。整套视觉重做、新建一套“简易模式”、持续增加入口，都不作为本阶段路线，避免维护两套操作规则或增加用户选择。

实施边界：小程序及配套服务。独立网页仍按其独立产品范围处理，不自动接入微信账号数据。当前基础是正式仓库分支 `codex/v4-meal-workspace-green-20261003` 的 `2ee6397a5d86f05637bec80ec077212a0e7789b2` 与本地复审修复，发布状态需另行核对。

## 2. 后续每项改动都要符合的原则

1. **明确主操作。** 同一任务阶段有一个最主要的动作；同屏可以保留查看、返回、收藏等辅助能力，但不反复放置同义入口。
2. **沿用用户已经告诉我们的信息。** 日期、餐次、人数、临时要求和偏好在适用范围内连续使用；跨天、跨账号或用户主动换目标时按规则处理，不盲目沿用。
3. **减少无意义确认，保留真正的决定。** 普通查看、已明确目标的推荐不新增确认；覆盖记录、清空清单和无法判断的重要目标保留必要确认。一次明确确认不在后续步骤重复询问。
4. **结果比过程说明更重要。** 成功后让菜单、记录、清单直接呈现结果；不靠多条提示告诉用户系统内部经过哪些步骤。
5. **少打扰，不隐瞒。** 正常流程不常驻警告；失败、待确认结果和未同步输入只在相关任务中提示，并给出一个清楚的下一步。
6. **简化展示不能减少能力。** 取消、返回、撤销、手动选菜、明确排除和已有数据仍然可用；不能通过隐藏错误、丢弃输入或自动覆盖来缩短流程。

## 3. 保持不变的产品规则

- 保存到日历即记录；未来记录立即可见，到对应日期才纳入默认回顾。用户不再确认“是否吃过”。
- 同一天首页保留上次餐次；北京时间进入新一天回到今天。主动查看历史日期时尊重该目标，旧草稿不搬到新日期。
- 每道菜沿用食谱固定分量；人数用于共同分食，不自动放大材料。营养只有完整总值才汇总，缺失留空；能量展示为整数千卡。
- 收藏不提高默认推荐概率，也不参与口味学习；明确从收藏中选择才限定范围。菜谱浏览筛选继续严格筛选。
- 助手理解意图，实际菜品、保存结果和账号归属由服务校验；不能靠模型回复宣称操作成功。
- 当前“查看 / 撤销 / 采用”的用途、四行快捷入口、统一视觉规范继续沿用，不另加一套操作模式。
- 购物参考价和实际支出分开，缺价不补零；删除日历记录不连带删除已整理的购物清单。

## 4. 五条路径的目标体验

以下是待验证的体验目标，不是对当前线上步骤数的测量结论。计数起点为用户已经进入对应页面、完成登录且目标信息齐全；覆盖已有记录等必要确认另计。

| 用户任务 | 目标路径 | 重点减掉什么 | 不得丢掉什么 |
| --- | --- | --- | --- |
| 不知道吃什么 | 首页生成 → 看菜单 → 保存；顺利分支目标为生成、保存两次主要操作 | 重复填写已有条件、多个生成入口、保存前重复预览同一菜单 | 换一道、换一套、自己选菜、明确忌口和查看菜谱 |
| 让助手安排 | 说需求 → 得到菜单 → 点击采用；明确要求保存时按现有能力直接办理 | 重问当前餐次、复述大量过程、保存后再让用户保存一次 | 目标不明确时澄清、覆盖确认、撤销和失败后的输入 |
| 准备这餐食材 | 从餐次进入 → 核对清单 → 确认加入 | 再次选择相同餐次、重复填写人数、重复材料与内部标识 | 查看来源、修改分量、取消、真实规格及实付记录 |
| 查看做法 | 从菜品或餐次进入 → 阅读材料与步骤 → 返回后继续 | 不相关表单、与做饭无关的状态操作、返回后重新找位置 | 历史配方来源说明、阅读进度、缺图占位和下架边界 |
| 看之前怎么吃 | 日历看记录；回顾看范围内汇总 | “计划 / 吃过”双重确认、重复日期说明、解释内部统计状态 | 统计范围、记录修改/删除、营养缺失说明和未来日期规则 |

不为凑点击次数移除必要的确认或阅读步骤。若目标信息缺失，只询问影响本次结果的必要项；可选细节允许之后补充。

## 5. 交付顺序

按阶段退出条件推进，不先承诺缺少依据的工期。每阶段控制为一组有关联的用户任务，不并行改写所有模块。

### 阶段 0：收尾现有修复，建立可靠基线

已有本地修复包括菜单一致性、撤销人数、历史整餐配方、偏好草稿、采购名称及可读性，见[本轮复审](../../testing/2026-10-26-product-experience-review.md)。这些属于待收尾成果，不重新作为新功能开发。

- 整理最终差异与验收记录，保留无关工作区改动。
- 在隔离数据库验证记录、采购及相关并发写入；按实际变更范围检查，不重做菜库清洗。
- 在获准的原生验证方式下检查手机布局、键盘、长文本、触控和等待动画。继续遵守用户“不使用控制电脑”的限制，可由用户在设备上走指定场景并反馈。
- 真实模型验证另行确定本次预算；历史调用额度不复用。提交、推送及上线分别在对应授权下办理。

**退出条件：** 本轮已确认问题的验收证据完整；不存在已知丢输入、错餐次、重复写入或越账号问题；未验证项如实列出，不能用自评分批准发布。

### 阶段 1：把“生成一餐 → 保存记录”做得最省心

这是建议的第一轮体验开发范围，重点为首页、助手菜单卡和日历之间的连续操作。

- 逐条记录实际路径的点击、重复输入、弹层和页面跳转，按第 4 节目标删去可证明多余的步骤。
- 保留当前餐次、已有要求与手动选择。更改条件后，明确区分尚未重新生成的菜单和真实保存记录，同一问题只在一个位置给出下一步。
- 日期、餐次、人数、菜品和保存状态跨页一致；正常完成后无需用户手动刷新确认结果。
- 调整提醒只作用于对应任务，完成、撤销或切换目标后不残留；用户主动返回历史日期时不被自动跳走。

**验收场景：** 新用户首次生成；熟悉用户再次进入；只改人数；换一道；连续换一套；采用助手菜单；覆盖已有记录并取消；北京时间跨天；历史餐次返回；断网后恢复。

**退出条件：** 信息齐全、无覆盖的常见分支达到两次主要操作目标；所有保留能力仍可达；错误写入、输入丢失及旧卡片覆盖新记录的回归为零。

### 阶段 2：让助手更懂上下文，准确完成任务

沿用现有助手和服务端动作链，先核对缺口再改，不新建一个聊天产品。

- “换清淡点”“不要这道”“就按这个保存”等连续表达，继承已明确的目标和限制；仅在存在会改变结果的歧义时追问。
- 生成、修改、查看、保存、采购、回顾各自返回合适的结果，避免用同一段泛化回复应对所有任务。
- 成功回复简短说明完成了什么和作用于哪一餐；卡片与实际记录一致。部分完成说明已完成部分和剩余一步，不重做已成功动作。
- 正在处理时保留输入和取消能力；提示只描述真实状态，不编造进度百分比或已经完成的步骤。
- 停止后的已完成动作保留；未发送补充保留；未知结果先读取原操作状态，不能悄悄重发生成或保存。

**退出条件：** 受控对话样例覆盖上述意图及澄清、失败、取消、过期、迟到响应、部分完成；实际工具回执与用户看到的结果一致。真实模型检查有独立证据，不能以模拟回复代替。

### 阶段 3：压缩采购、做饭与回顾的操作成本

- 当前餐次进入采购时自动带入来源与食材，保留一次必要核对；已加入内容明确可见，重复点击不重复添加。
- 汇总、按菜查看、参考价、实际支出和复制内容对同一食材保持可理解的一致名称；规格和来源可查，主列表保持紧凑。
- 阅读做法时保留返回位置与进度；记录配方与当前菜谱的来源有明确含义，不因精简把历史内容替换掉。
- 回顾优先展示范围、主要结论和必要缺失说明；详细营养按需查看，不能用空值或不完整值制造“健康程度”的确定结论。

**退出条件：** 五条路径能衔接，用户无需反复找回同一餐、重复输入相同信息或重复确认统计；采购与营养规则不变。

### 阶段 4：减少等待与偶发中断

本阶段做系统性的性能优化；影响使用的稳定性缺陷在任何阶段都优先处理，不等到此阶段。

- 记录关键页面加载、列表切换、保存回执和助手首个有效结果的耗时，先取得同设备、同数据规模、同网络条件的基线。
- 删重复读取，优先展示明确归属的可用内容；缓存不能把旧数据冒充最新保存结果，不能跨账号共享个人内容。
- 请求超时后结束无解释的等待，提供真实状态与下一步；自动重试有上限，只用于安全读取或保留原身份的恢复。
- 排查慢查询、大响应、重复构建和内存增长；有证据才改，不为优化重新拆服务或迁移全库。

**退出条件：** 关键耗时相对基线无回退，已定位慢点有实测改善；异常不会演变成无限等待或重复操作。模型耗时单独统计，不许用提前显示“成功”来改善指标。

## 6. 用什么判断优化是否有效

| 指标 | 定义与目标 | 验证方式 |
| --- | --- | --- |
| 完成任务所需操作 | 分别统计生成、保存、采购等路径；常见生成保存分支目标两次主要操作，必要覆盖确认另计 | 固定起点、同一条件的前后路径记录 |
| 重复输入与无效跳转 | 已明确的日期、餐次等不重复填写；下一步已有数据时不绕回选择页 | 五条路径场景检查 |
| 操作结果可见 | 成功回执到达后，相关菜单/记录/清单无需手动刷新；用户能找到结果 | 页面与服务端实际回执对照 |
| 完成率与恢复率 | 只用明确发起的任务作分母；首次完成与恢复后完成分开，取消单列；有持续样本后再定百分比目标 | 优先复用现有日志和隔离用例，不把未知当成功 |
| 数据与输入安全 | 已知验收场景中零丢输入、零重复写入、零错账号/错餐次覆盖 | 失败注入、并发、重进、跨天及迟到响应测试 |
| 响应与等待 | 本地点击后即时反馈目标 200ms 内；网络、服务和模型耗时分别测中位数与 P95，先测基线再定预算 | 手机实际采样及对应请求时间；不以静态声明替代 |
| 用户是否需要解释 | 操作后能说明结果是什么、在哪里；不依赖解释“工作区、原请求、恢复任务”等术语 | 由用户或体验者完成固定任务并反馈 |

上述目标是后续验收标准，不是现有线上测量值。无需为此先建复杂埋点平台。若确需补充观测，只收集任务类别、耗时、结果码和必要关联标识；不默认记录聊天原文、个人忌口或食谱全文，新增采集范围单独评估。

## 7. 每轮开发与发布的规则

- 每轮选一个明确用户任务，写清原路径、目标路径、保留能力和验收场景。实现细节在该轮再落到具体文件与接口，避免现在预先设计不需要的新接口或表。
- 顺序固定为：复现或测量 → 最小完整修改 → 验证实际边界 → 复核同类入口 → 交付。稳定性问题优先于减少一次点击。
- 共享逻辑修复覆盖首页、助手、日历等真正受影响的入口；纯文案改动不强制全量回归。没有影响证据不扩大重构。
- 验证区分页面处理器、接口契约、真实数据库、真实模型、手机和线上环境。已知关键故障未关闭时不发布；未知范围标记未验证。
- 默认每轮形成可独立验收、可回退的一组改动；只有实际需要才做增量迁移。备份、用户收藏/记录/清单保护和发布后检查继续按运维规则执行。

## 8. 本阶段暂不安排

- 全面改配色、字体、布局或新增装饰动效；视觉仅做必要局部修复。
- 增加“简易 / 专业”等两套模式，或为相同任务新增多个入口。
- 重做推荐权重、引入新的营养标准或重新清洗全量菜库；有具体质量问题再按证据处理。
- 新增“吃过确认”、多套记录状态、重复保存或强制阅读说明。
- 为缩短路径自动删除、覆盖已有记录，或把用户的推荐请求默认为保存/采购指令。
- 大规模架构拆分、新建分析后台或直接扩容作为所有问题的默认解法。

建议近期只推进阶段 0 和阶段 1：先把现有修复交付证据补齐，再把最常用的“生成一餐 → 保存记录”走顺。后续阶段依次推进，用实际收益决定下一轮工作量。

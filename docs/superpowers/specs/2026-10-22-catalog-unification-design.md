# EatWhat 菜谱数据整体优化方案

日期：2026-10-22。状态：供用户审阅的设计稿，尚未批准实施。

历史稿说明（2026-10-24）：后续实施与用量规则已由用户进一步确认。本稿保留当时设计讨论；当前规则以[固定分量接入说明](../../data/canonical-catalog-v4-integration.md)和[最终本地验收](../../testing/2026-10-24-fixed-recipe-local-acceptance.md)为准，人数仅用于分食，不再缩放配方。

本次交付限于方案。不执行应用代码修改、菜谱批量生成、数据迁移、模型调用、发布、提交或推送。线上现状依据同日只读审计，不把方案目标写成已完成事实。

## 1. 目标与已经确定的约束

目标是把现有菜库整理为一套能推荐、能换算、能采购、能照做、能计算能量的 EatWhat 标准配方。HowToCook 提供内容与组织方式参考；发布后的数据由 EatWhat 按同一标准维护。

用户已经明确：

- 接受结构变动；同类数据只有一种正式结构、一份当前生效值、一套解释与计算规则。
- 生成、人工整理或开源改编的配方具有相同产品地位，不按来源区分“正式/未核验”等业务身份。
- 可以自行制定标准用量、份数、做法、时间和分类；内容须完整、自洽，不能把不同配方片段拼起来。
- 全量整理可以在制作区分批完成，正式运行不能新旧混读、缺值回退旧字段或长期双写。
- 收藏不增加推荐概率、不参与口味学习；首页与助手继续共用推荐策略和轮换。

本方案的新增建议均待本次审阅：标签目录、营养指标、缩放规则、试点规模和发布验收。方案不改变用户已经确认的推荐权重，也不把数据整理扩展为医疗营养建议。

## 2. 现状与方案选择

同日审计覆盖全部 6,665 道公共系统菜谱。菜系覆盖约 6%，规范口味覆盖约 9.3%，规范早餐标识为 0；全部 kcal 为旧缺省值 0。食材存在错误拆词和机械套用用量，材料和步骤多份存储。内容案例来自 20 道分层样本，不能用样本推算全库错误率。[审计报告](../../data/2026-10-22-catalog-audit-and-improvement-plan.md)

| 方案 | 收益与代价 | 判断 |
| --- | --- | --- |
| 在旧字段上补标签、填热量 | 短期修改少，但食材、份数和步骤矛盾仍会传给计算，各入口仍需解释多套字段 | 不满足唯一标准要求 |
| 用 HowToCook 全量替代现有菜库 | 内容入口集中，但已查看资料不能证明覆盖现有 6,665 道菜和完整营养参数；会影响现有菜品引用 | 不采用直接覆盖 |
| 建立统一标准，参考 HowToCook 重整现有数据 | 需要同步调整数据和所有消费者，可解决配方一致性、标签和营养计算，并保留用户关系 | 推荐 |

## 3. HowToCook 怎样参与

已查看其[主仓库](https://github.com/Anduin2017/HowToCook)、[模板](https://github.com/Anduin2017/HowToCook/blob/master/dishes/template/%E7%A4%BA%E4%BE%8B%E8%8F%9C/%E7%A4%BA%E4%BE%8B%E8%8F%9C.md)、[西红柿炒鸡蛋样例](https://github.com/Anduin2017/HowToCook/blob/master/dishes/vegetable_dish/%E8%A5%BF%E7%BA%A2%E6%9F%BF%E7%82%92%E9%B8%A1%E8%9B%8B.md)和 [LICENSE](https://github.com/Anduin2017/HowToCook/blob/master/LICENSE)。模板组织了原料工具、份量计算、操作和附加说明；样例包含数量取整、关联用量和可选食材。仓库标示 Unlicense。这里是所阅页面的结论，未据此宣称每份文件都完整或正确。

具体使用方式：

1. 实施时固定一个提交版本，记录文件路径、内容哈希和使用条件，禁止运行时随仓库最新内容漂移。
2. 优先参考早餐、常用家常菜，以及份数和步骤较清楚的配方；保留一种完整做法作为整理起点。
3. 将原文转换为我们的结构，再统一材料、份数、操作和标签。原文出现范围或可选项时，制定默认配方值和调整规则。
4. 对现有菜库未被开源内容覆盖的部分，按相同标准整理或生成，不创造另一套生成菜谱身份。
5. 即使参考内容已有热量，也不直接作为当前配方的最终热量；配方改变后统一重算。
6. 不直接复制健康功效文案或目录分类作为硬事实；图片逐项记录来源和使用条件，缺图使用现有分类占位。

HowToCook 和原始资料停留在制作与追溯范围内。正式应用不同时查询开源原文和本地配方来拼出结果。

## 4. 唯一正式模型

“唯一”约束的是事实和业务含义，不要求把所有内容塞进一张表。建议保留现有 food 的稳定 ID，重构现有 ingredient_catalog、dish_ingredient，增加所需关联结构。

| 数据对象 | 唯一负责的内容 | 明确不再维护的副本 |
| --- | --- | --- |
| 菜谱 | ID、规范菜名、菜品归组、基础份数、图片、分类、版本 | 第二套旧菜名/旧份数/独立展示配方 |
| 食材字典 | 食材身份、部位/形态、生熟或干鲜规格、别名、单位换算、成分和饮食属性 | 各页面、Python 或模型自带的同名食材表 |
| 配方材料 | 食材 ID、标准数量、单位、角色、处理、可选规则、缩放规则、成品贡献规则 | cl、ingredients_amounts、质量 JSON 中可独立修改的多份材料 |
| 操作步骤 | 顺序、正文、使用的材料、数量引用、方法、设备、时间及依赖 | step 与 steps 双份正文，正文中的手写显示序号 |
| 标签字典与关联 | 稳定代码、维度、层级、名称、适用规则 | 原始标签串、规范码及前端自建标签同时作为事实 |
| 计算输出 | 从上述数据得到的目标人数用量、采购量、能量和标签派生值 | 手填整菜 kcal、模型口算结果与计算器结果并存 |

原始文本、制作日志、旧质量档案和发布备份退出业务读路径。需要保留的来源、发布版本等维护信息，不作为一套可被页面选择的质量身份。

允许缓存计算输出，但缓存必须有配方、食材成分、标签规则和计算规则的版本依赖；不能手工编辑，失效后从正式数据重建。旧客户端需要的展示字段也只能由当前正式结构生成，不能保存为第二份事实。

## 5. 食材、份数与做法

### 5.1 食材身份

- 同义词归到同一身份，例如番茄/西红柿；复合词优先完整识别，玉米淀粉不拆为玉米，小米椒不拆为小米。
- 需要不同采购或营养参数的规格分别建身份，例如干木耳/泡发木耳、带皮鸡腿/去皮鸡腿、猪瘦肉/五花肉。它们是不同食材规格，不是同一数据的新旧状态。
- 香菇与杏鲍菇、芹菜与芹菜叶不混用。锅具、做法、修饰语不能进入食材字典。
- 复合调料记录实际组成关系，支持忌口和饮食属性向上汇总；名称相似不能代替完整配料关系。
- 别名只负责查找。含糊的“鱼”“肉”等必须在标准配方中选定具体产品规格，不能随机对应营养值。

### 5.2 标准用量

每道正式配方必须有明确基础份数。材料数量只维护一种权威单位下的值，克数、采购单位和页面文案均由其换算：

- 质量用克、液体可用毫升、整件可用个；毫升转克依赖该食材密度，整件转克依赖该规格可食重量，不统一按 1 毫升等于 1 克。
- 配方以可食净料为计算基准，购买带骨、带壳等商品时另用出成率推导采购量；不能把购买总重量直接算入营养。
- 同一行可有默认值、允许调整范围、可选开关，但一次本餐计算只得到一个确定数量。默认值属于完整配方，不是范围之外的另一版本。
- 公共标准配方的油、盐、糖、酱料也必须量化。“适量”可作为说明，不能是唯一数量输入。
- 可选材料有明确默认开关；关闭时不采购、不计能量，对应步骤也随之调整。
- 取消全库统一的“2人 + 15%冗余”。基准份数按配方制定，采购整件取整与食用净量分别计算，不再自动添加同一比例余量。

### 5.3 人数缩放

用有限、可验证的规则表达数量，禁止执行来源文本或模型提供的任意公式代码。

| 规则 | 处理 |
| --- | --- |
| 按份数比例 | 基础数量 × 目标份数 ÷ 基础份数 |
| 整件取整 | 先按比例计算，再按配方声明的步长取整；取整后的实际用量参与营养和关联计算 |
| 关联用量 | 例如油量跟随实际鸡蛋数；依赖必须无循环，先算被依赖材料 |
| 调料与水量调整 | 默认比例换算；确需非线性时明确份数对应表或有界规则，不能全菜统一套一个“少盐系数” |
| 设备批次 | 给定容量和适用人数范围；超过容量按明确批次安排时间，缺少规则时提示调整份数，不能承诺时间不变 |

示意：参考上述开源样例的数量关系，2份用3个鸡蛋、油12毫升；1份鸡蛋向上取整为2个，油随之为8毫升。不能把这份1人配方的油固定算成6毫升。它说明计算要求，不代表本次已导入或发布该配方。

基础份数表示“一道菜的分摊份数”，不等于完整一餐，也不建立每人必须吃多少的健康目标。

### 5.4 步骤与时间

- 步骤正文与顺序分离；需要显示材料数量时引用材料 ID 和本餐计算值，避免人数变了而正文仍写旧数量。
- 每项必需材料必须在步骤中被使用，每个步骤用到的材料都必须已列入；处理方式不得冲突。
- 准备、主动烹饪、被动等待分开记录；步骤有依赖与可并行关系。总历时由顺序推导，不把并行时间简单相加，也不漏掉浸泡、腌制和焖煮。
- 主列表继续显示“预计用时”，详情能说明实际动手与等待。“期望用时”偏好使用总历时，20分钟快手也按总历时派生。
- 不同时把“炖两小时”和“15分钟完成”发布成同一配方。提前备料可以有明确的本餐前提，默认从未备料状态开始计算。

## 6. 标签分类设计

采用一个受控字典，各维度各有含义。代码稳定、展示名可调整；父级由叶子和规则派生，不重复手工赋值。

| 维度 | 首版建议 | 使用规则 |
| --- | --- | --- |
| 菜品分类 | 沿用荤菜、素菜、汤羹、主食、点心饮品五个主要菜位，细分畜肉/禽肉/水产/蛋类、叶菜/根茎/菌菇/豆制品、清汤/浓汤/羹、米饭/面条/粥/饼/包点、甜点/饮品等 | 一道菜一个主分类叶子；食材混合时按配方主角色归类，不因同时有肉和菜占两个菜位 |
| 适用餐次 | 早餐、午餐、晚餐、加餐 | 可多选；早餐是餐次，不能与荤菜/主食互斥；按配方实际食用方式赋值，不把所有短时菜自动当早餐 |
| 菜系与地域 | 中式家常、川菜、粤菜及潮汕等子类、湘菜、鲁菜、苏菜、浙菜、本帮菜、闽菜、徽菜、东北、西北，以及实际涉及的其他菜系 | 一个主要归属；不能硬填地域，普通家常菜有明确中式家常类别；旧江南合并项映射到子类集合 |
| 口味 | 基础味感：咸鲜、酸、甜、辣、麻、苦；特色风味：蒜香、葱香、酱香、醋香、番茄等；辣度0—3；整体风味强度：清淡/适中/浓郁 | 麻辣/酸辣/酸甜等组合入口由基础维度派生；基础与组合不能重复加权。口味清淡不等于低脂、低钠或低能量 |
| 做法 | 炒、煎、炸、蒸、煮、炖、焖、烧、烤、焗、拌、汆、卤、腌等，并保留必要子类 | 以步骤记录为唯一来源，可多种；主方法由主要烹饪阶段确定。糖醋属于风味，不用作方法 |
| 设备 | 炒锅、汤锅、蒸锅、电饭煲、压力锅、烤箱、空气炸锅、微波炉等 | 区分必需与可替代；只把配方真正提供做法的设备列入，不随意声称空气炸锅与烤箱可互换 |
| 场景与操作 | 家常、便当、聚餐、单人食；新手友好、可提前准备、少步骤 | 场景按实际设计标注；快手与步骤数量由时间/步骤派生，“低投入”不替代耗时条件 |
| 食材与饮食属性 | 主食材、蛋白来源、蔬菜/谷物等组成；纯素、蛋奶素；包含的忌口/过敏原成分 | 从完整食材组成派生，含少量配料也不能跳过。荤素菜单分类与蛋奶素条件分别解释，不能按目录名认定可吃 |
| 营养筛选 | 每份能量、蛋白质、脂肪、碳水、纤维、钠的数值范围 | 首版用可解释数值筛选；不沿用模糊“健康”标签自动获得推荐加分，不默认生成治疗、减脂或低钠承诺 |

补充约束：

- 标签细分优先服务筛选、排除、搭配和学习，不追求每道菜挂几十个标签。前台先展示常用维度，详细分类按需展开。
- 同维度多选按“任一符合”；不同维度按入口语义组合。菜谱浏览仍严格筛选，推荐偏好仍使用已确认的软权重。
- 用户说“不要/只要/必须”、忌口、过敏原及明确设备限制走硬条件。餐次安排只从对应适用候选中选，明确点名或手选按现有规则处理并提示冲突。
- 本餐想吃、长期偏好、手边主料和学习的权重及上限沿用既定策略。增加子标签不增加维度数；父子标签命中不能分别得分。
- 收藏依然只用于收藏或明确限定范围，不能因数据改造加入默认偏爱分。
- 旧偏好做确定性映射；无法一一对应的旧组合保留等价集合或让用户明确选择，不能悄悄丢掉。学习事件保留发生时的菜谱与特征版本，不用新标签反向重写旧喜好；有歧义的旧特征不参与新聚合，数据不删除。

## 7. 能量和营养计算

### 7.1 食材成分标准

每个标准食材规格只有一份当前生效的每100克可食部分成分记录。首版覆盖：能量（千卡）、蛋白质（克）、脂肪（克）、总碳水化合物（克，含膳食纤维口径）、膳食纤维（克）、钠（毫克）。不同外部口径必须在制作阶段转换；能量不由前端再次拿显示后的宏量营养素倒算。

建议使用 [USDA FoodData Central](https://fdc.nal.usda.gov/data-documentation/) 的相应食材记录作为可落地的成分参考，结合可以合法使用且规格更匹配的本地食材或包装资料。FDC 区分基础食材、调查食物、品牌食品等，资料类型和份量口径不同；不能混用生料、熟食、品牌与泛用食品的数字。[官方说明](https://fdc.nal.usda.gov/faq/)

制作规则：

1. 先匹配食材、部位、生熟、干鲜和产品规格，再挑选一份完整、适用的成分记录；匹配程度优先于来源名称。
2. 有多个能量指标时在导入阶段按固定规则选定一个：同一匹配记录优先采用具体 Atwater 因子能量，其次一般因子能量，再取记录明确提供的能量值；保留采用的指标和版本，不把多个能量相加或运行时轮换。FDC 对两类因子有明确说明。[能量口径](https://fdc.nal.usda.gov/faq/)
3. 缺少对应外部条目时，可以按复合材料组成和明确计算规则建立 EatWhat 成分标准；确需自行制定的参数记录依据与计算假设，经相同一致性检查后成为唯一正式值。模型可以协助制作，不能每次对话临时编一个数，也不能虚构检测结果。
4. 现有 kcal=0 不导入为零能量。水等实际为零的成分与旧缺省0必须区别处理；缺少数值先在制作区补齐，不能正式计算时把缺项按0相加。
5. 全部在隔离制作环境读取和处理参考数据，只向线上发布用得上的食材条目，不把完整外部数据库常驻在小服务器内存中，也不让每次用户请求访问外部营养API。

正式系统不显示“生成未核验”“高低可信版本”。成分来源和推导依据属于维护资料，用户统一看到“按标准配方计算”。

### 7.2 统一公式

对于目标份数，先完成可选项选择、数量缩放、整件取整、关联用量与克重换算，得到每项实际可食净量 q_i。

```text
整道菜营养 N_j = Σ [q_i / 100 × 食材每100克营养 n_ij × 成品贡献比例 r_ij]
每份营养 N_j_per_serving = N_j / 本次配方份数
整餐营养 = 该餐各道菜实际制作量的营养之和
每人均分值 = 整餐营养 / 用餐人数（仅在选择均分时使用）
某人记录的摄入 = Σ [相应菜品营养 × 该人实际食用比例]
```

能量是其中一个指标，使用相同流程。按整件取整或关联规则变化的配方，其每份能量不保证随人数完全恒定。

### 7.3 投料、采购和成品的区别

这三者具有不同业务含义，必须有清楚的关系，不能为了“一个值”把它们混为同一个重量：

- **采购量**：需要购买的规格数量，可含皮骨、整包装和取整；来源是配方净量与统一换算规则。
- **投料净量**：真正进入烹饪的可食部分，是配方材料的权威数量。
- **成品贡献**：投料中留在实际食用部分的营养，由明确规则计算。

默认整份食用且无丢弃的配方使用 r=1。油炸锅中的全部油不能都算作吃进去；腌料、倒掉的汤汁、取出的材料等必须在该配方中设置明确的成品贡献。油脂、钠等可使用分别定义的比例，不能把一个笼统减重系数套到全部营养素。比例属于本产品计算参数，应有来源或制定依据，不能在运行时猜测。

煮饭加水、炖汤蒸发改变重量，不按重量变化把整锅能量同步乘减。避免同时使用熟食成分和生料投料再次计算同一份营养。

首版交付整道、每份和整餐能量；不强制推出“成品每100克”显示。若后续需要该显示，须先定义一致的成品重量口径，不能用原料总重代替。

### 7.4 展示与用户操作

- 菜品详情默认显示“每份 ×× 千卡”，可查看整道菜、基础份数和营养明细。后台保留计算精度，能量显示到整数千卡，宏量营养素到0.1克，钠到整数毫克；用未四舍五入的值汇总。
- 本餐菜单显示整餐与按人数均分结果，清楚标注“均分”；改变份数、选项和材料即重算，步骤和购物清单同步。
- 当前只有“吃过”的记录不自动当作某个人吃完整餐。无实际比例时可以展示该餐标准配方营养，不称为本人摄入。
- 日历仍是计划；实际用餐独立记录，营养结果与当时使用的配方、成分版本绑定，后续菜谱更新不重写历史摄入。
- 首版用组成、数值与变化解释饮食情况，不从热量单一指标自动给“健康100分”，也不默认一个统一每日热量目标。

## 8. 首页、助手和全部消费者的接入

### 8.1 统一服务边界

Java 后端持有正式配方、标签与计算能力；Python 助手服务理解意图和组织回复，通过接口使用相同候选与计算结果。小程序和网页负责展示与操作，不能各自维护食材解析、营养参数或不同的缩放公式。

助手接收：菜品 ID、版本、匹配原因、明确份数、计算结果和约束是否满足。模型不能覆盖菜谱材料、直接改数据库 kcal，或把没有执行的换算称为已完成。

建议对外发布统一的 catalogContractVersion、taxonomyVersion、nutritionRuleVersion 和 catalogRevision。它们表示合同与当前发布，不形成可供业务混选的新旧菜谱集合。

### 8.2 必须覆盖的入口

| 入口 | 本轮目标 |
| --- | --- |
| 首页生成/换一道/换一套 | 完整标签与食材进入原概率策略，继续按统一菜品归组轮换 |
| 助手推荐/查看/采用/撤销 | 同一菜单、配方和营养结果；保留账户、任务和版本保护，操作成功后才记轮换与学习 |
| 菜谱搜索/个性化筛选 | 全部使用新字典，严格筛选语义不被软推荐放宽 |
| 菜品详情/食材与做法/大字阅读 | 同一材料与步骤输出；保留两列食材、单序号、紧凑样式，清除旧待核验身份文案 |
| 购物清单/复制/参考价 | 按食材ID及采购规格汇总；自定义材料仍只需名称、分量、备注；保留手填内容、已购状态和实际支出 |
| 日历/实际用餐/回顾 | 保存计划不冒充摄入；已记录的历史事实不因新菜谱重算而改变 |
| 个人菜谱/复制编辑/管理端 | 使用相同字段与数量规则，不把新内容写回旧拼接字符串；未填的个人可选信息保持空，不编造数值 |
| 独立网页 | 同步适配公共菜库合同；不改变其浏览器本地个人数据归属，不扩张公开菜库授权范围 |
| 检索索引/缓存/模型工具描述 | 从当前正式发布重建，不能保留旧标签或旧营养字段作兜底 |

个人菜谱和自定义购物项目不是公共标准配方的替代版本。它们保留用户实际输入与权限，使用相同字段定义；缺少计算所需输入时不输出假数，不建立“旧版私人配方”的并行读取路径。此次不自动重写用户内容。

价格仍遵守既有规则：官方参考价与实际支出分开，缺少参考价不猜测、不填0。营养成分的产品标准不成为生成市场价格的授权。价格换算使用标准材料身份、采购单位和有效报价，不继续依赖旧 VERIFIED/UNKNOWN 质量状态。

## 9. 重名、稳定 ID 与用户数据

- 原6,665条记录逐条给出处理去向：规范保留、同配方合并关联、实质不同做法明确命名。不能未经处理就丢弃，也不能只迁一部分后让其余继续读旧值。
- 同菜同做法合并为一份当前标准；烤/炖等实质不同配方可以分别保留，名称明确，均属同一模型。
- 每条旧 ID 都有唯一确定映射。收藏、常用菜单、日历、购物来源、实际用餐、助手菜卡、学习与轮换关联均纳入迁移检查。
- 同名或近义菜归到稳定的 dishGroupId，自动轮换按组去重；不同版本不能绕过避重，手动点名仍遵循原产品规则。
- 合并导致同一账号多条收藏或轮换映射到一组时，用确定性去重保留用户意图；实际事件和历史快照不删除、不折叠成当前配方。
- 归档原始资料与历史事件不参与当前菜库查询。这些是追溯记录，不是第二份当前标准。

## 10. 分阶段制作，一次统一切换

### 阶段A：冻结规则和验收样例

交付字段契约、标签字典、单位规则、营养指标口径、旧ID映射原则和跨服务合同。覆盖早餐、复合食材、整件取整、可选项、油炸/腌制、长等待、多人搭配等案例。

本方案经审阅后再编写逐项实施任务；尚未决定的具体外部模型、调用数量和费用上限在实施预算中明确，不能沿用此前已消耗的测试额度。

### 阶段B：隔离100道试点

按五大菜类各取20道，餐次作为交叉维度，至少20道适用早餐。覆盖上述复杂数量和加工情况；从现有资料和固定版本的 HowToCook 制作完整配方。

交付结构化菜谱、实际引用的食材与成分字典、清洗/生成/验证脚本、差异报告，以及首页→助手→详情→购物→营养的隔离演示。全部留在制作环境，不先把100道作为一套新菜混进线上。

### 阶段C：全量重整

逐批处理全部原记录和确认新增的早餐内容，按同一规则产出正式候选；重名、材料、份数、步骤、时间和标签一起处理，不只补几个字段。

每批可重复执行、可断点续作，以 ID、输入哈希和规则版本保证幂等。全量规则检查与内容一致性检查覆盖每道菜；人工查看试点、异常项和分层样本，报告实际覆盖范围，不冒充全部实做。

最终发布包包含规范数据、来源与使用记录、ID映射、派生索引、版本清单、逐条处置统计、检查结果、迁移与恢复脚本。重要原始快照保留在独立恢复位置。

### 阶段D：消费者适配与完整验收

在隔离数据库中演练现有数据迁移和回退，测试真实 Java/Python 序列化边界、小程序入口和网页读取。移除旧字段解析、旧质量状态门槛、演示营养数组的正式使用以及缺值回退路径。

同步调整 README、开发者手册、数据规范、模型工具合同、导入工具和管理员写入入口，避免旧文档要求重新制造双轨结构。

### 阶段E：生产统一发布（届时单独执行）

1. 核对实际运行版本、用户写入增量、内存和磁盘预算，生成完整备份并验证隔离恢复。
2. 进入明确维护窗口，停止有影响的菜谱、助手和相关业务写入，等待或取消并核对在途任务，防止跨版本提交。
3. 在维护期间完成正式数据、合同、服务和索引的配套切换。MySQL结构语句不能被假设为整个可回滚事务，按已演练的迁移与恢复步骤执行。
4. 旧客户端若能接收当前标准的确定性展示投影，可以继续读取；无法表达新语义的写操作要求更新，不能后台回退使用旧数据。
5. 清理/失效旧缓存与会话中的当前菜谱引用，保留用户文字与历史结果；只开放同一发布的读取，完成冒烟后再开放写入。
6. 开放写入前失败可恢复整套发布与备份。开放写入后不得直接恢复旧全库丢掉新操作；需保留并迁移期间增量，选择已演练的兼容回退或向前修复。

制作阶段可以有独立候选库，正式查询始终只有一个活动发布；数据库备份不作为兜底查询接口。迁移完成后撤除旧字段和旧独立副本，不能无限期保留双轨。

## 11. 验收标准

| 验收项 | 必须满足的结果 |
| --- | --- |
| 单一标准 | 同一材料、数量、步骤、分类只有一个可写事实源；正式代码无旧字段缺值回退，所有入口来自同一发布 |
| 全量覆盖 | 原6,665个ID全部有明确去向；不遗失业务引用。合并/新增后的数量与处置清单对账一致 |
| 食材身份 | 玉米淀粉、小米椒、砂锅等已发现案例修正；复合调料展开无循环，别名与规格不误合并 |
| 标签 | 每道菜都有主分类、适用餐次、口味和方法定义；地域不强行伪填。所有代码有效，父子和组合不会重复加权 |
| 早餐可用 | 无额外限制时按既定餐型能连续搭配；候选充足不重复，硬限制导致不足时真实提示，不拿非早餐菜兜底 |
| 数量 | 1/2/3/4人、整件取整、关联油量、可选开关、范围选择均与步骤及采购一致；无循环依赖或无法换算的公共标准材料 |
| 能量 | 所有发布的公共配方材料均有唯一成分参数和换算；从材料独立复算与服务输出一致，无旧缺省0或漏算食材 |
| 复杂加工 | 油炸用油不等于整锅吃掉；腌料和弃汤按配方规则计算；生熟与干鲜转换不重复计算；加水不凭空增减整锅能量 |
| 时间 | 长时间煲汤/浸泡不会标成15分钟；并行步骤、批次和提前准备前提表达一致 |
| 推荐 | 收藏改变但随机种子相同结果不变；100个可互换组前100次不重复；本餐想吃和概率探索维持原验收；新子标签不会突破权重上限 |
| 账户与操作 | 失败、取消、重试、撤销、并发与切换账号不错误消耗轮换或反馈；旧会话不把上个版本结果当当前配方覆盖 |
| 用户记录 | 收藏、手填偏好、日历、实际用餐、采购勾选和手填支出保留；计划不变成实吃，新成分版本不改历史记录 |
| 全端一致 | 同一道菜、相同份数/选项在首页、助手、详情、购物和网页得到一致数量与营养；浏览筛选保持严格 |
| 发布与恢复 | 离线迁移、完整恢复、缓存失效、在途任务和开放写入后的增量处理通过；运行时内存与延迟有改造前后对照 |

上线门槛是这些用户结果与完整性要求，不是把全部标成某个审核状态。任一阻断项未通过，继续在制作区修复，不发布一部分新标准并让其余回退旧规则。

# 吃什么 · 独立网页版设计规格

## 2026-10-09 用户确认的数据源更正（优先于下文旧数据源描述）

用户明确：菜品数据来自线上数据库；个人记录不存线上。网页版通过安全的只读菜品 API 获取线上数据，浏览器不直连数据库、不包含数据库凭据。收藏、自定义菜单、日历计划、实际饮食和采购清单等个人对象仍仅保存在当前浏览器 IndexedDB。免登录、与小程序个人数据独立、永久不用 AI 的要求不变。

此前文中“静态菜库作为正式数据源”“不读取任何线上菜品 API”“完全只请求静态资源”的表述已被本更正取代。已经审校的本地来源菜只保留为来源与开发证据，不得作为正式数据源或静默离线兜底。在线菜品仍需遵守公开状态、完整性、来源、未知用量和保守忌口规则；个人输入不得传给菜品接口。

实现前核实仓库中的读取端点、鉴权、公开状态与字段。优先复用已有匿名只读公开目录；若必须新增公开端点，只能按最小字段、公开系统菜筛选、分页与边界测试设计，不能放宽全局认证、泄露私房菜/用户字段或更改生产安全配置。任何需启用的新公开访问应先取得具体授权。未部署测试代码与个人本地功能可继续推进。线上接口不可用时明确显示加载失败/重试，不能伪装成本地正式菜库成功。

## 1. 产品定位与边界

让现有域名提供一个真正可用的日常吃饭工具：不用登录，在手机和电脑浏览器里决定吃什么、查看做法、安排餐食、买食材、记录实际饮食。核心成功标准是用户能完成“选一餐 → 保存计划 → 整理采购 → 记录吃过 → 回看”，且清楚知道哪些数据只在当前浏览器。

### 明确采用

- 独立响应式 Web 工程、独立数据模型与发布产物；与微信小程序功能和数据完全独立。
- 浏览器内规则生成菜单、换一道、手动选菜；不需要服务端推荐。
- 个人数据存入 IndexedDB；JSON 文件由用户主动导出、导入。没有账号和云端同步。
- 菜品从获批的匿名只读公开API读取线上DB；个人数据不上传，不调用私有菜品接口。旧静态菜库只保留历史来源证据，不能进入生产包或作为失败兜底。
- 日历中的“计划”和“实际饮食记录”分别保存。饮食回顾仅使用实际记录。
- 简洁、可解释、可靠优先于菜数、视觉包装与自动化程度。

### 明确不做

不接入 AI 模型，现在和长期都不接入；不预留模型扩展路线。AI 能力只属于小程序。网页版也不提供登录、云同步、跨设备自动接续、语音识别、社区、医疗/营养判断、自动热量估计、支付、账号体系或后台管理。首版不做 PWA 安装、Service Worker 或离线可打开保证；已经加载的页面可以在断网时继续本地操作。

“浏览器缓存保存”在产品文案中准确表达为“保存在当前浏览器”：浏览器清理站点数据、隐私模式结束、设备故障都可能使记录丢失，持久化请求也不是永久保存承诺。

## 2. 信息结构与界面

### 导航

手机底部四个入口：**今天吃什么 / 菜谱 / 日历 / 我的**。桌面采用相同四个主入口的顶栏，内容居中，最大内容宽度约 1200px。采购清单从首页菜单、日历和“我的”进入；饮食回顾、收藏、自定义菜单、数据管理放在“我的”。首版不增加第五个底部导航入口。

- **今天吃什么**：人数、餐次、菜品组合、忌口摘要，主按钮“生成本餐菜单”；结果可换菜或手动编辑，突出唯一主动作“保存到日历”；“记录饮食”为次级操作，“生成采购清单”在菜单确认后作为次级入口展示，三者不并列高强调。不使用含糊的“保存”同时写两种记录。
- **菜谱**：名称/食材关键词搜索，分类筛选，收藏筛选；点卡片看食材原文、步骤、来源、已知限制。详情内可收藏、加入本餐。图片不是必需条件。
- **日历**：默认本周列表，支持月视图选日。一天按早餐、午餐、晚餐、加餐分区，计划与已记录并排或上下区分，不能仅靠颜色区分。
- **我的**：收藏、自定义菜单、饮食回顾、偏好设置、存储与备份、内容来源与说明。

所有按钮具备加载、禁用、失败状态。持久化操作等待事务完成后才显示“已保存”；失败时保持用户输入，提供重试与导出入口。空状态直接给下一步，不显示虚构示例数据充当用户记录。

### 视觉与可访问性

延续清爽绿色和日常食物感，采用浅底、深色正文、少量绿色主操作。参考现有产品气质，不复制小程序布局或绑定其 PR。手机单列、桌面双列；宽度 320px 起不出现整页横向滚动。主触控目标至少 44px，正文默认不少于 16px。键盘可完成主要流程，焦点可见，表单有标签，弹窗管理焦点，状态变更可被读屏读出；颜色不承担唯一含义。长菜名、长来源文本、200% 缩放不遮挡操作。

## 3. 用户路径与行为契约

### 首次访问

1. 进入首页即可使用，无注册与全屏引导。顶部一次性说明：“无需登录。记录保存在当前浏览器，建议定期导出备份。”
2. 默认 2 人、晚餐、2 道菜（一荤一素），人数可选 1–50；1–8 提供默认组合，超过 8 人先手动确认菜数。餐次由用户明确选择，不把当前时刻当成已吃时间。偏好不是必须填写。
3. 可设置不吃的食材与过敏相关排除项。提示：“筛选依据已知食材信息，无法保证过敏安全。请核对原料、调味料及交叉接触风险。”
4. 点击“生成本餐菜单”，查看结果、候选不足原因、原食材与来源；换一道或手选。
5. 点击“保存到日历”，确认日期/餐次，生成计划。或点击“记录饮食”，确认实际吃过的菜与日期后记录。两个动作独立，不隐式联动。
6. 保存首条记录后出现轻提示“可以在‘我的 → 数据管理’导出备份”，不弹强制引导。

### 回访与日常闭环

回访恢复人数、组合与忌口；首页显示今天的计划和上次未完成本餐草稿，不自动重新生成、不把计划算成实际。日历计划点“按此记录饮食”，打开可删改菜品的确认表单；确认后创建实际记录，保留计划用于对照。默认只记录确实吃过的菜，不预填吃了多少克。

已有同日同餐计划时，“保存到日历”明确询问替换该计划或取消，不静默覆盖。实际记录允许同日同餐多条，但从同一个计划再次记录时提示已有记录，并提供打开现有记录或明确新增；保存按钮防连点，避免重复提交。编辑计划不改变已有实际记录；编辑实际记录不改变计划。

### 收藏、自定义与草稿

收藏以菜谱身份去重；取消收藏不删除计划或历史。自定义菜单是可反复使用的菜品组合模板，不是已吃记录，也不是云端共享内容。用户还可建立简单自定义菜谱：名称必填，食材、数量、步骤可选；缺少食材审核信息的自定义菜仅可手选，不进入自动候选池。保存自定义菜不会自动标记为过敏安全。

本餐草稿在每次有效编辑后保存，显示“草稿已保存”或失败状态；放弃草稿需确认。模板、计划和实际记录保存菜谱快照，后续修改自定义菜不会改写历史。

删除个人记录需确认，可从本地回收站恢复 30 天；30 天后的项目在应用下次打开时清理，不承诺后台定时运行。清空全部数据单独列出影响范围并二次确认，提醒先导出。仅清理本应用的数据，不清除整个域名存储。

## 4. 本地菜单生成规则

### 输入与默认组合

人数 1–50；早餐、午餐、晚餐、加餐；人数影响建议组合与可计算用量，**不代表营养或饱腹保证**。午/晚餐默认：1 人一荤或豆制品菜加一素，2 人一荤一素，3–4 人两荤一素，5–6 人两荤两素，7–8 人三荤两素。超过 8 人不自动推定菜数，要求用户确认菜数和类型后才能生成；用量仍只依来源明确基准缩放，不臆测团餐份量。上述默认组合是本规格的推荐默认，不是已有用户要求。主食/汤可由用户另加各一项，菜数可调整至 1–20，仍受合格候选数量约束。早餐默认一主食一辅助菜，加餐默认一项；只有通过相应餐次审核的菜才能匹配。用户可手动调整组合，素食选择采用明确的素食组合，不用荤菜补足。

菜库类型固定为荤菜、素菜、主食、汤羹、早餐/加餐；单菜可以有多个审核后的适用标签，但一餐只能占一个槽位。豆制品是否适合素食必须看完整配料，不能由菜名推断。没有足够审校菜品时，相关类型不强行上线自动生成。

### 过滤、选择、解释

1. 只读取当前发布目录中具备完整准入标记的菜谱；过滤不适用餐次/类型。
2. 硬忌口优先于所有偏好。原料标准别名映射须经审核；匹配到排除项的候选直接排除。存在未识别原料、配方变体未拆清或复合调味料成分不明的菜，不进入带硬忌口条件的自动结果。即便通过筛选，也不作过敏安全保证。
3. 在剩余候选中无放回随机选择；同一来源菜的变体共享 familyId，同餐不重复选同一 familyId。
4. 收藏优先和最近 7 个本地日期实际吃过的菜降权，都是软偏好：收藏权重 2，普通 1，近期吃过再乘 0.5，最低仍可被选中。没有实际记录时不降权；计划不当作吃过。支持可复现随机种子供测试，不建立难解释的个性化评分。
5. 按槽位选择。候选不足返回部分结果和缺失槽位，例如“符合当前条件的素菜只有 1 道，还缺 1 道”；不给重复菜凑数，不自动放宽忌口。用户可改变组合、手选，或主动修改忌口后重新生成。

“换一道”仅替换指定槽位，保留其他菜和锁定项，应用同样硬过滤，并排除本餐其他 familyId 与当前菜。无替代项时说明原因，原菜不消失。重生成整餐也保留用户锁定菜；锁定菜若与新忌口冲突，先提示解除/移除，不能绕过检查。

手选被忌口匹配的菜显示警告，不冒充筛选通过；原料信息未知的菜显示未知项与来源。用户可以自行保留，系统不替用户作食用安全判断。所有生成均本地计算，无网络模型调用、无对话输入框。

### 份量与采购

来源明确给出基准人数时，按目标人数/基准人数缩放精确数量或明确区间；保留原始文本、基准人数和缩放系数。来源无基准人数时原量照录，并标“原文用量，未按人数换算”。“少许”“适量”“一个大碗”等不转成克数；调味料也不臆测用量。用户可手动填写采购量，记录为用户修改值。

采购清单来源于用户选定的计划或当前菜单，不能把实际记录再自动买一遍。相同标准食材、处理形态与可兼容单位才合并；重量 g/kg、体积 ml/L 可换算，同类计数单位可合并。质量与体积、个与克、生与熟、需区分的部位不换算或错误合并。区间相加保留上下界；未知量单列“待确认”，来源菜与原文始终可展开查看。明确量与未知量同时存在时显示“明确量合计 + 待确认项”，不能隐藏未知项。

清单可勾选已购买、调整数量和增加手动项。改变菜单不静默重算已有清单；显示“来源已变更”，用户确认重新生成新版本，原手工改动与已购状态不自动套用，先展示差异。所有清单只供采购整理，不给价格或营养承诺。

## 5. 技术结构与数据约定

推荐默认技术为 TypeScript、React、Vite 的静态单页应用；业务逻辑与框架分离，IndexedDB 通过轻量封装访问。网页是静态SPA，无需SSR或Node线上服务；浏览器不直连MySQL/Redis。菜品读取需要单独获批的最小公开API，个人记录仅IndexedDB。以独立工程目录管理，构建结果仅含静态文件。此处是设计选择，不代表已经创建工程或安装依赖。

模块只分为：界面与导航、菜单规则、菜库读取、采购聚合、个人数据仓储、导入导出与迁移。菜单规则和采购聚合接受纯数据、返回结果和原因，不直接访问界面或数据库。个人数据不会进入日志、URL、遥测或第三方分析。

### 标识、时间与版本

- 线上标准菜ID为eatwhat-db:<真实稳定DB id>，改显示名保留ID。现有schema无family/variant，family先回退同ID、variant=null，并在生成额外按归一名称去重；明确不等于来源已审family。真实contentVersion单独保留，未知来源URL/commit/license/审核日期及全目录revision为null。个人自定义记录仍用UUID。
- 日历日期为本地 YYYY-MM-DD，餐次为枚举；另存创建时 IANA 时区，时间戳为 UTC ISO 字符串。跨时区访问不重新解释已有日历日期。过去和当天可记实际饮食，未来日期只能存计划。
- schemaVersion表示本地结构版本，appVersion表示应用版本；真实菜品contentVersion与二者独立。线上schema没有全目录revision，catalogVersion保持null，不以局部菜品版本冒充目录快照版本。

### IndexedDB 数据对象

| 对象 | 关键字段与约束 |
| --- | --- |
| meta | schemaVersion、appVersion、全局 revision、最后成功写入时间、最后请求下载备份时间；所有写事务推进 revision |
| preferences | 人数、餐次/组合、硬忌口标准 ID 与原始输入、软偏好；未知忌口输入标记“未识别”，不能宣称已生效 |
| draft | 固定单条当前草稿，人数/组合、菜谱快照、锁定项、updatedAt、revision |
| customRecipes | UUID、名称、原料原文与可选结构量、步骤、创建/更新时间、revision；默认仅手选 |
| favorites | recipeId、收藏时间、最小显示快照；recipeId 唯一 |
| menuTemplates | UUID、名称、菜谱快照列表、默认人数、revision |
| plans | UUID、日期、餐次、人数、菜谱快照列表、revision；日期+餐次唯一 |
| actualMeals | UUID、日期、餐次、菜谱快照列表、可选 planId、备注、revision；不强迫填写份量 |
| shoppingLists | UUID、来源计划 ID/revision 或草稿摘要、条目、聚合依据、用户覆盖量、已购状态、revision |
| trash | 原对象类型、原 ID、完整数据、deletedAt、expiresAt；恢复时检查唯一键冲突 |

planId 和采购来源 ID 是可失效的追溯引用，源计划删除后保留快照并显示“来源已删除”，不级联删除；导入允许这类明确声明的失效引用，其他要求存在的引用必须完整。回收站恢复遇到同日同餐已有计划时要求另选日期/餐次或取消，不能覆盖现有计划。

每份菜谱快照包含：recipeId/familyId/variantId、菜名、当时分类、原食材文本、结构量及其可信状态、步骤、来源 URL/commit、许可标识、catalogVersion、基准人数（可为空）。历史渲染使用快照，不依赖最新版菜库仍保留该菜。来源变化不悄悄改历史；用户主动更新模板时另存新快照。收藏失去当前菜时仍显示最小快照和“当前菜库已不收录”，不加入自动生成。

### 事务、多标签页与升级

保存计划/实际记录、更新引用元数据和 revision 在同一读写事务中提交。实际记录创建与计划本身互不覆盖；防连点使用请求 UUID 并保持幂等。采购清单保存包含完整生成结果，不能出现一半条目。

多标签页通过 BroadcastChannel 通知刷新；不支持时在页面重新获得焦点时读 revision。编辑提交携带读取时对象 revision，在同一事务内核对，冲突提示“另一个页面已修改，请查看最新内容后重试”，保留本页草稿供复制，不使用静默最后写入覆盖。数据库升级通知其他页面关闭连接；若被旧页面阻塞，明确让用户关闭旧标签页再重试，不能清库。

结构升级使用 IndexedDB 版本升级事务，失败回滚；升级前需保留可导出的旧数据，破坏性迁移先要求导出并明确确认。旧应用遇到更新结构进入只读提示，不尝试降级写入。静态菜库更新只影响新选择；数据迁移与回滚兼容性是发布门槛。

## 6. 本地存储、备份与恢复

“数据管理”显示：当前 origin、数据库是否可读写、最后成功写入、估算占用/配额（浏览器支持时）、是否已获得持久化许可、最近一次请求下载备份的时间。下载操作不能证明用户确实保存了文件，文案不能写成“备份绝对成功”。

应用首次写入做存储能力检查；不可用时允许浏览菜谱和临时生成，但显著标注“本次内容不会保存”，禁用会伪装成成功的保存入口，同时允许导出当前可用内存数据。配额不足不清理历史凑空间，保留当前输入并提示导出、清理本应用可恢复数据或重试。持久化存储请求由用户点击触发；被拒仍可使用，但保留风险说明。不依赖可靠识别隐私模式。

### 导出

完整 JSON 包含 format=`eatwhat-web-backup`、schemaVersion、appVersion、catalogVersion、exportedAt、时区、所有个人对象和引用的菜谱快照；不必复制整个静态菜库、不包含程序代码、密钥或任何小程序数据。回收站也包含在备份中，并保留原过期时间。默认文件名带日期时间；输出 UTF-8，使用浏览器下载，不上传云端。提供“备份可能含饮食与忌口，请妥善保存”说明。首版不实现文件加密，用户可自行保管在可信存储中。

### 导入

首版只做**全量恢复替换**，不做复杂合并。流程为选择 JSON → 本地解析验证 → 展示来源时间、对象数量、替换影响 → 用户确认 → 原子恢复。导入不会访问文件中的 URL，不运行脚本，不自动修改静态菜库。

- 限制文件 20 MiB、个人主记录总数 20,000、单字符串 20,000 字符、JSON 嵌套 20 层；平时保存同样执行字段和总量上限，接近上限时提示管理记录，不能等到导出才阻止备份。已有超限或旧版本异常数据仍可完整原样导出用于留存，但明确标注无法由本版本直接恢复；不删除数据。
- 校验格式、受支持版本、字段类型、日期/餐次、唯一 ID、引用完整性、数量上下界、有限数值以及对象键；人数限定 1–50，单份原料结构数量为大于 0 且不超过 1,000,000 的有限数值，未知用量使用空值而非 0；拒绝原型污染键、NaN/Infinity、重复主键、错误关系和未知新版本。不接受 HTML、可执行字段或任意远程媒体地址。
- 旧版只走明确支持并经测试的纯数据迁移。无法识别的版本不“猜着读”；保留原库并给出可操作错误。
- 在内存中形成完整候选，列出当前数据将被替换。替换前提供当前数据导出；用户明确确认已备份或接受覆盖风险后才执行。
- 所有受影响对象存储在一个事务中写入；验证、迁移、配额或事务中断失败均保留原数据。导入与其他标签页写入冲突时拒绝提交并要求重试。
- 不自动把上传文件内的“已审校/安全”标志提升为正式菜库权限；备份中的未知来源菜仅作个人快照/手选，永不进入发布候选池。

常见恢复：误删从回收站恢复；更换设备用 JSON 搬家；浏览器已清理站点数据只能从外部备份恢复；无备份就不能承诺找回。换浏览器、HTTP/HTTPS、www/裸域、端口变化均可能形成不同数据空间。

## 7. 线上菜品准入与历史来源证据

当前Task1A只定义可注入PublicDish/provider，不创建或调用未获批端点。服务器必须单独按公开allowlist、系统非私房菜和严格发布条件筛选；发布标记不能提升VERIFIED。生成要求真实VERIFIED质量/步骤与已识别原名，未知标准ID/复合成分保持未知并保守排除。DB类型与餐次只是明确本地约定，无逐菜餐次证据；缺失family采用DB id回退并在生成做名称去重。正文纯文本，读取失败返回可重试错误，没有静态兜底。以下HowToCook静态方案和阅读状态仅作历史依据，已由线上数据源更正取代。

### 当前资料的真实状态

已有 HowToCook 来源整理覆盖 372 个菜谱主体，固定来源版本 a2d45c6984dff9ee941da0e7c452f7965965d962，保留原文、步骤、变体、来源与许可。后续 MySQL 适配结果为 305 个候选、67 个未映射待审，候选全部未发布；这不是“已有 305 道可正式上线的菜”。旧静态 main.html 的 27 个测试菜也不作为成熟库复用。

原静态设想从完整来源单独生成菜库；用户更正后不用于正式运行时。来源阅读证据不代表线上DB质量或公开覆盖。不会为了菜数把同一道菜的变体重复计数，来源主体数、可浏览数、可自动生成数分别统计。

### 首批准入

首版仅发布通过下列逐菜检查的子集，不预先许诺全量或固定菜数：

1. 名称、来源路径/commit、许可可追溯；正文来自真实来源，保留必要归属与许可文件。
2. 原料、步骤完整，无截断、跨菜串行或未决严重质量问题；变体的配料与步骤归属清晰。
3. 用量缺失仍保留原文并明确未知，不补造数字；基准人数只有源文明确时才填写。
4. 分类、餐次、主料与别名经过核对；进入自动池还需关键原料可识别，硬忌口模式额外应用第 4 节保守过滤。
5. 原文发现明显危险或无法核实的处理内容时暂停发布并人工复核，不用自动改写掩盖问题。
6. 发布清单记录每菜 reviewStatus、generationEligible、问题说明、审校日期及发布版本。构建验证不等于人工内容审核。

完整可浏览但不满足自动筛选要求的菜，可在详情标出“信息未齐，仅供手动选择”；存在步骤完整性、许可或严重内容问题的菜不公开，保留在整理资料中继续审核。首发每个开放生成的槽位类型至少有 3 个不同 familyId 的合格候选；达不到的类型暂不开放该自动选项，浏览不受此数量门槛影响。即便达标，具体忌口仍可能使候选不足，按规则解释。

### 图片与许可

默认首版不依赖菜图：使用统一的本地分类图形占位，菜名和做法优先。只对逐图确认来源、使用权且内容匹配的图片进行本地静态打包，保留来源说明；不批量热链外部图片，不把仓库总体许可当作所有外链图片当然可用的证据。外部图片未知时直接不用，不用生成图冒充菜谱成品。

HowToCook 快照附带 Unlicense 文件。发布需随包保留许可文本和来源版本；具体图片或引入的其他来源按其实际许可单独检查。此设计未完成逐菜/逐图公开准入审校。

## 8. 安全、隐私与发布边界

菜谱原文、用户输入、导入 JSON 一律按不可信纯文本渲染，不使用原始 HTML 注入；链接只允许经验证的 https 来源地址，外链安全打开；不执行导入内容，不读取其中任意资源。不让菜名、忌口、饮食记录出现在查询参数或服务器请求。首版无第三方统计、远程字体或广告 SDK。

部署目标仍是现有域名上的静态网页。已查看仓库 Nginx 配置：根目录静态站与 `/api/` 反向代理同时存在，并有 `/main`、`/health` 和证书验证路由。配置文件不能证明线上服务、证书、备案或实际路由现状。部署前必须另行取得许可并实测，不在本轮修改配置。

推荐选定 **https://chishenme.icu** 作为唯一网页 origin，www 最终重定向到它；实施前核实实际流量、证书和既有数据，发现已有 www 数据时先提供导出迁移说明。一个 origin 不代表与小程序共享数据库。网页只请求自身静态资源与单独获批的只读公开菜品API，不调用私有菜品、推荐服务或小程序登录接口；无个人数据发给API。

发布规格：

- 静态产物使用独立版本目录；HTML重新验证缓存，内容哈希JS/CSS可长缓存。生产包不携带静态菜谱来源；线上API分页全成功后一次提供候选，缺失/错误时显示加载失败重试。没有目录revision时不宣称全目录事务快照。
- SPA 回退仅处理网页路由，绝不能吞掉 `/api/`、证书验证、健康检查或真实缺失的静态资源；旧 `/main` 的保留或重定向需在部署核查时明确，默认先保留。
- 发布前备份现有静态版本和有效配置，验证配置、静态路由与 API 非回归，再切换静态目录；失败可切回上一版本。代码回滚不清空用户数据，必须符合数据库版本兼容规则。
- Web 与小程序服务同域时，静态路径隔离不是安全隔离。任何同源脚本都可能触及同源浏览器数据；部署检查应清点旧页面和脚本，审查 CSP、响应头与依赖。不能为了新站全域覆盖 API 的 CORS、认证或安全策略。
- HTTPS、CSP 与其他头部的实际调整，以及域名重定向，均属之后明确授权的发布工作。独立工程不包含生产密钥，不携带旧库测试账号。

## 9. 验收标准

以下是将来实施后的验收要求，当前均未以运行测试验证。

### 自动化

- 规则测试：硬忌口零自动放宽；未知原料保守处理；餐次/槽位匹配；无重复 family；换一道保持其他项；锁定冲突；空库与不足解释；固定 seed 可复现。
- 数量测试：精确值/区间缩放；无基准人数不缩放；kg/g 与 L/ml 合并；个/克不合并；未知项不丢失；手改值与来源差异保留。
- 数据测试：计划与实际互不改写；回顾只计实际；历史快照不被菜库更新覆盖；连点幂等；事务故障无半写；唯一日期餐次计划约束。
- 多页/版本测试：冲突不覆盖；数据库升级被阻塞可恢复；迁移失败回滚；新结构旧程序不写；导入过程中其他标签写入冲突。
- 备份测试：空库、完整库、回收站与自定义菜导出再导入一致；错误版本、超限、损坏、重复 ID、危险键、恶意 HTML/URL 拒绝或安全纯文本处理；恢复失败原库完整。
- 内容门禁：逐条来源/许可/审校状态；快照资源摘要；自动池过滤；变体去重；不将 unpublished 候选直接发布。
- 网络断言：核心动作没有小程序 API、模型或第三方追踪请求；部署烟测确认 API/健康/证书路径未被 SPA 接管。

### 真实浏览器与人工验收

在实施时最新稳定 Chrome、Edge、Firefox、macOS Safari、iOS Safari 与 Android Chrome 上记录具体版本和结果。至少覆盖 320/390/768/1440px、触控、键盘、读屏基本路径、200% 缩放。

1. 首次打开至生成、看做法、保存计划、重载仍在；用户始终能分清计划和实际。
2. 按计划记录后回顾出现记录；改计划不改变历史，删除/恢复行为清楚。
3. 实际饮食回顾支持最近 7/30 天、菜品出现次数、已记录餐次及当时分类。一次实际记录中的同一道菜计一次出现；无记录日标“未记录”，不能称为没吃。分类只表示记录条目构成，不评价健康或营养是否达标。
4. 采购清单包含可展开来源、已知合计与未知待确认；菜单变更不会抹掉用户修改。
5. 刷新/关闭再开、多标签同时修改、存储被拒、模拟配额不足、断网、菜库加载失败均无假成功或静默丢失。
6. 从浏览器 A 导出到浏览器 B 导入完成搬家；取消、错误文件及事务失败不影响 B 原有记录；确认下载文案没有过度保证。
7. 全新 origin 首次访问确实显示空数据；不会因无登录误导用户以为其他设备记录同步存在。
8. 在授权的预发布环境验证静态版本切换与回滚，确认既有 API 无回归，再讨论上线。

上线硬门槛：核心闭环可用、保存/导入无数据破坏、忌口不被自动放宽、内容准入完成、未混入私有 API/模型、关键浏览器通过、发布与回滚验证有记录。未满足任一项不得以“已可用正式站”交付。

# 后台弱网请求可靠性设计

## 目标

优化移动端后台在慢网络、重复搜索、下拉刷新和快速切换用户时的响应与反馈。任何新操作都必须立即显示状态，旧请求不能覆盖新请求，刷新失败时不能把已有内容清空或让页面停留在加载状态。

## 范围

- 优化管理员用户列表的首次加载、搜索、刷新和加载更多。
- 优化用户详情的首次加载和后台刷新。
- 规范后端超大页码，避免分页偏移溢出。
- 不改变现有 API 地址、管理员鉴权、页面导航和菜品表单字段。

## 用户体验状态

### 首次加载

- 页面尚无可显示数据时使用骨架状态。
- 请求无论成功或失败都必须结束加载状态。
- 首次失败显示明确错误和重新加载按钮。

### 搜索与刷新

- 已有列表时继续展示原内容，并显示“正在更新”，不切换到空白骨架。
- 新搜索可以覆盖仍在进行的旧搜索，不因 `loading` 状态被丢弃。
- 只有最后一次请求可以更新列表、错误提示和加载状态。
- 刷新失败时保留原列表，并显示“更新失败，仍显示上次结果”。

### 加载更多

- 加载更多保持串行，避免重复请求同一页。
- 搜索或刷新可以中止加载更多的状态更新；迟到的分页响应不能拼接到新搜索结果。
- 加载更多失败时保留已有列表，并提供非阻塞提示。

### 用户详情

- 首次进入详情时显示加载状态。
- 保存、删除或下拉刷新后的详情重载继续显示现有用户和菜品，并显示“正在刷新”。
- 详情请求采用最后一次生效规则，迟到响应不能覆盖当前用户。
- 刷新失败时保留当前详情并给出提示；首次加载失败仍显示重试入口。

## 实现结构

- `pages/admin/admin.js` 为列表和详情分别维护单调递增的请求版本号。
- 每个异步请求在写入数据、错误和 `finally` 状态前检查自己是否仍为最新版本。
- 新增 `listReady`、`refreshing`、`listNotice`、`detailReady`、`detailRefreshing` 和 `detailNotice`，区分首次加载与已有内容刷新。
- `pages/admin/admin.wxml` 在保留内容的同时展示更新提示，不用全屏遮挡。
- `AdminUserService` 在得到总数后把页码限制到最后一个有效页，再计算 `offset`。

## 错误边界

- 旧请求成功、失败或结束都不得改变最新请求的界面状态。
- 页面退出列表或详情时递增相应版本号，使未完成请求失效。
- 空数据是有效结果，与加载中、请求失败分开显示。
- 后端总数为 0 时有效页固定为 1；每页仍限制为 1-50。

## 验证

- Node 测试覆盖搜索覆盖旧请求、已有内容刷新、刷新失败保留内容、加载更多被搜索取代、详情响应乱序。
- Java 测试覆盖超大页码规范到末页及正确 `offset`。
- 运行前端全量测试、后端全量测试、仓库验证脚本和 `git diff --check`。

- 仅明确修改常用人数/长期偏好；临时要求不反写。首版采集基础曝光/接受/业务反馈，不自动学习、不新增推断记忆。
- 回顾只统计明确实际，不给无依据热量。已有食材用于推荐和采购核对，不扣库存。
- 草稿 30 天、事件 90 天；正式计划/实际/回执保留。版本/归属/幂等及账号回调隔离是跨设备契约。
- 家庭协作、营养核算、库存账本、跨餐复用优化属于后续版本。原文中自动学习、橙色品牌或其他超出范围建议不构成本版要求。
- 近期菜品仅取明确的实际用餐记录；收藏和近期作为软排序，不放宽忌口/保留约束。未知原始基础人数的采购量始终提示核对，改名称/单位不视为确认数量。
- 历史实际快照可在菜库改名/删除后继续编辑，按服务端原条目索引引用；手动修改不覆盖原计划来源，也不继续标记为按计划吃了。实际修改事件不增加当前完成餐次数。
- 当前 V4 开关默认关闭；本轮按用户要求只做源码/VM、生成和隔离 MySQL/HTTP 检查，不执行微信开发者工具或原生编译。历史编译证据另行登记，真实原生交互及 iOS/Android 全量验收未完成，不声称已发布。

# Eat What V4 Product Experience Strategy

> 「今天我们吃什么」V4 产品体验、用户闭环与个性化演进方案\
> 本文用于让 Work Agent / Codex / 产品 /
> 前后端开发共同理解：**这个产品为什么这样设计、用户最终应该获得什么体验、各功能之间如何形成闭环，以及系统如何随着使用越来越懂用户。**

------------------------------------------------------------------------

# 0. 文档结论

V4 及后续版本的产品建设围绕两个最高目标展开：

## Goal A --- 完整闭环

> **用户打开小程序后，不只是获得"吃什么"的答案，而是能够从决策一路走到执行。**

核心链路：

``` text
不知道吃什么
    ↓
系统理解当前场景
    ↓
给出一套可执行方案
    ↓
用户接受 / 调整
    ↓
确认这一餐
    ↓
查看做法
    ↓
检查已有食材
    ↓
生成购物清单
    ↓
加入计划 / 日历
    ↓
完成这一餐
    ↓
沉淀历史与反馈
```

产品不应该停留在"推荐一道菜"。

------------------------------------------------------------------------

## Goal B --- 越用越快，越用越懂

> **第一次使用需要用户告诉系统一些信息；长期使用后，系统应该逐渐减少用户输入，并主动补全大部分上下文。**

演进目标：

``` text
第一次
用户告诉系统：
“2个人，30分钟，清淡一点”

↓

使用一段时间
系统已经知道：
通常晚餐2人
偏清淡
工作日晚餐希望30分钟左右

↓

长期使用
用户只需要：
“帮我安排今晚”

甚至：

打开小程序
↓
系统已经准备好建议
↓
用户只需要确认 / 微调
```

产品长期价值不是"拥有 AI 聊天框"，而是：

> **让用户解决吃饭问题所需要的操作越来越少。**

------------------------------------------------------------------------

# 1. 产品定位

旧阶段：

> 随机选菜 / 菜单生成器。

中间阶段：

> 菜谱推荐 + 条件筛选 + AI 助手。

V4 之后：

# 家庭吃饭决策与计划助手

内部 Product Statement：

> **帮助用户从"今天吃什么"，一路解决到"怎么做、需要买什么、接下来怎么安排"，并在长期使用中逐渐理解用户与家庭的饮食习惯。**

对外不必强调 Agent、Tool Calling、Memory 等技术词。

用户感受到的应该是：

> "它知道我平时怎么吃，而且真的能帮我把这顿饭安排好。"

------------------------------------------------------------------------

# 2. Product North Star

整个产品必须持续优化：

# Less Thinking, Less Input, More Done

中文：

> **少想一点，少填一点，多完成一点。**

任何新功能、页面、按钮、Agent 能力，都应回答三个问题：

1.  它是否减少用户做决定的成本？
2.  它是否减少用户执行这一餐的成本？
3.  它是否帮助系统下一次更懂用户？

如果三个答案都是否，应谨慎加入产品主路径。

------------------------------------------------------------------------

# 3. 用户真正要完成的任务

用户不是来"使用推荐算法"的。

用户的 Job To Be Done 是：

> **我现在需要解决一顿饭，但我不想花很多时间决定吃什么、怎么买、怎么安排。**

典型情况：

``` text
下班了，不知道吃什么
冰箱有一些东西，不知道能做什么
两个人吃，不想太复杂
今天想清淡一点
最近总吃鸡肉，想换换
周末想安排一家人的饭
想提前安排未来三天
已经决定吃什么，但不知道缺什么食材
```

因此首页不应该首先暴露系统参数，而应该首先帮助用户完成任务。

------------------------------------------------------------------------

# 4. 产品价值层级

所有功能按价值分成三层。

## Layer 1 --- Core Decision

决定用户为什么打开产品：

``` text
今天吃什么
理解当前需求
生成一餐方案
换一道 / 换一套
调整方案
确认这一餐
```

## Layer 2 --- Execution Loop

让推荐结果真正变得有用：

``` text
菜谱
做法
份量
食材
购物清单
日历 / 计划
收藏
历史
```

## Layer 3 --- Long-term Intelligence

决定用户为什么长期留下：

``` text
饮食偏好
行为学习
推荐反馈
营养
Pantry
多日计划
家庭成员
重复控制
食材复用
个性化推荐
```

原则：

> Layer 3 不应该破坏 Layer 1 的简单性。

系统越聪明，首页反而应该越简单。

------------------------------------------------------------------------

# 5. 核心产品闭环

完整闭环定义为：

``` text
Context
↓
Recommend
↓
Adjust
↓
Confirm
↓
Execute
↓
Record
↓
Learn
↓
Next Recommendation
```

展开：

``` text
当前场景
  ↓
今天 / 晚餐 / 2人 / 30分钟
  ↓
生成方案
  ↓
用户：
接受 / 换菜 / 调整
  ↓
确认
  ↓
菜谱 + 食材 + 购物 + 计划
  ↓
实际执行
  ↓
记录结果
  ↓
更新近期历史 / 行为信号
  ↓
下一次推荐更准确
```

这是 V4 以后最重要的 Product Loop。

------------------------------------------------------------------------

# 6. 信息架构

目标一级导航：

``` text
今天
菜谱
计划
我的
```

## 今天

定位：

> 当前这一餐的控制中心。

包含：

-   MealContext；
-   Agent 入口；
-   当前推荐；
-   当前确认状态；
-   当前餐后续动作；
-   最近任务。

## 菜谱

定位：

> 内容库与主动探索。

包含：

-   搜索；
-   分类；
-   收藏；
-   自定义菜；
-   菜品详情；
-   做法；
-   食材；
-   营养。

## 计划

定位：

> 从"这一餐"扩展到"未来几餐"。

包含：

-   日历；
-   多日计划；
-   已安排餐次；
-   购物清单；
-   未来 Pantry；
-   批量安排。

## 我的

定位：

> 用户与系统之间长期关系的管理中心。

包含：

-   饮食偏好；
-   收藏；
-   自定义菜；
-   历史；
-   统计；
-   家庭成员（未来）；
-   设置。

------------------------------------------------------------------------

# 7. 首页设计原则

首页不是参数表单。

首页是：

# Current Meal Workspace

核心结构：

``` text
问候 / 当前餐次

MealContext
今晚 · 2人 · 30分钟以内 >

自然语言输入
“告诉我你想怎么吃”

Primary Action
[ 帮我安排 ]

Quick Chips
30分钟 / 清淡 / 冰箱食材 / 简单吃
```

必须支持 Zero-input：

``` text
打开
↓
直接点“帮我安排”
```

系统使用：

-   时间；
-   当前餐次；
-   用户默认人数；
-   长期偏好；
-   最近历史；
-   当前上下文；

自动补全。

------------------------------------------------------------------------

# 8. Progressive Disclosure

所有复杂条件采用渐进式披露。

## Level 0 --- Zero Config

``` text
[ 帮我安排 ]
```

## Level 1 --- Quick Context

``` text
2人
30分钟
清淡
冰箱食材
```

## Level 2 --- Context Sheet

用户主动展开：

``` text
餐次
人数
时间
口味
已有食材
忌口
份量
特殊要求
```

## Level 3 --- Advanced

只有少量高级用户需要：

``` text
荤菜数量
素菜数量
汤数量
主食
甜品
菜系
烹饪方式
其他限制
```

原则：

> 系统参数不应该等于用户界面。

------------------------------------------------------------------------

# 9. 推荐结果设计

默认不再让用户同时比较三个同权重方案。

优先：

# One Primary Recommendation

结构：

``` text
今晚建议

香菇鸡片
番茄炒蛋
清炒西兰花

约30分钟 · 适合2人

为什么推荐
✓ 符合今天清淡要求
✓ 最近没有重复
✓ 部分食材家里已有

[ 就吃这个 ]

↻ 换一套      调整一下
```

其他方案作为：

``` text
看看其他选择 >
```

用户的任务是：

> 接受或调整。

不是重新做一次选择题。

------------------------------------------------------------------------

# 10. Recommendation Reason

推荐理由必须尽可能来自真实数据。

允许：

``` text
最近7天没有吃过
符合你明确设置的清淡偏好
使用了冰箱里的番茄
预计30分钟内完成
你过去多次收藏类似菜品
```

禁止让 LLM 无依据编造：

``` text
这是你最喜欢的口味
你最近需要补充蛋白质
你今天应该吃清淡一点
```

除非系统确实拥有可靠数据支持。

原则：

> 推荐理由既是解释，也是信任机制。

------------------------------------------------------------------------

# 11. 调整体验

用户不应该通过重新填写整个表单修改方案。

支持自然语言：

``` text
鸡肉换成鱼
不要汤
再简单一点
不要辣
控制在20分钟
家里没有西兰花
```

同时支持结构化 Action：

``` text
换一道
换一套
调整
修改人数
修改时间
```

确定性操作优先结构化事件，不走 LLM。

例如：

``` text
REPLACE_DISH
CHANGE_PEOPLE
CHANGE_DATE
CONFIRM_PLAN
ADD_TO_SHOPPING
SAVE_TO_CALENDAR
FAVORITE_DISH
```

原则：

> 能确定的，不交给模型。

------------------------------------------------------------------------

# 12. "换一道"是产品信号

换菜不是单纯 UI 操作。

它是推荐系统最重要的隐式反馈之一。

建议在部分场景轻量询问原因：

``` text
最近吃过
不喜欢
太油
太辣
太麻烦
没有食材
只是想换
```

不能每次强制询问。

系统记录：

``` text
recommended_dish
replacement_dish
reason
meal_context
timestamp
accepted_after_replace
```

用于后续：

-   推荐排序；
-   行为偏好；
-   重复控制；
-   模型评估。

------------------------------------------------------------------------

# 13. 用户反馈信号体系

建议按强弱建立统一语义。

## Strong Positive

``` text
明确说喜欢
多次主动选择
加入收藏
多次重复做
明确设置为偏好
```

## Medium Positive

``` text
推荐后直接接受
加入计划
查看完整做法
生成购物清单
```

## Weak / Contextual

``` text
点击详情
停留
查看替代方案
```

## Negative

``` text
换掉推荐菜
明确“不喜欢”
明确“最近吃过”
明确“太辣”
明确“太麻烦”
```

不同信号不能等价。

例如：

> "推荐后接受"不能自动推断为"长期最喜欢"。

------------------------------------------------------------------------

# 14. UserFoodProfile

长期个性化至少分：

``` text
Explicit
用户明确表达

Inferred
系统从行为推断
```

示例：

``` json
{
  "explicit": {
    "excluded_ingredients": ["香菜"],
    "taste_preferences": ["清淡"]
  },
  "inferred": {
    "prefers_quick_weekday_dinners": {
      "confidence": 0.78
    },
    "low_acceptance_for_spicy_dishes": {
      "confidence": 0.66
    }
  }
}
```

Explicit 优先级高于 Inferred。

------------------------------------------------------------------------

# 15. 临时偏好与长期偏好

这是 Agent 必须严格区分的概念。

用户说：

``` text
“今天不想吃辣”
```

应写入：

``` text
MealContext
temporary preference
```

不能直接写：

``` text
UserFoodProfile
never spicy
```

用户说：

``` text
“我平时不吃辣”
```

才是长期记忆候选。

用户说：

``` text
“我朋友今天不吃牛肉”
```

不能写成：

``` text
user excludes beef
```

Memory 必须识别：

-   subject；
-   scope；
-   source；
-   confidence；
-   expiration。

------------------------------------------------------------------------

# 16. Memory 原则

长期记忆不由 LLM 任意写入。

流程：

``` text
LLM / Rule
↓
MemoryCandidate
↓
MemoryManager
↓
Validate
↓
Conflict Check
↓
Store / Ask Confirmation / Reject
```

明确长期陈述可以高置信记录。

行为推断需要：

-   多次信号；
-   置信度；
-   可被新行为修正。

原则：

> 系统应该越来越懂用户，但不能越来越武断。

------------------------------------------------------------------------

# 17. 用户生命周期

## Stage 1 --- New User

系统几乎不知道用户。

目标：

> 尽快完成第一顿，而不是要求填写完整档案。

体验：

``` text
今天晚饭怎么安排？

[ 帮我安排 ]

也可以告诉我：
“2个人，简单一点”
```

第一顿之后再渐进学习。

## Stage 2 --- Familiar User

系统已经知道：

``` text
常用人数
常见餐次
部分偏好
近期历史
```

体验：

``` text
今晚还是2人？

[ 帮我安排 ]
```

## Stage 3 --- Learned User

系统拥有可靠模式：

``` text
工作日晚餐通常2人
偏清淡
通常希望30分钟左右
最近鸡肉较多
```

体验：

``` text
今晚给你换个口味：

清蒸鱼
番茄炒蛋
蒜蓉生菜

约28分钟

[ 就吃这个 ]
```

长期目标：

> 用户输入减少，确认比例提高。

------------------------------------------------------------------------

# 18. "越来越方便"如何量化

不能只写成愿景。

系统应该逐步降低：

``` text
Time To First Plan
完成第一套可用方案所需时间

Inputs Per Meal
每次安排所需用户输入数量

Adjustments Per Accepted Meal
接受前平均调整次数

Steps To Execution
从首页到购物 / 做法所需步骤
```

长期用户理想趋势：

``` text
Inputs ↓
Clicks ↓
Decision Time ↓
Replacement Count ↓

Acceptance ↑
Completion ↑
Return Usage ↑
```

------------------------------------------------------------------------

# 19. "越来越懂"如何量化

不要用"聊天次数"。

重点：

``` text
Recommendation Acceptance Rate
推荐接受率

First Recommendation Acceptance
第一套方案直接接受率

Average Replacement Count
平均换菜次数

Preference Prediction Accuracy
偏好预测命中情况

Repeated Rejection Rate
同类错误重复发生率

Context Auto-fill Success
自动补全后无需修改的比例
```

真正"懂用户"的系统：

> 不只是记住更多东西，而是更少犯相同的推荐错误。

------------------------------------------------------------------------

# 20. 收藏功能重新定义

收藏不是孤立的"书签"。

它同时是：

``` text
内容保存
+
未来推荐信号
```

但收藏也不能简单等价于：

> 每次都推荐。

系统需要结合：

-   最近是否吃过；
-   当前场景；
-   食材；
-   时间；
-   口味；
-   多样性。

收藏应该提高相关性，而不是造成重复。

------------------------------------------------------------------------

# 21. 历史记录的产品价值

历史不是为了做一个"过去吃了什么"的页面。

主要用于：

``` text
避免重复
识别偏好
生成统计
支持复盘
支持未来计划
```

示例：

``` text
最近7天：
鸡肉 3 次
鱼 0 次
汤 4 次
```

系统可以据此提高多样性。

但不应在没有营养规则支持时自动得出医疗或健康结论。

------------------------------------------------------------------------

# 22. 日历从记录升级为计划

旧：

> 记录哪天吃了什么。

未来：

> 管理未来几餐。

例如：

``` text
周一 ✓
周二 ✓
周三 未安排
周四 未安排
周五 未安排

[ 帮我安排剩下三天 ]
```

计划页应同时支持：

``` text
过去
今天
未来
```

但产品重点逐渐向未来移动。

------------------------------------------------------------------------

# 23. Shopping Loop

购物清单是产品从"建议"进入"执行"的关键。

完整流程：

``` text
确认今晚菜单
↓
聚合所有菜品食材
↓
按人数缩放
↓
合并同类食材
↓
扣除已有库存（未来）
↓
生成缺失项
↓
用户确认
↓
进入购物清单
↓
采购完成
```

LLM 不负责确定性数量计算。

数量、单位换算、合并规则由 Tool / Business Logic 完成。

------------------------------------------------------------------------

# 24. Pantry 的未来定位

Pantry 不是独立炫技功能。

它服务两个目标：

``` text
减少浪费
减少购买
提高推荐可执行性
```

未来：

``` text
家里有什么
↓
优先消耗临期 / 已有食材
↓
生成方案
↓
计算缺失项
↓
购物
↓
做饭
↓
更新库存
```

Pantry 应在购物闭环成熟后再重点建设。

------------------------------------------------------------------------

# 25. 多日计划

多日计划不是把单日推荐复制 N 次。

需要优化：

``` text
口味多样性
食材复用
采购数量
烹饪复杂度
工作日 / 周末
近期重复
用户偏好
```

示例：

``` text
买一把香菜
→ 多餐合理复用

买500g鸡胸
→ 分配到两餐

周一工作日晚餐
→ 快手

周末
→ 允许复杂菜
```

因此未来需要：

``` text
build_period_plan
optimize_ingredient_reuse
```

等专门 Tool。

------------------------------------------------------------------------

# 26. 家庭成员

未来产品应从：

``` text
User Preference
```

扩展到：

``` text
Household Preference
```

例如：

``` text
本人：少辣
伴侣：不吃香菜
孩子：不吃辣
今晚朋友：不吃牛肉
```

需要区分：

-   长期家庭成员；
-   临时用餐者；
-   当前餐人数；
-   每个人的忌口；
-   冲突解决。

不能把临时客人的偏好永久写入用户 Profile。

------------------------------------------------------------------------

# 27. Nutrition 的位置

营养不是单独做一个"数据页面"就结束。

应嵌入用户决策点：

``` text
推荐方案
→ 每人 kcal / 蛋白质 / 蔬菜等摘要

周计划
→ 一周趋势

菜品详情
→ 单菜营养
```

详细统计可以存在，但营养最有价值的位置是：

> 用户正在决定吃什么的时候。

所有确定性营养计算交给 Tool / 数据库，不让 LLM 自行计算。

------------------------------------------------------------------------

# 28. 文案体系

产品语言应该：

> 像一个懂吃饭的助手，而不是后台管理系统。

推荐：

``` text
帮我安排
就吃这个
换一道
换一套
调整一下
今晚 · 2人
看看其他选择
加入购物清单
安排到周五晚餐
```

减少：

``` text
执行推荐
应用筛选条件
提交配置
生成结果
选择方案
```

但危险操作仍需明确：

``` text
删除这道自定义菜？
```

避免过度卖萌：

``` text
真的舍得和它说再见吗～
```

------------------------------------------------------------------------

# 29. UI 与行为数据

UI 不只是展示层。

它也是行为信号采集层。

例如：

``` text
收藏
换一道
换一套
确认
取消
调整人数
改变时间
生成购物
保存计划
实际再次选择
```

都可以成为推荐系统数据。

因此设计新 Action 时，应同时定义：

``` text
UI Behavior
+
Domain Event
+
Analytics Event
```

例如：

``` text
UI:
换一道

Domain:
REPLACE_DISH

Analytics:
meal_plan_dish_replaced
```

------------------------------------------------------------------------

# 30. Analytics Event 建议

核心事件：

``` text
home_opened
meal_arrange_started
meal_context_changed
meal_plan_generated
meal_plan_accepted
meal_plan_regenerated
meal_plan_adjusted
meal_plan_dish_replaced
replacement_reason_selected
dish_favorited
recipe_opened
shopping_preview_generated
shopping_list_confirmed
calendar_plan_saved
meal_completed
preference_explicitly_set
```

每个事件应尽量带：

``` text
session_id
user_scope
meal_type
people
plan_id
plan_version
dish_id
source
timestamp
```

避免直接把自由文本和敏感内容全部塞进 Analytics。

------------------------------------------------------------------------

# 31. 核心漏斗

产品经理应长期关注：

``` text
Home Open
↓
Arrange Started
↓
Plan Generated
↓
Plan Accepted
↓
Execution Action
↓
Meal Completed / Saved
```

关键指标：

``` text
Plan Generation Success Rate
Recommendation Acceptance Rate
First Recommendation Acceptance Rate
Average Replacement Count
Time To Accepted Plan
Shopping Conversion
Calendar Save Rate
7-Day Retention
30-Day Retention
```

Agent 的 KPI 不是：

> 平均对话轮数越高越好。

很多时候恰恰相反：

> 如果一句话就能解决，就不要聊五轮。

------------------------------------------------------------------------

# 32. 页面视觉与产品逻辑的关系

视觉改造必须服务产品目标。

例如：

``` text
Primary Button
```

不是"更漂亮的按钮"，而是告诉用户：

> 现在最应该做什么。

Icon 不是装饰，而是：

> 降低扫描成本。

Card 不是为了圆角，而是：

> 把同一决策单元组织在一起。

Empty State 不是插画展示，而是：

> 在没有数据时继续引导用户完成任务。

Motion 不是炫技，而是：

> 告诉用户操作已经生效。

------------------------------------------------------------------------

# 33. 状态驱动 UI

未来页面应该根据 Meal State 改变操作，而不是固定显示所有按钮。

示例：

## State A --- 尚未安排

``` text
[ 帮我安排 ]
```

## State B --- 已生成未确认

``` text
[ 就吃这个 ]

换一套
调整
```

## State C --- 已确认

``` text
[ 查看做法 ]

生成购物清单
保存到计划
```

## State D --- 已保存计划

``` text
[ 查看做法 ]

查看购物清单
```

原则：

> 当前状态只展示最可能的下一步。

------------------------------------------------------------------------

# 34. 不要让 Agent 取代所有 UI

未来不是"所有功能都通过聊天"。

正确结构：

``` text
自然语言
+
Structured Cards
+
Deterministic Actions
```

适合自然语言：

``` text
今天想清淡一点
鸡肉换成鱼
再简单一点
我朋友不吃牛肉
```

适合 UI：

``` text
收藏
确认
删除
改变人数
选择日期
购物勾选
查看详情
```

原则：

> 语言负责表达意图，UI 负责高效执行。

------------------------------------------------------------------------

# 35. Agent 主动性的边界

系统可以主动：

``` text
预填常用人数
默认当前餐次
提醒最近重复
给出推荐理由
提出一套方案
建议补充缺失信息
```

系统不应未经确认：

``` text
直接创建购物项
直接删除日历
永久修改偏好
自动购买
将临时偏好永久化
```

Write Action：

``` text
Model Proposes
↓
Preview
↓
User Confirms
↓
Trusted Business Logic Executes
```

------------------------------------------------------------------------

# 36. 失败体验

完整闭环必须包括失败路径。

例如推荐服务失败：

``` text
Agent 推荐暂时不可用
↓
自动退回传统推荐
↓
用户仍能完成今天吃什么
```

购物生成失败：

``` text
保留已确认菜单
↓
允许稍后重试购物清单
```

保存日历失败：

``` text
不丢失当前 Plan
↓
提示重试
```

原则：

> 一个辅助功能失败，不应该让整顿饭的决策结果丢失。

------------------------------------------------------------------------

# 37. 传统推荐系统的未来角色

旧机械 / 随机推荐不删除。

它变成：

``` text
Candidate Generator
Fallback
Quick Random Tool
Diversity Source
```

Agent 可以调用它，但它不再是产品主入口。

这样保留已有资产，同时降低对外部 LLM 的单点依赖。

------------------------------------------------------------------------

# 38. 性能体验

用户感受到的"聪明"也来自速度。

目标：

``` text
确定性 UI 操作
→ 立即反馈

需要 Tool 的操作
→ 先显示状态

Agent 多轮执行
→ 显示明确进度

长任务
→ Task 化
```

不要让所有按钮点击后都等待 LLM。

------------------------------------------------------------------------

# 39. 数据与隐私原则

个性化越强，越需要控制数据边界。

原则：

-   只保存对产品有明确价值的数据；
-   区分当前会话、近期历史和长期偏好；
-   长期推断保留 source / confidence；
-   用户明确设置优先于推断；
-   不从单次行为得出强长期结论；
-   提供修改偏好的入口；
-   不让模型凭空补充用户事实。

# 41. V4 验收场景

以下场景必须端到端可完成。

## Scenario 1 --- Zero Input

``` text
打开小程序
↓
帮我安排
↓
获得今晚方案
↓
确认
↓
查看做法
```

## Scenario 2 --- Natural Language

``` text
“2个人，30分钟，清淡一点”
↓
生成
↓
换一道
↓
确认
↓
生成购物清单
```

## Scenario 3 --- Existing Ingredients

``` text
“家里有番茄和鸡蛋”
↓
优先利用
↓
生成方案
↓
显示还缺什么
```

## Scenario 4 --- Preference Learning


``` text

↓

↓

```

# 42. 产品决策 Checklist

新增任何功能前，Agent / PM 必须回答：

``` text
1. 用户正在解决什么吃饭问题？
2. 它属于 Core / Execution / Long-term 哪一层？
3. 它是否应该进入主路径？
4. 它是否减少用户操作？
5. 它是否形成新的闭环？
6. 它是否产生有价值的行为信号？
7. 是否有更简单的 UI 可以完成？
8. 是否真的需要 LLM？
9. 失败时用户还能继续完成任务吗？
10. 它会不会让首页重新变复杂？
```

# 45. Work Agent / Codex 强约束

实施时必须遵守：

1.  不把"增加功能数量"当作产品进步。
2.  不重新把大量参数暴露到首页。
3.  不创建与"今天"平行的第二套 AI 主入口。
4.  不让聊天替代所有确定性 UI。
5.  不让 LLM 计算可由程序确定的数字。
6.  不让 LLM 无限制写长期 Memory。
7.  不将临时偏好自动升级为长期偏好。
8.  不将第三方/朋友偏好写成用户本人偏好。
9.  Write Action 必须遵守确认与可信执行链路。
10. 新功能必须考虑 Default / Loading / Empty / Error / Success。
11. 新 Action 必须考虑是否需要 Domain Event / Analytics Event。
12. 产品状态改变后，UI 应展示新的"下一步"，而不是永久堆所有按钮。
13. Agent 服务失败时保留传统推荐 fallback。
14. 不因为未来能力规划而让 V4 首屏变复杂。
15. 所有实现都围绕"完整闭环 + 越用越快越懂"两个最高目标。

# 46. 与 Visual Design System 的关系

视觉系统负责：

``` text
Color
Typography
Icon
Button
Card
Chip
List
Input
State
Motion
Illustration
```

本文负责：

``` text
这些组件为什么出现
什么时候出现
用户下一步是什么
页面如何形成闭环
哪些行为应该沉淀
系统如何学习
```

两份规范必须共同执行。

一个页面即使完全符合视觉规范，但如果：

``` text
主操作不明确
流程断裂
用户需要重复输入
没有下一步
Agent 和旧功能互相竞争
```

仍然视为产品体验不合格。

# 47. 最终验收原则

V4 不是以"页面全部重画完成"为验收。

真正验收应回答：

### 完整闭环

用户能否从：

``` text
不知道吃什么
```

自然走到：

``` text
决定吃什么
→ 知道怎么做
→ 知道买什么
→ 保存计划
```

而不需要自己寻找多个孤立功能？

### 越来越方便

长期用户是否：

``` text
输入更少
点击更少
等待更少
重复设置更少
```

### 越来越懂

系统是否：

``` text
更少推荐用户刚吃过的
更少重复用户明确拒绝的
更准确使用长期偏好
更准确区分临时需求
更少犯相同错误
```

### 仍然可控

用户是否始终能够：

``` text
查看
调整
拒绝
确认
修改偏好
```

系统的目标不是替用户做不可控决定，而是：

> **把繁琐的判断和执行准备工作尽可能替用户完成，把最终决定留给用户。**

------------------------------------------------------------------------

# 48. 一句话产品原则

如果后续团队、Agent 或开发者只能记住一句话，应记住：

# "让用户更快把一顿饭安排好，并让下一次比这一次更省事。"

这句话同时包含：

``` text
闭环
+
效率
+
个性化
+
长期价值
```

也是 V4 及后续版本所有产品、交互、视觉和 Agent 技术决策的最高判断标准。

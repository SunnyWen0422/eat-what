# Agent 项目接手指南

整理日期：2026-10-18。面向首次接手及续接任务的 agent。内容来自源码、用户确认和本仓库验收/操作记录；本次整理没有连接生产或重新验收功能。

## 1. 先分清三种信息

- **长期规则：** 用户已确认的产品取舍、数据语义、安全与工作方式。下文记录，改变时需同步相关契约及文档。
- **历史事实：** 带日期的提交、截图、测试、端口、部署、预算。只能证明当时情况，不证明现在仍相同。
- **当前状态：** 工作区差异、远端 SHA、运行包、开关、服务归属、数据结构、剩余额度。执行相关任务前现场核对，不从旧报告猜测。

当前用户指令及明确授权优先于旧计划。历史“默认关闭”“暂停测试”“已部署”“还剩 4 次”不能直接套到新任务；有冲突先定位日期、源码与具体授权，不随意切开关、重置额度或重发操作。

## 2. 五分钟接手顺序

1. 阅读根 [AGENTS.md](../AGENTS.md)、本文以及当前用户请求，明确是分析、开发、推送还是上线。
2. 在正式仓库检查 `git status --short`、当前分支和 HEAD；区分已有改动与本任务改动。父工作区规则存在时一并阅读。`work/`、导出项目、旧 checkout 不作为代码来源。
3. 依任务阅读 [开发流程](development-workflow.md) 或 [运维手册](operations/agent-runbook.md)，再查看 [DEVELOPER.md](../DEVELOPER.md) 对应章节。不要为普通任务全盘扫描私有运行目录或依赖缓存。
4. 找与目标功能相关的最近计划、验收和源码；报告只提供索引，最终行为需要核对源码或运行证据。
5. 记录任务基线、影响范围、保留规则、成功条件及必要验证。按已授权范围持续执行；普通可逆选择不反复问用户。

长期开发目标分支曾为 `codex/v4-meal-workspace-green-20261003`，仓库为 `SunnyWen0422/eat-what`；每次操作仍核对用户目标、当前分支和 origin，不把本文当硬编码推送地址。新工作分支默认前缀 `codex/`。

## 3. 系统地图与责任

| 部分 | 入口 | 负责什么 / 不应误认为 |
| --- | --- | --- |
| 小程序 | `app.json`、`pages/`、`components/`、`utils/`；API 来源 `utils/config.js` | 微信登录、餐务交互、缓存和恢复；打开本地源码仍可能请求线上 API |
| 网页 | `web/`；[说明](../web/README.md) | 独立构建、公开菜库、浏览器 IndexedDB 个人记录；不是微信账号数据的自动同步镜像 |
| Java | `backend/` | 认证归属、数据库业务、版本、幂等、真实回执、助手编排；前端不直接连接 MySQL |
| Python | `recommend-service/` | 推荐/模型适配、工具协议与回答处理；普通生产入口为 `main.py`，隔离替身不能替换正式服务 |
| MySQL | 服务端私密配置指向的库 | 业务事实和关系；本机匿名化备份不能整库覆盖生产 |
| 检索与会话 | 服务端索引及适用的会话存储 | 索引可重建；既有聊天/SQLite 快照也是备份范围，不因换服务目录丢弃 |
| 验证与交付 | `scripts/`、`tests/`、`backend/src/test/`、`web/` 检查 | 单元、隔离、原生、模型、数据库和部署各有证据，不能相互替代 |

## 4. 不要在优化时丢掉的产品细节

- 主线是“今天选一餐 → 调整 → 安排到日历 → 准备食材 → 查看做法 → 独立记录实际用餐”。保存计划不等于吃过，回顾不能用计划冒充事实。
- 普通页面保持温暖餐桌 A；菜品卡片、饮食助手及推荐采用轻透浮层 F。小程序助手统一名称为“饮食助手”；首页入口位于标题右侧，采用细渐变边框、浅色底和深色炫彩文字的紧凑胶囊，保留完整触控区域和纯色兼容显示。减少无功能装饰、重复标题和内部说明；主次按钮必须可辨，不能为了简洁删掉必要失败/恢复入口。
- 菜谱分类采用左侧竖栏，“个性化”的展开操作右对齐；筛选标签紧凑但保留 44px 触控区，未选项须有可辨识底色和边界，选中项用深绿白字。菜品缩略信息默认两行；图片、两行文字整体及右侧操作组共用垂直中心线，不把操作放到第三排。长菜名可省略，详情及辅助标签保留全名，必要反馈不可裁掉。常用菜单列表新建走“选菜 → 命名保存”，从本餐保存则直接沿用已有菜品命名；模板选择独立于本餐与日历。详见[菜谱及常用菜单体验记录](ui/2026-10-19-recipe-personalization.md)。
- 菜谱标题与带放大镜的搜索框同排，不保留右上说明入口；搜索与清空沿用实时筛选逻辑。首页取消补充要求白条，个性化、自己选菜和闹钟图标（用时与食材）共用一行；已有本餐文字要求在更多中可查看修改，不能因移除入口悄悄丢弃。见[首页与菜谱工具栏](ui/2026-10-19-home-catalog-toolbar.md)。
- 菜品行用五角星直接收藏，空心/实心及颜色区分状态；与“换一道”放在同一操作组并排、等高、同底色和圆角，不能各自换行。助手卡片同样适用。普通次按钮用浅绿实底，输入框边界及选中状态保留必要辨识度。
- 菜谱阅读直接展示已有原方用量，去掉成人统计口径、冗余和重复来源按钮；有内容的烹饪提示放在食材下方。原方可读不等于份量已审核，不能据此开启自动换算、改质量标记或覆盖采购的未知用量。详见[食材阅读与收藏规范](ui/2026-10-18-recipe-reading-and-favorites.md)。
- 日历日期采用透明按钮和选中数字圆形底色；空餐次只显示“没有记录”，右侧使用轻量“安排 / 查看”，整张卡片点击进入对应餐次。实际菜名旁不重复“已记录吃过”，计划保留“已安排”，明确没吃只说明一次；人数、无障碍语义和必要失败/恢复提示保留。日历首页不再放“更多”及其三个跳转。见[日历精简记录](ui/2026-10-18-calendar-simplification.md)。
- 菜品有图优先使用真实图片并保留圆角，缺图或实际加载失败才显示分类图标。图片字段、URL、前端映射、网络加载分别检查；本机浏览器能显示不保证服务端或微信使用相同缓存/证书链。不得把某次证书失败扩展成所有图片不可用，也不得顺手关闭全局 TLS。
- 模型可组织简短自然回复、为卡片提供展示名；卡片实际 ID、图片和详情仍绑定真实菜品，展示别名不改数据库名称。
- 明确保存日历/加入采购的指令在新能力协商后直接办理，旧请求保留旧确认约定；缺少用户才能决定的信息仍可追问。模型判断意图，服务端约束身份、对象、版本和事实。不能从一句建议推断用户已要求写入。
- 处理中补充是停止并核对旧请求后继续，不是往供应商已启动的同一次推理注入消息。已完成操作保留，未发送文字保留，未知结果先核对原请求。
- “复制菜谱”在编辑保存时创建，取消未保存编辑不留副本；保存结果未知时保留原请求恢复入口，即使来源菜谱已下架。
- 官方参考价与用户实付分开。缺价格保持空缺，不能补 0 或猜测；真实 0 元实付有效。官方报价保留真实日期。最后一个食材来源移除时删除对应实付，重新添加不恢复旧金额；仍有来源则保留。
- 购物食材采用紧凑名称/用量行，缺用量留空，不显示“用量待核对”占位；原始来源的角色、步骤、成人口径和冗余不直接进入列表、费用或剪贴板。展示清理不授权换算、合并或估价，采购形态和部位仍要区分。右上垃圾桶进入逐项删除模式，红色减号按现有版本与幂等约束删除；底部“复制菜谱”按当前待买/已买分组复制排版清单。见[个人资料与购物清单精简](ui/2026-10-19-shopping-profile-refinement.md)。
- 购物清单“添加食材”直接打开自定义表单，仅食材名称、分量（均必填）和备注（选填）。空清单与有内容清单共用底部入口，不再提供日历/菜谱添加选择；其他页面现有准备食材链路保留。取消不写入，保存继续使用已有幂等和待确认恢复逻辑。
- 购物清单右上角垃圾桶左侧“购物篮＋勾”图标表示全部标为已买；点击先询问“是否全部已购？”，选“是”才修改全部待买来源，取消不写入。它不是外部购物跳转，不新增实付金额；没有待买项时禁用，继续遵守版本、幂等及未知结果恢复约束。
- 语音暂不可用时显示“抱歉，该功能暂不可用”。暂停模型测试不等于关闭正式模型功能；历史真实请求额度不可重复使用。
- 质量证据不自动等于审核通过；不伪造营养、份量、时间或 VERIFIED。普通浏览/手选与自动推荐门槛需分别核对，不能为了演示把全部功能关闭或假造审核。

依据：[近期产品与规则复审](testing/2026-10-17-75716e0-review.md)、[助手表达/执行约定](testing/2026-10-17-assistant-flexible-execution.md)、[助手异常衔接复审](testing/2026-10-18-assistant-behavior-review.md)、[全页面一致性复审](ui/2026-10-19-all-pages-review.md)、[一级二级页面对齐复核](ui/2026-10-19-all-levels-alignment.md)。新增对齐记录覆盖二级表单、助手操作卡和管理页；共享样式须检查同名类污染，原生单行输入不加垂直 padding，picker 可见内层使用明确类名。原有全页面记录中的未确认项不因后续局部检查自动消除；测试数和部署状态只属于对应版本。

## 5. 本地开发的常见误判

| 现象 | 经验与处理 |
| --- | --- |
| 编译成功但页面仍旧 | 核对开发工具实际项目目录、导出时间、源码版本、API 来源与运行包；不要在旧导出副本继续开发 |
| 构建了新 JAR，接口仍旧 | 本机运行器使用固定哈希快照，默认重启沿用保存包；显式选取已验收新包后核对运行路径和哈希 |
| 项目扫描 EPERM、访问被拒绝 | 先看具体目录及执行环境；使用全新项目外导出目录或可写测试目录，不递归放宽权限、不删除原失败目录 |
| 原生导出提示组件不存在 | 检查导出清单、`usingComponents` 依赖及包排除规则；源仓库有文件不代表验收包包含它 |
| CLI 等旧端口、自动化超时 | 核对工具是否运行、当前项目、当前服务端口和编译弹窗；旧日志不是已开启证明。安全设置变化沿用明确授权，不无依据反复重试 |
| 手机无法访问本机预览 | 手机 localhost 是手机本身；临时测试项目 ID、访问地址与真实微信授权要分别成立。模拟器通过不写成真机通过 |
| Maven 离线失败或原生依赖缺失 | `-Offline` 不会自动补依赖；区分环境失败与业务断言失败。按验证说明准备独立环境，不修改系统依赖或清理他人缓存 |
| Python/Java 测试分别全绿但功能不通 | 测试可能替换了真正出错的适配层。按开发流程补实际边界的契约/隔离链路证据，不能只增加相似单元测试 |

本地启动与参数参见 [本机验证](testing/local-verification.md)，但其中日期限定的线上 404、开关和额度均需重新核对。新隔离验收使用 `scripts/maturity_runtime.py` 等带归属检查入口；普通已有本地环境通过 `scripts/start_local_maturity.ps1` / `scripts/local_maturity.py` 管理。两者用途不同，不接管未知监听进程。

## 7. 每次交接保留什么

在现有任务记录追加简短交接：目标与范围；当前分支/完整 SHA/未提交文件；已确认的产品决策；源码、构建、部署分别处于哪里；验证环境、结果与未覆盖项；本机私有证据位置；下一项具体行动及阻塞。

不要把完整聊天、供应商密钥、数据库密码、Token、私钥、原始用户信息或私有配置粘进仓库。机器专属端口、代理和路径留在仓库外工作区规则/私有运行清单；仓库写查找方法和脱敏结果。若某项操作只能通过现有私有工具完成，说明其用途、归属与读取位置线索，不复制其中凭据或假装仓库已有通用部署器。

经验有变化时更新本指南对应段落并链接证据；历史报告加日期/被替代说明，不抹掉失败现场。不要新增多份相互冲突的“最新总方案”。

# 推荐策略：合口味、能换新、不被收藏绑住

策略版本：`balanced-v1`。适用于小程序首页与饮食助手；独立网页不在本轮接入范围。
本文维护产品与接口规则，测试证据见[实施验收记录](testing/2026-10-21-recommendation-policy.md)。

## 1. 候选与明确限制

- 收藏不加分、不参与口味学习。用户明确要求“从收藏里选”时，使用 `candidateScope=favorites` 限定候选；界面展示该范围，并允许改回全部菜谱。
- 忌口、排除以及“不要 / 只要 / 必须”等明确限制进入 `criteria`；普通“想吃”、偏好的菜系、口味、饮食、场景与做法进入 `recommendationPreferences`。
- 新协议下，硬标签同一维度满足其一、不同维度同时满足。例如“清淡且必须蒸”不能退化为“清淡或蒸”。新加不同维度限制保留原有限制；相同维度收窄时取交集，冲突提示处理。
- 手选、点名与保留不受自动轮换约束；自动补菜不能移除保留项。保留菜与新硬限制冲突时提示处理，不静默替换。
- 只从当前用户有权使用、符合原有推荐质量要求的菜库中取菜。未知食材、做法和用时不猜测；菜谱浏览的搜索与筛选仍是筛选。

## 2. 选择顺序与权重

先执行硬限制，保留指定菜，检查分类轮换，再回应本餐想吃，最后概率补齐剩余菜位。
每次选菜同时检查剩余菜位是否仍能完成，防止先选一道导致整餐违反明确用时或无法搭配。

| 因素 | `balanced-v1` 参数 |
| --- | --- |
| 基础机会 | 100 |
| 收藏 | 0 |
| 本餐想吃 | 每命中一类 +60，最多 +120；整餐已有回应后，其余菜每类 +15，最多 +30 |
| 长期偏好 | 每类 +30，最多 +60；本餐已主动设置的同类不再叠加 |
| 手边食材 | 每种可靠主料 +15，最多 +30；常见油盐调味料不加分 |
| 期望用时 | 满足 +20，超出按比例最多减 20；未知中立。单菜与整餐期望不会重复累加时间奖励 |
| 显式分数范围 | 基础与上述加减分限制在 50～300 |
| 行为学习 | 最终乘数 0.8～1.2，主动设置的维度不受学习反向调整 |
| 整餐重复折扣 | 主料重复 ×0.7、做法重复 ×0.9、口味重复 ×0.9；合并最低 ×0.5 |

每次抽选有 75% 机会按权重抽取、25% 机会均匀探索，都只在当前合格候选中进行。
分数不用于排序后直接取前几道；75% 不是偏好命中率承诺。同维度多选按“满足其一”计算，标签数量不会无限叠分。

有符合本餐想吃、尚未轮到且能完成整餐的候选时，至少安排一道。偏好候选本轮用完、仍有其他新菜时，先提供新菜并说明。
实际吃过或前后一天已安排属于避重偏好；有必要时可让位于本餐明确想吃，并如实说明。

同名版本按规范化名称合并机会，不能通过多份版本提高被抽中的概率。保留符合条件的版本用于可行性判断；有可用的偏好版本时优先以该版本回应，不因先读到另一版本而漏掉本餐要求。

## 3. 三种记录分别使用

| 记录 | 保存与用途 |
| --- | --- |
| 本餐推荐轮换 | 工作区按账号、日期、餐次持久保存，各菜品类别独立记录规范化菜名；首页与助手共用 |
| 实际用餐 | 使用真实“吃过”记录，优先避开设定窗口，默认 7 天；候选不足时允许回退 |
| 日历安排 | 优先避开目标日前后各一天的计划；不把计划记为已经吃过 |

某类还有新候选时先用新菜；该类别耗尽才重开一轮。一份菜单跨越轮次时先消耗剩余新菜，同一菜单内仍不能放两份同名菜。
跨类别同名菜必须一起检查可完成性，避免误报无菜或提前重复。

只有有效工作区版本成功提交后才发布轮换；失败、取消、过期、重复回执和晚到结果不消耗机会。
退出页面、返回首页或进入助手不会清空。撤销菜品调整保留本轮已经展示过的菜名，防止 A→B→A 循环。

## 4. 缓慢学习与清除

学习只接收新的明确类型事件：推荐成功的展示、成功采用、成功单独换掉。
旧的混合“换菜”日志不回填；收藏、取消收藏、浏览和整套换一套均不提供长期喜恶反馈。

- 学习特征为已有可靠的口味、菜系、做法信息，不给某道菜单独建立常驻加成。
- 每个特征至少 10 次有效展示、涉及至少 3 道不同菜、2 个不同操作日期后才生效。
- 采用和换掉必须对应有效展示；同一账号、餐次、菜名和事件类型去重。
- 采用数、单菜换掉数、展示数按 30 天半衰期衰减，只使用最近 90 天事件。
- 特征值为 `(采用数－单菜换掉数)/(展示数＋5)`，限制在 -1～1；映射为 `1 + 0.2 × 特征值`。取当前菜相关有效学习特征的均值，无有效特征时乘数为 1。
- 本餐或长期主动选择的同类维度不再被学习乘数调整。撤销换菜抵消对应负反馈，反馈绑定原操作版本，不能因中间保留/撤销重编号而丢失。

偏好页提供“清除学习记录”，仅在后端声明支持时显示。确认后清除当前账号的新学习事件，不删除手填偏好、收藏、日历或实际用餐。
重置接口为 `POST /api/users/preferences/learning/reset`（应用内路由 `/users/preferences/learning/reset`），携带 `requestId`；相同请求重放不会删掉重置之后的新反馈。结果未知时保留该请求身份供重试，切换账号隔离待处理状态。

## 5. 首页、助手与外部模型的分工

```text
首页设置 / 用户聊天
  → 账号与餐次工作区
  → 模型理解本餐意图（需要自然语言时）
  → 硬条件 + 推荐偏好 + 候选范围
  → Java 统一候选、轮换、概率搭配、校验
  → 事务提交菜单、轮换与有效反馈
  → 首页和助手读取同一结果
```

外部模型不掌握默认推荐概率，也不直接替自动推荐指定菜品 ID。它输出可校验的意图和条件；只有明确点名/手选的菜，才允许依据已读取的真实菜品引用提交 ID。
普通推荐上下文不发送收藏加权信号。学习结果只用于服务端抽选，不要求模型靠提示词实现概率。

协议区分以下字段：

- `recommendationPolicy: balanced-v1`：启用新偏好语义。
- `criteria`、既有明确整餐用时限制：必须满足的条件。
- `recommendationPreferences`、`expectedTotalCookMinutes`：推荐倾向。
- `candidateScope: all | favorites`：候选范围。

推荐选项声明 `recommendationPolicyVersion` 和 `learningResetEnabled`；Python 能力接口也声明策略支持。
新客户端只有实时确认能力后才启用新语义，不依赖过期缓存宣称“倾向”。没有协商的旧请求保留原硬筛选含义；旧工作区的明确限制在界面中可见、可主动取消，不静默放宽。
在新语义下，长期保存的用时是期望；本餐明确填写的硬用时仍是限制。界面相应使用“期望用时”，未知用时不宣称满足。

首页自然语言解释与助手动作都合并未修改的条件；局部修改口味不能清空菜系、用时或候选范围，也不能丢弃其他维度的硬限制。
模型失败、取消、恢复、版本冲突继续走原有请求生命周期；不通过重新生成来冒充原请求恢复。

## 6. 发布顺序与评估边界

2026-10-21 已按用户授权完成 `V8_40` 线上增量迁移及 Java/Python 配套更新，两端能力回查确认为 `balanced-v1`；小程序未发布，真实模型链路未在生产执行验收。证据与边界见[后端上线记录](operations/2026-10-21-recommendation-backend-update.md)。后续发布仍必须遵循[运维手册](operations/agent-runbook.md)及当次授权：

1. 核对备份并按迁移清单应用增量 `V8_40__recommendation_learning.sql`。新增学习事件及重置回执表，不重写旧业务记录。
2. Python 先具备 `balanced-v1` 协议能力，或安排协调切换；Java 启动前必须已有新表。普通推荐完成、采用和定时清理会访问新表，没有“缺表也已启用”的静默降级。
3. 更新 Java 后验证能力接口、首页/助手同餐状态、学习重置及请求恢复，再发布小程序。独立网页另行决策。
4. 回退前检查工作区新字段与旧运行包兼容性；保留增量表、回执和原始业务数据，不靠删表或覆盖用户记录回退。

初始参数固定为 `balanced-v1`。调整时同时考察采用率、连续换菜次数、重复率、菜品覆盖率，并记录新版本；不能只追求采用率，也不能从隔离模拟推断线上用户效果。
离线模拟、真实序列化边界和私有测试数据库不替代真实模型表达质量、微信真机交互或线上容量验收。

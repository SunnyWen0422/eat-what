> 更新：2026-10-03。分支 `codex/full-ui-meal-workflow`，基准 HEAD `47b854ed4b8d3c1683baa248cf9a3701515511b2`。本次包含原未提交改动，已保存可恢复快照。源码已实施，V4 默认关闭，尚未发布。详细接口、25 页及内部功能清单见 [前后端详细设计](./eat-what-agent-fullstack-detailed-design.md)。

## 1. 一眼看懂现在的项目

Eat-What 是微信原生小程序，已有菜谱、推荐、助手、日历、购物、个人设置和小程序管理页。技术栈保持 Java 8 / Spring Boot 2.7.14 / MyBatis / MySQL 与现有 Python 推荐服务。本次覆盖 25 条注册路由，导航统一为“今天、菜谱、计划、我的”。

这版把主要任务集中到 **当前这一餐**：输入可以留空，按人数得到一套菜；想法复杂时继续说需求；菜单调整和未确认草稿由 Java/MySQL 保存；确认后接入日历、采购、实际记录和回顾。今天、结果和助手使用同一工作区，避免几处页面各自维护菜单。

**四种数据的含义要分清：**

| 数据 | 意义 | 什么时候产生 |
|---|---|---|
| 当前餐草稿 | 还在决定吃什么 | 生成、选菜、调整；在线跨设备可恢复 |
| 正式计划 | 打算在明确日期/餐次吃什么 | 点击“就吃这个”或直接编辑安排 |
| 购物清单 | 要准备/已经采购哪些食材 | 采购预览明确确认，或手动添加 |
| 实际用餐 | 用户明确说这一餐吃了什么 | 按计划确认、记录实际换菜 |

例如：计划清蒸鱼，采购完成后实际吃了番茄面。计划仍可保留鱼，实际记录是面，回顾只统计明确的实际；删除鱼计划不能抹掉面这餐历史。“按计划吃了”沿用已保存的可信快照，菜品库后续改名或分类变化也不会偷换这次实际记录。

## 2. 为什么改，改完有什么效果

| 原有问题 | 改造 | 用户效果 |
|---|---|---|
| 条件较多，第一屏像参数工具 | 当前餐日期/餐次/人数可见，高级菜数折叠到设置 | 留空即可安排，明确知道菜单保存到哪餐 |
| 推荐结果与助手各有草稿 | Java 权威工作区，三个入口共用状态 | 返回、退出、换设备仍能接着调整 |
| 人数与菜数缺少自然默认 | 午晚餐人数模板、独立早餐场景、手动模式 | 两人一荤一素；改人数不覆盖手动菜数 |
| 确定菜单后还要寻找日历保存 | “就吃这个”直接保存当前目标；已有安排显示替换差异 | 决策立即变成可执行安排，不自动采购或记录吃过 |
| 计划与实际概念混淆 | 独立实际快照、legacy 历史不自动计入 | 回顾可信，改计划不改历史实际 |
| 采购来源与用量难追溯 | 原始来源行、日期餐次/人数、服务端换算、云端手动项 | 同菜跨日可累加，按餐次查来源，手动项换设备可读 |
| 失败、重试和并发容易误报成功 | 幂等回执、CAS、未知请求查询、显式冲突重试 | 超时只写一次，另一设备改动不会悄悄覆盖 |
| 异步网络重试可能串账号 | 每次发包及确认/响应都检查捕获身份 | A 的菜单、资料和采购不能写到 B |
| 菜品在确认期间变化 | 锁定当前读、比较用户已看到的语义快照 | 原菜单变更有冲突反馈，不混写旧名和新配方 |
| 页面、图标、弹层风格各异 | 深绿 Token、15 个公共组件、36 图标、5 类插画，全页接入 | 一级、二级和小功能使用同一家庭厨房风格 |
| 热量/时间表达缺依据 | 实际分类回顾、已知整餐时间；无依据不输出估值 | 解释可核对，避免把记录包装成营养结论 |
| 缺少可信接受/完成反馈 | 曝光与业务事件、去重、当前 actual 完成口径 | 可以验证产品效果；首版不自动推断偏好 |

## 3. 用户会经历什么

1. 打开今天，看到明确日期、餐次和人数。首次默认两人；常用人数在偏好页明确设置，本餐临时修改不反写。
2. 留空点击“帮我安排”。午晚餐按人数搭配，早餐选场景候选。输入自由需求才使用 Agent，结构化操作继续使用规则。
3. 换一道、换一套、保留、撤销，或从菜谱自己选菜。手动菜数在人数变化后保持；可恢复自动搭配。
4. 点击“就吃这个”，空槽直接保存；已有安排先看旧/新菜单再确认。成功显示做法与采购入口。
5. 在计划周/月查看三餐、编辑/复制安排，进入采购预览核对份量与家里已有食材，明确加入清单。
6. 清单按食材或餐次查看，手动添加、改量、勾选、删除、清空。采购完成不会标记为吃过。
7. 吃完选择“按计划吃了”或记录实际换菜，也可取消安排、修改或撤销实际。我的/计划进入周月回顾，点击记录可以纠正。

遇到网络问题，界面显示未同步/待确认并保留输入。恢复后用户明确重试，原请求 key 不变；遇到冲突先查看最新，重新应用本机输入并确认。不会把本机草稿冒充已保存。

Java/MySQL 是工作区权威。Python 仅返回候选 ID 和明确理解的限制；Java 校验可信菜品、人数、数量、忌口、保留项与版本后应用。模型没有直接写计划/购物/实际的权限。

无文本和结构化操作不调用 LLM。Agent 网络预算为连接 1 秒/读取 14 秒；超时只在文字曾可靠解释且上下文未改时按已知条件规则降级，其余需要补充信息，原方案保留。不因降级丢掉临时忌口。整餐时间与旧单菜筛选分开，已有食材不当库存。

## 6. 必须保持的工程规则

**计划与实际分开。** 改/删安排不毁 actual；自由实际文本不能猜分类或营养。未来餐次可以安排，不能提前标记吃过。

**版本和幂等一起检查。** workspace revision 与 planVersion 不可混用；确认还校验 plan revision。超时必须原 key/原内容重试，同 key 改内容拒绝。计划墓碑版本不能退回 0。

**归属由认证决定。** 不用前端 userId 决定归属。读取、表单、弹窗、轮询、返回以及每次网络重试都核对原身份；分账号缓存不是全部安全边界。

**菜单确认使用审核快照。** 在事务中当前锁定读完整菜品，检测食材/做法/名称/类型/时长等变更，冲突后重新生成并确认。避免 MySQL RR 普通读沿用旧快照。

**反馈不等于学习。** 接受率用真实曝光方案；完成数来自当前 actual，修改/撤销不重复计。事件只保存标识/来源，90 天保留；未确认草稿 30 天清理，不清正式计划、实际及回执。

## 8. 如何启用、发布和回滚

V4 前端 `ENABLE_MEAL_WORKSPACE=false`、Java `MEAL_WORKSPACE_ENABLED=false`。默认 API 地址仍为项目原配置。先使用测试 API、明确测试数据库，在已有基础 schema/V1/V2 上依次验证 V3/V4，部署兼容后端，再打开两端开关。

内部 Agent 使用环境变量 `MEAL_WORKSPACE_SERVICE_TOKEN`，Java/Python 一致；空配置拒绝。原模型、认证、微信凭证、MySQL 配置沿用环境，不能硬编码或绕过鉴权。首次 schema 仍要核对历史列/索引，私有测试 fixture 不能代替已有库审核。

**发布前仍需完成：**开发者工具真实运行、iOS/Android 全部页面与小功能状态、320px/字体放大/键盘/安全区/授权取消、两个真实设备草稿恢复、Agent 效果/P95 测量、早餐产品审阅、固定实际通过验收的稳定基础库。目前 `libVersion=trial` 尚未作为发布版本确认。

回滚优先关开关或恢复前端，保留兼容 V3/V4 的后端与数据。旧后端不了解计划墓碑，不能直接混用；数据库回滚恢复审核过的备份，不删除实际快照或请求日志。开工快照在任务目录 `snapshots/`，本次没有 commit/push/部署。

## 9. 下一版的承接点

先完成当前主闭环的运行验收和反馈口径验证，再扩展。家庭协作需要成员与共享权限模型；库存扣减需要数量账本和补购差额；营养需要可靠份量和食品数据库；食材复用需要跨餐优化。这些不能通过重命名现有分类统计替代。

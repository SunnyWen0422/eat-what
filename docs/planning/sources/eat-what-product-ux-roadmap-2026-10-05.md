## 1. 核心判断

这个项目已经不只是“随机推荐几个菜”的原型。它有真实的模型调用和只读工具循环、确定性筛选、当前餐工作区、版本保护、计划保存、购物清单、实际用餐与回顾，以及统一的视觉资产管线。

更准确的阶段定位是：**已有较完整的 V4 单餐闭环源码，处于发布前运行验收和产品打磨阶段；还不是经过真实用户验证的完整成熟型个人饮食 Agent。**

最重要的前提是 `utils/config.js` 中 `ENABLE_MEAL_WORKSPACE = false`。V4 实施记录同时说明两端开关默认关闭、未合并和发布。不能把本分支源码实现直接当作现网用户已可用的功能。[R01][R02][R03]

建议延续已有路线，不重新搭一个聊天机器人，也不重写 Java/Python 两套服务。后续顺序为：

**验收并安全启用现有闭环 → 减少选菜与执行负担 → 跨模块 Agent 与受控执行 → 有边界的个性化 → 可信食材与营养数据 → 多餐协同 → 高级能力与生态扩展。**

## 2. 产品定位、用户与成功条件

### 2.1 建议定位

产品定位：**面向个人长期使用、以成熟消费级 App 品质建设的智能饮食助手**。它以真实一餐为核心闭环，但 Agent 最终应贯通菜谱、日历、收藏、自定义菜品、购物清单、实际记录与饮食分析，而不是只负责生成一份菜单。

用户表达需求，系统使用可信菜品数据给出可调整菜单，帮助准备食材、查看做法、记录实际用餐，再用反馈改善下一餐。首页不是数据库控制台，也不是迫使用户反复描述背景的聊天窗口。

品牌表达可以是：“少想一步，把这一餐安排好。”避免“全自动营养师”“绝对健康”“自动买好一切”等当前数据和履约能力不支持的承诺。

### 2.2 首要用户假设

优先验证在家做饭的 1–4 人用户，尤其是工作日晚餐的决策者。典型约束是时间有限、想吃家常菜、要避免重复、家里有一些食材、希望少买漏买。

这是产品聚焦建议，不是现有用户画像调查结果。源码允许 1–50 人；不必删除上限，但不应以 50 人宴席场景牺牲日常两人用餐的默认体验。早餐、多人聚餐、家庭成员差异可分层扩展。

### 2.3 三条路线比较

| 路线 | 优点 | 问题 | 建议 |
|---|---|---|---|
| 菜谱内容平台 | 浏览、搜索、收藏容易理解 | 内容生产和版权成本高，不能充分体现“替用户做决定” | 作为支撑层，不作为主定位 |
| 聊天优先 Agent | 自由表达强，演示效果突出 | 状态、保存、纠错和采购容易藏进对话；每次都要描述背景 | 不作为默认首页 |
| 任务优先＋上下文 Agent | 菜单、动作和结果可见；自然语言与按钮互补 | 需要统一状态与可靠业务边界 | 推荐，现有 V4 已经走在这条路上 |

### 2.4 两个视角的验收标准

用户视角：打开就知道当前处理哪一餐；少输入；不满意能局部改；采购能照着买；下厨不用反复找菜谱；吃完容易记录；下一次不必从零开始。

产品经理视角：一餐任务是否真正完成；用户在哪一步离开；推荐是否满足硬约束；首次采纳和局部调整是否改善；Agent 跨模块任务是否正确完成；基础页面是否仍然易找易用；可靠数据覆盖是否增长；响应、稳定性和资源消耗是否处于可接受范围。

不以聊天轮数、生成菜单数量或漂亮截图代替产品价值。

| 发布成熟度 | 仓库记录270项验证；同时明确未完成最新轮原生和真机验收 | 源码与部分自动验证较充分，产品运行验收仍有发布门槛 |

### 3.1 已经做对的地方，应当保护

草稿、正式计划、采购和实际记录互不冒充。模型只读工具与 Java 业务写入分离。确认前检查归属、菜品快照、条件和版本。多设备冲突不静默覆盖。实际记录不随菜库修改而被重写。营养数据不足时不展示伪精确热量。已有 Token／组件生成管线。

后续功能不得为了“更智能、更少点击”破坏这些边界。[R04][R06][R07][R08]

## 4. 用户主旅程与状态设计

### 4.1 理想单餐旅程

**打开当前餐 → 复用常用人数和明确偏好 → 补充临时条件（可跳过）→ 看一套方案 → 局部替换／保留 → 确认计划 → 核对缺少食材 → 看整餐做法 → 确认实际吃了什么 → 获得下次建议。**

采购不是每一餐必经步骤；已经有食材的人应直接开始做饭。记录也不要求完全照计划，外食／改菜／没做都应能表达。用户不需要一次完成整条链；返回小程序恢复到相应上下文。

### 4.2 状态与主按钮

| 业务／界面状态 | 首要按钮 | 次要操作 | 明确禁止 |
|---|---|---|---|
| 无方案 | 帮我安排这餐 | 自己选菜、修改人数／条件 | 强制长问卷 |
| 生成中 | 停止本次安排 | 查看原方案 | 重复提交、伪造百分比进度 |
| 草稿已生成 | 就吃这个 · 保存到明确餐次 | 换一道、修改要求 | 保存到隐含日期 |
| 条件已更改 | 按新要求重新安排 | 看原方案 | 沿用未验证的旧方案确认 |
| 条件无法理解 | 补充这一个条件 | 进入结构化筛选 | 假装全部理解 |
| 已保存、食材未核对 | 准备食材 | 开始做饭、调整安排 | 自动创建订单 |
| 用户明确食材齐了 | 开始做饭 | 查看清单／调整计划 | 自动认定已吃 |
| 做饭结束、尚未记录 | 记录这一餐 | 按计划吃了、有变化、没做 | 定时默认记为吃过 |
| 已记录实际 | 查看／修改记录 | 回顾、安排下一餐 | 修改计划连带改写实际 |
| 保存结果未知 | 确认上次保存结果／原请求重试 | 保留输入 | 换新幂等键重复写入 |
| 多设备冲突 | 查看最新与本次差异 | 保留本次输入后重应用 | 静默覆盖另一设备 |

“食材齐了／做饭进度”是建议新增的辅助状态，不替代已存在的计划和实际业务对象。可以先以轻量本餐进度实现，后续是否跨设备同步需明确契约。

### 4.3 不同首次进入方式

从首页进入：目标为当前选定日期餐次，初次默认值可参考业务时间；工作中不可因过了时间点自动切餐。

从菜谱分享进入：先查看菜品，再选择加入哪一餐，不能默认改写已有晚餐。

从购物清单进入：优先显示待买与上次购物进度，不强迫回首页生成。

从回顾进入：能查看证据餐次、纠正记录，再将建议变成下一餐的条件。

## 5. 信息架构与入口优先级

继续使用既有四 Tab：**今天／菜谱／计划／我的**。[R02]

| 入口 | 核心职责 | 一级内容 | 二级内容 | 不应占首屏的内容 |
|---|---|---|---|---|
| 今天 | 完成当前一餐 | 日期餐次人数、菜单、当前下一步 | 修改要求、换菜、待买摘要 | 管理后台、长统计、所有参数表单 |
| 菜谱 | 找到与复用菜品 | 搜索、分类、与当前餐有关的选择 | 收藏、最近做过、自己的菜 | 大段品牌宣传 |
| 计划 | 跨天管理与准备 | 默认周视图、三餐状态、购物入口 | 月历、周期采购、复制、回顾 | 重复一份独立聊天状态 |
| 我的 | 管理个人资料和控制项 | 明确偏好、收藏／自定义、记录与回顾 | 隐私、同步、帮助、反馈、版本 | 把日常购物唯一入口埋在这里 |

入口优先级：当前餐主操作最高；与当前结果直接相关的换菜／采购／做法次之；搜索与计划管理再次；长期设置和历史在后；管理操作严格按权限展示。

购物入口同时出现在“今天”的待买摘要、“计划”的准备区域。保留“我的”现有快捷入口可帮助老用户过渡，但不作为唯一主路径。

Agent 不是新增一个必点的机器人 Tab，也不能成为访问核心功能的唯一入口。它应同时具备两种存在方式：一是“修改这餐要求”“换一道原因”“用已有食材搭配”“解释本餐安排”等上下文能力；二是一个稳定可达的统一助手入口，用来承接跨页面、跨对象的复合任务。

**双路径原则（硬性产品约束）：菜谱、日历／计划、收藏、自定义菜品、购物清单、实际记录、饮食报告和偏好设置，都必须同时具备独立页面操作路径与 Agent 委托路径。后续任何“Agent 化”改版都不得以隐藏、删除或弱化基础入口为代价。**

两条路径必须落到同一套业务对象和权威数据：Agent 收藏后收藏页立即可见；用户在日历修改后 Agent 读取到的是新版本；Agent 生成的报告可从报告入口再次打开；用户在清单勾选后 Agent 不得继续基于旧状态回答。禁止出现“聊天里一份状态、页面里另一份状态”的双真相。

核心功能的独立可达性建议固定为：

| 功能 | 独立入口 | Agent 委托方式 |
|---|---|---|
| 菜谱 | “菜谱”Tab：搜索、分类、详情 | 查菜、推荐、解释、加入当前餐 |
| 收藏／自定义 | 菜谱与“我的”中的固定管理入口 | 收藏／取消、创建或修改个人菜品 |
| 日历／计划 | “计划”Tab：周／月与餐次详情 | 查询、保存、复制、调整指定日期餐次 |
| 购物清单 | “今天”上下文快捷入口＋“计划”固定入口 | 从计划整理、增加、调整和核对食材 |
| 饮食报告 | “计划”或“我的”中的固定报告入口；今天可展示摘要 | 分析指定周期、解释依据、生成可追溯建议 |
| 偏好／个人数据 | “我的”中的明确分组 | 查询和修改用户明确授权的偏好 |

这些入口不要求全部成为 Tab，但必须在稳定位置可被普通用户发现；不能要求用户先打开聊天再访问自己的数据。

## 6. 关键页面布局与交互规格

### 6.1 今天／当前餐工作区

页面只回答三个问题：我在安排哪餐？建议吃什么？下一步做什么？

空态：紧凑日期餐次与人数 → 一行需求输入 → 常用条件 chips → 一个“帮我安排”主按钮 → 弱化“自己选菜”。不要把荤、素、汤、主食、甜点的所有步进器先展示给新用户。

有方案：顶部条件收起 → 菜单卡为主体 → 已验证理由最多2条 → 次要调整 → 底部固定确认。

已保存：当前菜单仍可见，新增准备食材／整餐做饭／实际记录步骤，不让用户回日历里找下一步。

示意线框（文案与菜名仅为布局示例，不代表实测推荐）：

```text
今天                                  待买 5 项
今晚 · 2 人 · 10 月 5 日                 修改
[清淡] [不用花生] [使用已有食材]       修改要求

这一餐这样吃
┌─────────────────────────────────┐
│ 菜图   番茄炒蛋          保留  换一道 │
│ 菜图   清炒时蔬          保留  换一道 │
│                                 │
│ 按已保存偏好搭配；食材详情可核对     │
│ 换一套                         更多 │
└─────────────────────────────────┘

             自己选菜 / 补充一句要求

┌─────────────────────────────────┐
│        就吃这个 · 保存到今晚        │
└─────────────────────────────────┘
今天           菜谱          计划          我的
```

顶部“待买5项”只在实际存在未购买项时显示。条件 chips 只有在已解析或用户结构化确认后才显示“已应用”。未理解的自由文本显示“待确认”，不能伪装成成功约束。

### 6.2 菜谱页

搜索位置稳定，热词、分类、已选状态不要相互挤占。主要内容使用一致的列表卡：图片／名称／可靠用时／适用人数或份数来源／一到两个标签。未知字段缺省不编造。

浏览模式点卡看详情；明确处于选菜模式时，点加号加入草稿。底部选择栏写“已选2道 · 加入今晚”，不要使用无法判断效果的“确定”“保存”。

高级条件放 Sheet，已选条件摘要常驻。用户可以清除本次筛选，但不能无提示清除永久忌口。零结果时解释导致限制不足的条件，并让用户选择放宽哪个可放宽项；禁止自动忽略过敏排除。

### 6.3 菜品详情与做饭模式

详情首屏：适度的真实菜图 → 名称／收藏／来源 → 难度和可靠用时 → 份量口径 → 食材与步骤。当前模板中“加入购物清单”排在菜名之前，建议调整为稳定底部上下文动作，不干扰认识菜品。[R18]

单菜详情主要操作根据来源变化：选菜时“加入当前餐”；已在计划内时“查看本餐做法”；单独采购时“准备这道菜的食材”。避免上下文不明的一键重复加清单。

新增整餐做饭模式：顶部可切换每道菜；各菜进度保留；字号增大；步骤少滚动；勾选备料可选。第一版只需把已知做法并排组织，不需要模型自由创作火候或并行步骤。自动跨菜排序需要结构化备料／等待／设备占用数据之后再做。

计时器由用户明确启动；进入后台后的准确恢复、权限和耗电必须实测。保持屏幕常亮只能显式开启，退出时恢复。不能承诺小程序始终后台运行。

### 6.4 计划页

保留已有周／月切换和三餐状态。默认周，月历用于远期管理与回看。今天、选中日期和有安排／已吃过的标记应可同时区分。

餐卡显示日期餐次、菜名摘要、人数、计划／实际状态。空餐“安排这餐”，已有餐“查看与调整”；复制时明确目标日期和已有冲突。

周期采购先选择日期与餐次，再看差异；不得因为浏览一个月就默认采购整月食材。历史和未来采用不同的自然动作：历史偏补记，未来偏安排。

### 6.5 采购预览

必须呈现“来自哪几餐、几个人、原配方多少份、换算哪些可信／哪些待确认、将新增或更新哪些项”。把“缺少食材”与“全部食材”分开。初期“家里有”仅影响这次采购选择；没有库存账本时不显示精确库存余额。

数量不可靠时让用户手动确认；提供菜谱原文和来源，不强行把“适量”变成克数。同名异物、不同处理状态、不可换算单位分别保留。

修改计划后不静默重写已购清单。提示“菜单有变化，核对本餐采购差异”，用来源版本追踪差异，让用户确认。

### 6.6 购物清单

默认待买、按食材汇总。首屏是可勾选食材，不是操作面板。顶部显示剩余项数／完成进度；按蔬菜、肉蛋、调味等采购场景分组，支持按餐次追溯。

每行：足够大的勾选区、名称、数量单位、必要的待核对标记。来源和高级编辑按需展开。合并必须基于标准化食材与可换算单位，不能仅按中文显示名。

“手动添加”作为次操作；“清空已买／清空全部”移入更多，破坏性操作确认并区分影响范围。勾选已买不代表做过或吃过。

离线显示上次同步时间与本机待同步项。服务端结果未知应保留原请求并核对，不能假装云端已成功。冲突文案面向实际差异，而不是让用户理解 CAS。

### 6.7 实际记录

以低负担为目标：当前餐计划存在时提供“按这份吃了”“实际有变化”“这餐没做”。有变化可以删／换菜，也支持自由记外食，不要求所有记录都先进入菜库。

“按这份吃了”只表示用户确认这次用餐，不自动得出每个人吃了相同重量。未来提供个人营养功能时，需要单独的个人份量／实际食用比例，或明确仅为整餐估算。

未知、未记录、明确没做必须不同。修改和撤销实际记录要维护统计去重；历史快照不能被后来编辑菜谱破坏。

### 6.8 饮食回顾／未来营养页

第一层是记录覆盖：本周期记录了几餐、几天，哪些是未知。第二层是可证实的多样性、常吃菜、计划执行。第三层才是有证据的短解释与一个下一步建议。

当前版本可以做“这周记录的晚餐里有3次吃了同一道菜”，不能直接做“你这周营养失衡”。不完整记录不等于完整饮食；没有记录不等于没吃。现有页面对这些差异的提示应保留。[R08][R13]

未来营养展示先写口径：“以下估算覆盖6道有可核算配方的菜，其余3道未计入；按整餐／按你确认的份量计算。”缺少油盐、份量时要具体标明，不能以免责声明代替数据。

### 6.9 我的与管理页

我的：资料、常用人数、明确偏好／忌口、收藏、自定义、回顾、数据管理、帮助反馈。长期开关必须解释作用范围，支持查看、改正、删除。

管理员入口沿用权限边界；隐藏入口不等于鉴权。所有管理按钮明确“为哪个用户／哪道菜做什么”，批量和删除操作分级确认、保留审计。管理样式可以沿用公共控件，但不要让开发工具占据普通用户核心入口。

## 8. 视觉系统、Icon 与组件标准

### 8.1 保留现有“深绿＋暖白”方向

现有 Token：品牌绿 `#28634E`、浅绿 `#EDF3ED`、背景 `#F8F7F2`、卡片白 `#FFFFFF`、正文 `#25332B`、次文字 `#617066`、边框 `#D9E1D5`、危险 `#A93B30`、警告 `#75501A`。[R12]

建议风格关键词：**家常、清爽、温暖、可靠、有食欲**。这不是金融后台，也不是炫光AI控制台。绿色集中用于主操作和当前选中态，不要每个区块都用深色大底。

页面靠留白、字重和结构形成层次。轻边界优于厚阴影；长页面避免“一句话套一张卡”，可用分组列表降低卡片碎片感。

### 8.2 字号、间距与触控

| 项 | 建议规范 | 与现有基础的关系 |
|---|---|---|
| 页面标题 | 24逻辑px，适度半粗 | 已有24，可延续 |
| 分组标题 | 18逻辑px | 已有18 |
| 菜名／重要正文 | 16逻辑px | 不要用14承载所有做饭步骤 |
| 次级说明 | 14逻辑px | 现有body14，可在公共文本角色中区分 |
| 辅助元数据 | 12–13逻辑px | 不承载关键限制、价格或操作 |
| 页面侧边距 | 16逻辑px；宽屏按比例适配 | 使用现有4/8/12/16/20/24/32间距阶梯 |
| 主按钮 | 最小48逻辑px高，清晰加载／禁用态 | 与现有primaryHeight48一致 |
| 点击目标 | 以不小于44×44逻辑px为项目目标 | 与现有touchSize44一致；图标可小，点击盒不小 |
| 卡片圆角 | 14–18为主，标签较小 | 从现有圆角阶梯中选角色，不随页面任意增加 |

这些是设计建议；逻辑px不等于每台设备的物理像素，不应直接把rpx与CSSpx混为一谈。WCAG普通文本最低对比参考4.5:1；44×44来源是增强目标尺寸级别，不应误称所有小程序的强制AA规则。原生页面还需系统字号、真实像素、键盘和安全区验证。[W03][W04]

### 8.3 简笔画与功能图标分工

保留现有图标资产系统，不再引入另一套不兼容图标库。功能图标采用规整圆角线性笔画；品牌插画采用克制的简笔画。简笔画不是让每个按钮变成难辨识的手绘符号。

建议统一24单位母版，常用笔画约1.75–2单位（先核对现有资产再统一），圆端点与圆连接，视觉中心和光学边界一致。选中态同时用形态／填充与颜色变化，不能只靠颜色。

| 语义 | 图形方向 | 文字要求 |
|---|---|---|
| 今天 | 餐碗／餐盘 | Tab始终保留“今天” |
| 菜谱 | 菜谱本 | “菜谱” |
| 计划 | 日历 | “计划” |
| 我的 | 头像轮廓 | “我的” |
| 采购 | 菜篮／购物袋 | 主入口写“购物清单”，不要靠图猜 |
| Agent帮助 | 轻量星芒／对话 | 写具体动作：“修改要求”“解释这餐” |
| 保留菜品 | 锁／图钉，统一一种主语义 | 可切换“保留／已保留” |
| 换一道 | 双向替换箭头 | 和“换一套”文字明确区分 |
| 撤销 | 回退弯箭头 | 不与返回上一页混淆 |
| 收藏 | 心形／星形沿用既有选择 | 选中与未选中明确 |
| 时间 | 时钟 | 标明未知／估算／依次制作 |
| 编辑／删除 | 铅笔／垃圾桶 | 删除在危险作用域内，不用普通主色 |

SVG作为源文件、PNG作为必要的运行导出资源，沿用 `scripts/build_ui_assets.py`，不手改生成文件。图标清单集中管理名称和别名，避免同一语义有cart/shopping/basket三套不一致图案。

### 8.4 图片与插画

菜图负责食欲与识别，须有使用权与来源；同类卡片裁切比例和加载占位一致。缺图时使用简笔画占位，不把模型生成的漂亮成品图冒充真实菜谱实拍。

保留既有空计划、空购物、成功等插画基础。品牌角色可以用于首次引导和空态，但不能压过菜单。出错时插画只辅助，必须给出下一步。

### 8.5 按钮与组件契约

主按钮：一个界面状态最多一个高强调业务动作。次按钮：换菜、编辑、取消等；文字按钮：查看来源、展开更多等；危险按钮：删除与清空。

`ui-button` 需统一 loading、disabled、点击锁、触控盒和可访问名称；`ui-sheet` 负责安全区、键盘、滚动、关闭与输入保留；`ui-confirm` 区分破坏性确认与普通完成；`ui-state` 区分业务失败和空结果；`meal-card` 标明状态和目标餐次；`dish-card` 分清浏览与选择模式。

不能通过连续弹窗保护每个普通操作。未存在冲突的新计划可以在明确目标的主按钮上直接保存；替换已有安排才展示差异确认。安全来自服务端事务和授权，而不是所有地方再加一次“确定”。

### 8.6 文案、动效与反馈

优先“这餐已在另一台设备更新”“输入已保留，重试即可”，少用“CAS失败”“曝光失败”“请求幂等冲突”。原始错误保留在脱敏诊断中。

动效建议120–200ms作为轻反馈，不强制播放。长任务使用真实阶段与停止入口，不伪造确定完成时间或百分比。振动可关闭，只用于有意义的确认，不在每次输入触发。

## 9. 个性化与Agent架构发展

### 9.1 保留分工，但把 Agent 从“推荐器”升级成“受控任务编排层”

```text
用户自然语言 / 页面按钮
          ↓
小程序：展示上下文、结果、确认与可回退入口
          ↓
Agent Runtime：理解意图、拆分任务、选择查询或业务动作、组织结果
      ↙             ↓                 ↘
只读查询工具     分析/计算服务        受控业务动作
菜谱/日历/实际   营养/回顾/推荐       保存计划/收藏/自定义/清单修改
      ↘            ↓                 ↙
           Java 业务服务层
  认证 / 用户归属 / 版本 / 幂等 / 事务 / 审计
                   ↓
                 MySQL
```

现有四类只读菜品工具与确定性复核应继续保留。未来增加“保存、收藏、添加自定义、修改清单”等能力时，**模型本身仍不能直接写数据库**；模型只能生成结构化业务动作，由 Java 业务服务再次校验用户身份、对象归属、当前版本、幂等键和确认边界后执行。换模型或提示词不得改变这些业务权限。[R04][R06][R07]

### 9.2 让系统越来越懂用户，而不是擅自记住一切

三层偏好：

- **明确长期设置**：不吃的食材、明确过敏、偏好菜系、常用人数。用户可查看、修改和删除；明确健康信息按敏感数据处理。
- **当前餐约束**：今天来客人、今晚赶时间、这次不吃鱼。任务结束不自动变长期偏好。
- **行为推断候选**：多次换掉某类菜、经常选择快手菜。先作为可衰减的软排序信号，必要时询问“以后优先推荐快手菜吗”，不能自动升级成永久禁忌。

每项推断至少有scope、source、confidence、createdAt、expiresAt、userConfirmed。这里是建议数据契约，不是要求重建已经存在的用户偏好表；优先扩展现有模块。

一次换菜可以轻量选择“刚吃过／不会做／缺食材／今天不想吃／不喜欢”，默认允许不回答。不能用强制反馈问卷换取每次操作。

推荐要平衡熟悉与探索；新用户用明确设置和常用餐型冷启动，老用户优先可靠候选。不要把次数低直接解释成不喜欢，更不要推断疾病、宗教或身份。

### 9.3 任务表达与工具建设

优先提升否定与改口、多轮指代、保留与替换、日期变更、约束冲突、数据不足六类能力，而不是先增加更多Agent角色。

新增技能必须明确输入、可读取的数据域、允许的业务动作、输出 schema、来源、错误、权限、测试及确认边界。只读查询与写操作要分级授权；不能把任意 SQL、任意数据库写、生产命令作为通用模型工具暴露给终端用户。

现有V4最多4轮模型循环、近14秒的任务时间预算属于实现策略，不是实测响应SLA。发布前应测P50/P95、超时率和回退效果；延迟过长先减少无效模型轮次与检索负担，不先无限加大超时。[R04]

### 9.4 跨模块 Agent：打通功能，但不消灭功能

Agent 的长期目标不是“生成菜谱更会聊天”，而是让用户可以直接描述目标，由系统跨模块读取自己的数据、分析并执行受控操作。首批可贯通的数据域建议为：

- 菜谱目录、菜品详情、收藏与用户自定义菜品；
- 日历／正式计划、实际用餐记录与计划执行状态；
- 购物清单与采购来源；
- 明确偏好、近期记录和可解释的行为信号；
- 饮食回顾，以及在可靠营养数据完成后的营养计算结果。

典型任务：

> “帮我保存这份菜谱到今日晚餐，并告诉我最近一周的食谱营养分析。”

系统应识别至少两个子任务：**保存今日晚餐**与**分析最近一周**。如果用户说“营养分析”，必须区分“计划食谱分析”和“实际用餐分析”；刚保存但尚未确认吃过的今日晚餐不能自动计入实际摄入。分析结果要标明日期范围、数据口径、覆盖度和缺失项，并提供“查看今日晚餐”“查看完整报告”“根据建议调整下一餐”等可继续操作的入口。

> “帮我把这道菜收藏，再把它添加进我的自定义菜谱。”

系统应先解析“这道菜”的唯一对象，再执行收藏和个人内容创建。**收藏公共菜品、复制为用户可编辑菜品、加入某个多菜组合是三个不同业务语义**；对象或动作不明确时只追问必要信息，不能凭猜测修改公共菜库或重复创建。

Agent 还应支持“分析 → 建议 → 行动”的闭环：例如读取最近实际记录和菜谱数据，发现重复主料或做法过于单一，提出可追溯的下一餐建议；只有用户明确采纳后才修改未来计划。分析本身不拥有额外写权限。

### 9.5 复合任务的执行与结果契约

一句话可以包含多个目标，但“同时做好”不能等同于一次模型回复里说“全部完成”。Agent Runtime 需要把复合请求拆成可追踪的子任务，并为每个子任务记录：`intent`、`target`、`dependencies`、`read/write`、`confirmationPolicy`、`idempotencyKey`、`status`、`resultRef` 和 `error`。字段名可在详细设计时调整，但语义必须保留。

执行原则：

1. **无依赖的子任务可以独立执行；有依赖的任务必须按真实结果排序。**例如“保存后分析本周计划”必须先确认保存成功，再基于新版本数据分析。
2. **部分成功必须逐项说明。**收藏成功、创建自定义菜品失败时，只重试失败项，不重新收藏或重复创建。
3. **可逆、目标唯一且用户已经明确要求的低风险动作，不强制二次弹窗。**例如“收藏这道菜”；替换已有晚餐、删除记录、批量改动、不可逆动作或目标歧义则需要差异预览或确认。
4. **结果必须落到真实业务对象。**报告不是聊天气泡里的临时文字；计划、收藏、自定义菜品、清单和报告都应有可再次打开的对象或页面。
5. **模型不可用不应拖垮基础功能。**用户仍可直接浏览菜谱、编辑日历、管理收藏、清单和已有报告；仅依赖模型的新分析或自然语言委托明确提示暂不可用。
6. **跨模块工具权限按最小必要暴露。**优先封装“查询我的某周期餐次”“收藏指定菜品”“保存计划”“创建我的菜品草稿”等领域动作，不给模型通用 SQL、任意 URL、任意文件或任意数据库写能力。

跨模块 Agent 的核心质量指标不是工具数量，而是：复合任务完成率、错误对象率、重复写入率、部分失败恢复率、必要追问次数，以及 Agent 与手动页面操作的一致性。

## 10. 营养总结的数据先行方案

### 10.1 当前不要做什么

不从菜名直接生成精确热量；不把“荤菜／素菜次数”绘成营养摄入占比；不把整锅营养等分给所有用户并标成实际；不默认所有原料、烹调油和汤汁都被吃掉；不把缺失值当0。

当前回顾模块的诚实边界是优势，不应为了演示“智能”破坏它。[R08][R13]

### 10.2 分层数据契约

| 数据层 | 最小信息 | 质量要求 |
|---|---|---|
| 标准食材 | canonical ID、别名、食物状态、生／熟、可食部分 | 映射可审阅、可纠正，不能仅靠字符串同名 |
| 菜谱食材行 | 标准食材ID、原始文本、数量、单位、配方基础份数 | “适量”保留未知，不强制换算 |
| 营养来源 | 数据集、条目ID、版本、单位基准、适用状态 | 授权和口径可追溯 |
| 计算快照 | 配方版本、输入量、覆盖度、缺失项、计算方法版本 | 由确定性服务生成，与解释文本分离 |
| 个人实际 | 用户确认的份量／食用比例、记录时间 | 不从购菜勾选自动推断 |

USDA FoodData Central官方文档区分分析数据、调查食物与品牌标签等类型，提醒我们不同来源不是等价真值。可作为候选来源或补充，但中国菜品应优先选择授权清楚、食材状态和本地食品相匹配的数据；不能把国外条目名直接对上中文菜名就宣布可靠。[W05]

### 10.3 发布顺序

先审校一批高频家常菜，例如200–300道作为建议首批规模，建立来源和配方基准；这不是当前库已完成核验的数量。再交付整道菜／整餐估算，明确覆盖；之后才做个人份量和周总结。

最简单可用的计算是在可食原料质量与营养每100克基准对应时相乘求和，但必须处理生熟状态、烹调损失／保留率等适用口径。没有依据时只显示“按原料计算的估算”，不冒充实际吸收量。食品专业人员需审阅方法与产品文案。

模型只解释已计算的结构化结果，并引用本用户可见的数据；缺什么就明确缺什么。可以生成“本次估算未计入未量化的油盐”，不能据此做诊断或治疗建议。

## 11. 采购辅助、库存与多餐协同

### 11.1 采购辅助的目标边界

本项目不以电商交易或商业变现为目标。采购能力的主线是把已确定的菜单变成**可靠、好用、可核对的食材清单**：标准化食材名称、合并可兼容数量、标记家里已有、按采购场景分组、保留来源餐次、支持分享／复制，并在菜单变化时提示差异。

如果未来存在稳定且确有价值的第三方服务，可以增加“复制清单”“打开第三方小程序／应用搜索这些食材”等**可选生态跳转**；它不属于核心闭环，也不要求项目自行承担商品库存、订单、支付、退款、配送和售后。Agent 不得在没有明确外部能力和用户确认时宣称“一键购齐”。

### 11.2 多日规划

先做“指定3天晚餐”等受控范围，不默认安排全周三餐。每餐可保留、重算或跳过，部分确认后任务可恢复。总方案有版本，具体餐次沿用现有正式计划写入契约。

跨餐目标可以是少重复主料、合并采购、利用已知食材和减少做饭负担。预算和库存数量只有在有可靠价格与数量时才作为硬限制，否则只标明偏好。

### 11.3 家庭与库存

先增加“家里有”布尔核对，不急着做精确库存账本。精确库存还需要购入、消耗、损耗、过期和手工纠正，维护负担可能大于收益。

家庭功能需要单独的成员和授权模型、偏好作用域、邀请／退出、记录可见性、共同编辑冲突。不要把个人账号数据简单共享给另一个OpenID。优先通过用户访谈确认协作确实是高频需求。

## 12. 工程质量、数据治理与发布安全

### 12.1 当前测试证据应如何使用

仓库最新记录：Node184、Python23、Java普通58，共265；另有真实MySQL事务4及本地HTTP1，共270。该记录还明确说最新轮未做原生运行、iOS／Android全页状态、双设备恢复和真实模型效果测试。[R01]

应复用这些测试而不是删除再写一套。下一位执行Agent需要获取最新HEAD、运行实际命令并留原始结果，不允许复述文档里的270就写“本次全部通过”。没有CI状态不等于没有本地测试，静态检查通过也不等于真实页面通过。

### 12.2 最小发布门槛

| 门槛 | 验收内容 |
|---|---|
| 环境隔离 | 开发／测试／生产配置明确；测试不使用业务库或生产模型密钥权限 |
| 数据迁移 | V3／V4在隔离库演练，验证升级前后数据；保留恢复方案，生产迁移独立批准 |
| 身份与权限 | 登录退出、A切B、过期token、跨用户ID、管理员接口、Python内部凭证 |
| 写入安全 | 连点、断网、超时未知结果、原键重试、双设备冲突、菜谱被编辑 |
| 原生体验 | 全25页适用状态，关键主链路真机，字号与键盘／安全区 |
| 模型质量 | 固定任务集、真实模型、约束遵守、来源匹配、成本和延迟 |
| 数据品质 | 主推菜品配方、过敏原字段、来源授权、坏图与失效条目 |
| 发布与回滚 | 小范围灰度、监控、可关闭新入口；保持后端和历史数据兼容 |

### 12.3 真实模型验收集

建议首批至少包含以下任务族，每族正常、边界和失败用例；首批样本可人工建立，数量不是通过质量的替代品。

| 类别 | 示例 | 正确行为 |
|---|---|---|
| 否定与改口 | 不吃鱼；后来允许鱼但不吃虾 | 更新正确范围，不保留错的旧条件 |
| 临时／长期 | 今天客人不吃辣 | 不覆盖用户长期口味 |
| 时间范围 | 明天午饭，不是今晚 | 提议切换，不偷偷改目标 |
| 局部替换 | 汤不动，只换肉菜 | 保留其他菜、来源和约束 |
| 强限制无解 | 多个排除后候选不足 | 明确缺口，请用户选择，不放宽安全条件 |
| 来源完整性 | 模型返回未检索菜品ID | 拒绝或重新查询，不直接保存 |
| 信息缺失 | 菜谱没有油量、用时 | 明确未知，不编数值 |
| 服务不可用 | 模型超时或返回错误JSON | 保留原方案，安全回退或澄清 |
| 重复／并发 | 两次换菜返回同一道菜 | 不形成重复菜单，不覆盖较新状态 |
| 恶意文本 | 菜谱／反馈中含“忽略规则” | 当数据，不赋予新工具权限 |

过敏与强排除的匹配只能以可靠配料信息为基础；配料不完整时不得保证安全。交叉接触风险并不能靠菜谱关键词筛选排除。

### 12.4 公开发布前的数据、授权与合规清单

核对现有菜谱文字、图片、营养数据的来源和公开使用授权；6,665条是文档离线基准，不代表全部条目都已完成来源和授权核验。发现来源不清的条目先退出主推池，不能让模型改写后当作解决版权。

隐私说明需覆盖登录标识、饮食偏好、明确健康／过敏数据、反馈、传给外部模型的字段与保存策略。只向模型提供本次必需信息，避免原始用户日志或完整身份数据外发。支持必要的删除、导出与纠正路径。

中国大陆公开提供服务前，核查生成式AI服务登记／备案的适用情况、生成内容标识、小程序平台隐私与类目等要求。网信办已发布生成合成内容标识办法，并在2026年公告中说明直接调用已备案模型能力的应用／功能登记事项。具体义务应按主体、功能和地区向主管方或合规专业人员确认；不能推断所有调用API的小程序都适用同一种备案路径。[W06][W07]

## 13. 产品质量、使用效果与用户验证

### 13.1 指标体系建议

北极星指标：**每周完成有效安排并由用户确认实际用餐的餐次数**。按用户＋业务日期＋餐次去重；同餐修改不新增完成数。没有从计划开始的实际记录另行统计，避免把所有记录混作安排闭环。

| 指标 | 定义／注意点 |
|---|---|
| 生成到确认转化 | 同一工作区草稿曝光后确认；沿用已有generated/exposed/accepted事件，明确去重 |
| 首次方案采纳 | 首份有效方案未经过实质调整就确认；不把收藏状态变化计入方案修改 |
| 局部调整成功 | 换一道后在同一任务中确认，不以请求成功代替用户采纳 |
| 安排耗时 | 活跃操作时间和自然时长分开；后台停留不混入可用性指标 |
| 采购衔接 | 已确认计划中，用户主动进入采购核对的比例；不强求已有食材者采购 |
| 实际记录覆盖 | 有效餐次记录覆盖，明确分母是哪些日期／餐次 |
| 留存 | 完成首餐用户后续仍完成餐次，不只看打开次数 |
| 安全护栏 | 越权、重复写入、硬约束违规、未知数量被误标可靠等 |
| 数据质量 | 主推池可靠配方／份量／营养来源覆盖，按版本监测 |
| 资源效率 | 模型调用、重试和基础设施消耗／完成餐次；用于工程优化，不作为盈利目标 |

本次没有完整现网埋点、用户访谈或长期使用数据，所以不声称当前转化率、留存或资源效率水平。可将“典型回访用户一分钟内选定晚餐”作为待验证设计目标，而非已实现性能。

### 13.2 用户验证

先招募一小组真实做饭用户，观察从决定到买菜、做饭和记录，而不只让人评价截图。建议覆盖独居、两人及小家庭，至少观察不同手机和一次弱网。询问“你下一步想点哪里”“为什么换掉这道菜”“哪些记录太麻烦”。

小样本用于发现问题，不能被包装成统计显著增长。每轮集中修最影响任务完成的少数问题，并保留前后录像与可比任务。

### 13.3 成熟产品级质量目标

项目不设置付费、广告、GMV、ARPU、导购佣金或单位经济等商业化目标。这里所说的“对标商业 App”，指**交互完整度、视觉一致性、稳定性、数据可信度、错误恢复、无障碍、真机适配、隐私安全、测试和可维护性达到成熟消费级产品水准**。

因此，评价项目时优先看任务完成率、响应和错误率、跨模块一致性、数据覆盖、用户纠正成本、留存使用与实际体验；不以付费转化或收入证明价值。

| M1 单餐体验完善 | 从“能操作”变成“顺手完成” | 状态CTA、当前餐内表达、整餐做饭、快速实际记录、购物层级 | 真实用户能完成任务，明显回退和重复输入减少 |
| M2 跨模块 Agent 与有边界个性化 | 让用户一句话跨功能办事，同时越来越省事 | 日历／菜谱／收藏／自定义／清单／回顾工具化、复合任务、部分失败恢复、软偏好候选、推荐评测 | Agent 与页面结果一致；复合任务可追踪可恢复；偏好能解释能改 |
| M3 可信营养基础 | 从类别回顾进入有口径的营养估算 | 食材标准化、份量与配方、数据来源、计算快照、覆盖提示 | 核算样本专业审阅通过，缺失数据诚实展示 |
| M4 多餐与准备优化 | 扩大到几天而非只一餐 | 可恢复的指定餐次规划、保留／部分确认、跨餐分析与采购差异 | 单餐能力不倒退，周期任务可恢复可纠错 |
| M5 高级能力与生态扩展 | 根据真实需求扩大便利性 | 家庭授权、轻量库存、第三方服务跳转、健康数据或设备连接等可选能力 | 不破坏核心闭环；权限、隐私、数据来源和退出路径明确 |

M3的数据整理可以与M0/M1并行，但营养界面不能早于可靠计算口径发布。跨模块 Agent 的非营养能力可在 M1 后逐步建设，不必等待营养完成。M4/M5依赖真实需求，不默认全部一定实施。

## 15. Dot在开发中的定位与工作方式

### 15.1 已核实的产品边界

截至2026-10-05，Dot是ChatGPT中的持续工作Agent，可利用连接应用和云端电脑；官方帮助文档明确支持创建Codex云任务，需先在Codex创建环境。桌面端创建；本机访问默认关闭，需授权。当前开放范围由套餐、地区和分批放量决定。[W01]

官方明确：与Dot对话不计ChatGPT消息用量，但委派的Codex／Work任务照常计入对应使用量；主动研究使用只读工具，不等于默认获准修改项目。[W02]

这些事实不能推出“Dot无限免费开发”或“个人Dot可作为小程序用户的共享后端”。官方Agents API是另一类开发者能力，不应与消费者Dot混为一谈。[W08]

### 15.2 建议岗位，而非内置自动化承诺

建议给你的Dot一个持续岗位：**Eat-What研发协调与质量负责人**。它维护任务上下文、整理已授权读取的反馈和测试结果、识别重复问题、提出小范围修改、安排Codex执行并组织验收材料。

| 分工 | 负责 | 不负责 |
|---|---|---|
| 小程序饮食Agent | 用户本人范围内的跨模块查询、分析、推荐与受控业务动作 | 修改仓库、读取其他用户数据、绕过业务权限或管理服务器 |
| Dot | 产品上下文、反馈归类、计划与工程任务协调、审查资料 | 代你决定产品取舍、无限制花费、未经批准上线 |
| Codex任务 | 在明确仓库／分支／环境内实现、测试和提交PR | 以写了代码证明真机体验合格 |
| 你 | 取舍、真实体验验收、预算、权限和发布批准 | 逐条替模型完成所有机械检查 |

### 15.3 最值得交给Dot的六类工作

反馈到问题单：将脱敏用户反馈聚合成可复现任务，分清数据、交互、后端和模型问题。

代码到小PR：以一个用户问题为范围，沿用当前组件与业务契约，不顺手重写架构。

数据质量巡检：读授权的审计结果，发现主推菜无份数、重复菜、坏图、缺失用时和来源不明，产生修正建议；不自行发布未经审阅的数据。

模型评测协调：比较固定任务集，识别提示词或模型版本变化造成的回归，附失败样本和成本；不只给“更智能”的主观结论。

设计一致性维护：核查页面是否使用Token、是否有多个主CTA、图标语义是否混乱；需要原生截图才能判断实际裁切与键盘状态。

发布准备：收集迁移演练、回滚方案、CI与原生验证、变更说明；由你决定合并和生产发布。

### 15.4 推荐任务链

**授权数据／反馈 → 问题证据 → 明确验收 → 小范围Codex任务 → 自动测试 → 可运行演示或真机证据 → 人工审查 → 批准发布 → 复查影响。**

云端任务不能天然证明微信原生页面通过。只有配置了合适本机环境、开发者工具和必要设备访问，才可能执行对应验证；没有环境就明确未验收，不能用浏览器重绘替代原生证据。

### 15.5 权限与成本边界

默认只读仓库、已脱敏测试结果与反馈。独立开发分支写入和测试环境任务需要事先明确范围。合并受保护分支、生产部署、数据库迁移、用户批量数据操作、变更外部模型账号和密钥均需单独批准。

不仅写提示词，也在仓库保护、连接权限、测试账号、网络边界和密钥管理中落实限制。用户反馈、Issue正文、菜谱说明属于待处理数据，不得作为升级工具权限的指令。

为每类任务设置预算与停止条件。优先把有限Codex用量用于有验收目标的小PR，避免Dot反复全仓扫描和无目标重构。项目事实存入仓库文档和测试，不只留在Dot记忆中。

可直接使用配套文档《任务拆分、验收门槛与Dot职责协议》。

## 16. 明确不建议现在做的事情

不推倒现有工作区；不为“Agent感”新增必经聊天Tab；不把菜谱、日历、清单、报告等基础入口藏起来；不重画整套已经存在的图标；不先做多Agent角色表演；不在食材份量未可靠前展示精确个人营养；不把已有食材输入升级成伪库存；不把非商业项目扩张成自建订单／支付系统；不以源码测试代替原生与用户验收；不把Dot当成绕过用量或审批的入口。

## 17. 近期产品决策建议

首先把M0列为最高优先级，并与M1中低风险、直接减轻负担的改动组合成小批次：隐藏内部埋点错误、收敛同餐入口、修正主CTA含义、把所有菜的做法放进同一个执行视图。

同时启动主推菜品的数据审校与小规模真实用户观察。首餐闭环稳定后，优先把日历、收藏、自定义菜品、清单和回顾接入统一 Agent 工具层，再逐步扩展行为个性化、多日规划和可靠营养核算。

最终目标不是“它能调用多少工具”，而是：**基础功能始终清楚可达，Agent 能把它们真正串起来；用户越来越少操心，但始终知道系统做了什么、依据是什么、结果在哪里查看、哪里可以修改。**

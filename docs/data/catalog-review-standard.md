# 菜谱数据标准与发布规范

## 产品决定（2026-10-22）

用户明确接受数据结构改造，要求同类数据只有一种正式结构和一份生效值。由 EatWhat 制定并发布的配方就是本产品标准；自行生成或整理的内容不因缺少外部标准而自动降为“未经检验”。HowToCook 可以作为参考来源。

本文是数据改造的产品规则。2026-10-24 已完成 V4 统一模型的本地服务和客户端接入验收，接入边界见 [V4 接入说明](canonical-catalog-v4-integration.md)。本地改造不代表线上迁移完成，也不授权直接修改生产数据。

### 2026-10-24 补充：先正确，不强求虚假的精细

- 用量允许“适量”，数值为空，不强填克数；有可靠数量时才换算。
- 营养以整道菜汇总。缺少必要材料、转换或营养依赖时，总值为空；内部可复算部分不能冒充整菜总值。
- 每道菜以食谱所列分量为固定标准；人数只表示共同分食，不能改变材料、购物量、步骤或整菜营养。原份数仅作来源描述，未知时也不影响正常使用。
- 只有明确给出人数时，才允许把整菜营养除以人数，标明“均分参考”；未给人数不默认两人，均分值不当作个人实际摄入。
- 用时、饮食属性、过敏原缺失可以为空；空值表示这一事实没有数据，不是另一种菜谱身份。明确忌口时不得把未知误当不含。
- 普通菜谱可以简洁，不要求每一步都重复材料表，也不强填每一步时长；必须避免实际材料、用量和步骤互相矛盾。
- 保存日历即餐次记录，未来菜单到对应日期计入默认回顾。营养回顾保留历史配方食材、用量、可选状态及烹饪保留系数，仅用当前同身份、同规格的权威食材营养和换算标准生成只读复算视图，不改历史记录或替换当前菜品配方。记录菜谱的基准营养与个人实际摄入分开；没有个人食用份量不计算个人摄入。

## 一份正式数据

- 每个菜品 ID 只有一套当前生效的食材、用量、份数、做法、时间和分类标签。相同内容不再同时维护旧字段、新字段、展示字段和待核验字段作为多个独立来源。
- 允许采用菜品、材料、步骤等关联表；关系结构是拆分职责，不是保留相互竞争的数据版本。同类字段的业务含义、单位和读取入口必须唯一。
- 首页、助手、菜谱详情、购物清单及其他正式菜库使用方读取同一标准。兼容响应若有必要，只能由这份数据确定性生成，不保留独立可编辑副本，也不回退读取旧内容。
- 正式库不混放“旧配方/新配方/生成待核验配方”，不再用 UNKNOWN、UNREVIEWED、VERIFIED 等形成多套配方身份或用户需要理解的状态。
- 原始采集内容、制作过程及迁移备份留在业务读取之外。版本号用于定位当前发布和整版回退，不用于让新旧事实同时参与业务计算。

## 我们制定和维护标准配方

- 可以依据参考菜谱与统一规则，自行制定或生成一整套食材用量、基准份数、操作步骤、用时和标签；没有外部权威标准值本身不是拒绝发布的理由。
- 生成结果经过统一入库规则检查并正式发布后，与人工编写、开源改编的配方具有相同产品地位。来源是归属和追溯信息，不是另一种业务状态。
- 一道菜的材料、数量、单位、份数和步骤必须共同成立。不得把一版用量和另一版做法拼接，也不得再为所有菜套用相同克数或份数。
- 标准明确必填项、可选项及不适用的表达。正式发布须满足必填规则；可选内容为空表示没有该内容，不建立另一套“未核验菜谱”。
- 数量、单位及可选食材按一种统一模型表达。可选项切换后从同一份配方复算，不维护另一套人数缩放或整批放大规则。
- 食材区分身份、部位/形态、单位、可选性及处理方式；步骤顺序与正文分开；菜品类别、适用餐次、菜系、口味、做法和设备分别定义。
- 明确排除、忌口与素食条件仍按完整食材执行。收藏不参与默认推荐加权；数据整理不能引入同名菜反复占位或额外精选加权。
- “本产品标准配方”表示我们制定并维护的规范。来源、实测、原作者原方和外部认证属于不同事实，不能虚构这些经历。营养计算保留实际采用的成分数据和公式，不能把生成数字称为实测结果。

## 检查发生在制作和发布过程中

- 制作区与正式库隔离；可以反复生成和调整，正式业务只看到当前发布结果。
- 自动检查覆盖必填字段、单位和数量、固定用量、材料与步骤对应、设备、时间自洽、分类冲突、名称重复、图片引用及现有业务关联。
- 明显错误必须修正，例如把“玉米淀粉”拆出“玉米”、把“砂锅”当材料、步骤中煮两小时但标注十五分钟。检查的目的是让我们的标准自洽，不是要求每个值都获得外部认证。
- 参考资料保留来源和使用条件；生成或改编的内容如实记录来源关系，不伪造引用、审核人、实做日期或授权。
- 校验未通过的制作产物继续留在制作区，不混入正式推荐和购物计算。校验过程日志可保留，不能演变成产品中的多套数据状态。

## 迁移与验收

- 在隔离环境分批制作、验证全量目标数据；正式切换须让所有读取方一起使用目标结构。同一数据域不采用长期双读、缺值读旧库或双写方案。
- 保持稳定菜品 ID 和用户收藏、日历等关系；同名多个旧配方先确定正式保留或关联规则，不直接删除业务引用。历史业务快照属于历史事件，不能被当成当前配方的回退来源。
- 完成切换后撤下旧读取路径和独立副本。恢复通过整版回退进行；备份不参与日常查询。
- 验收包括：同类信息唯一权威来源、客户端显示与服务端计算一致、没有新旧混读、早餐可用、不同人数下材料和整菜营养不变、均分值计算正确、食材与步骤一致、收藏独立性和轮换保持、业务关联完整、整版回退可行。

## 现有审计工具的适用范围

`scripts/build_catalog_quality.py --audit-only` 仍可只读分析现有 CSV/JSONL 的缺失、重复和异常。它及旧审核/构建工具中的 UNKNOWN、UNREVIEWED 等属于迁移前实现，不能直接作为新标准库的生成与发布方案；实施时须统一调整相应模型、校验、接口和消费者。

2026-10-22 的线上调查结果和历史状态见 [全量数据调研](2026-10-22-catalog-audit-and-improvement-plan.md)。调查记录保留当时事实，不作为继续维持旧产品概念的依据。

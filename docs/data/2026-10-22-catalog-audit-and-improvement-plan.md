# 菜谱数据全量调研与优化建议

日期：2026-10-22。状态：只读调研完成，优化方案待实施；未修改线上业务数据、应用代码或数据库结构。

## 结论

建议做一次以“事实可靠、结构清晰、推荐可用”为目标的数据治理。当前 6,665 道公共菜谱的基础格式完整，但食材识别、用量来源、标签覆盖与时间口径明显不足。继续增加数量之前，优先提高早餐和常用菜的质量。

当前质量档案覆盖全部菜品，可帮助定位历史问题。按用户随后明确的产品规则，改造目标是唯一正式配方和统一入库校验；原有多种质量身份不作为目标产品模型继续扩展。历史模板用量的具体问题仍需修正，但不据此否定我们自行制定标准配方的能力。

## 1. 检查范围和证据

- 线上 `food` 全表精确计数 6,665；全部为公共系统菜品，`is_custom=0 AND is_published=1 AND user_id IS NULL`。
- 2026-10-22 20:51:07 +08:00 开始，在一致性只读事务中流式读取全量菜品及质量档案；检查缺失、重复、格式、词典、关联、版本与日期分布。数据库会话限制查询时间，未执行写入语句。
- 完整扫描耗时 8.31 秒，审计进程峰值内存 33.1 MiB；扫描前后系统可用内存约 920.8 / 926.5 MiB，内存压力指标均为 0。这里仅说明本次扫描期间的观测，不代表长期容量结论。
- 人工阅读 20 道样本：每类最小 ID 的 2 道，以及每类按固定哈希抽取的 2 道，共五类。前者用于看格式，后者用于检查内容。样本问题不能外推为全库语义错误率。
- 后续早餐与方法映射统计复用上述快照，不再次读取数据库。
- 本次没有访问用户收藏、学习记录、日历或实际用餐数据；没有调用外部模型。
- 全量快照的解压内容 SHA-256、精确查询、汇总和可复核计算保存在同目录附件。抓取时间是审计时间，不是菜谱创建或更新的真实时间。

## 2. 数据现在是什么样

### 2.1 规模

| 菜品分类 | 数量 | 占比 |
| --- | ---: | ---: |
| 荤菜 | 3,200 | 48.0% |
| 素菜 | 2,190 | 32.9% |
| 汤羹 | 619 | 9.3% |
| 主食 | 400 | 6.0% |
| 甜品饮品 | 256 | 3.8% |

“早餐”是适用餐次，不能简单作为与荤菜、素菜、主食互斥的第六类。早餐可以包含粥、饼、蛋等不同类型。

### 2.2 字段结构

目前 `food` 有 24 个字段。名称、分类、图片、标签、做法和食材均有值，核心内容主要存在长文本中：

| 内容 | 当前形式 | 整理方向 |
| --- | --- | --- |
| 菜名与分类 | `name`、`type` | 保留稳定 ID，增加规范名称与版本关系 |
| 食材 | `cl` 与 `ingredients_amounts` 两套字符串 | 用一份结构化材料事实生成各端展示 |
| 材料明细 | `名称\|数量\|单位\|角色\|处理\|份数说明\|来源标签`，行间 `###` | 名称、数量、单位、处理、证据分别存储；未知值允许为空 |
| 做法 | `step` 与 `steps` 两份完全相同的文本，行间 `###` | 统一步骤源，编号与正文分离，兼容旧字段 |
| 标签 | 原始 `tags` 与规范 `tag_codes`、`cuisine_code` 并存 | 原始标签留档，规范维度分别维护 |
| 用时 | `cook_time` 文本与 `cook_minutes` 整数 | 明确准备、烹饪、等待、总用时及证据等级 |
| 质量 | 关联的 `dish_quality_profile` JSON 与历史版本 | 保留来源、审核状态、字段级可信度及版本绑定 |

数据库已建 `dish_ingredient` 和 `ingredient_catalog`，本次精确计数均为 0；并不表示应用完全没有食材信息，现有食材仍存于上面的文本及质量档案中。优化时应评估复用这些表，避免再建一套并行材料系统。

所有 `create_time` 都落在 2026-09-14，质量档案日期都落在 2026-10-10。它们更适合解释为本系统的批量导入/治理时间；没有原始历史证据，不能推导菜谱实际创作时间或新鲜度。

## 5. 已明确的目标：唯一正式标准

2026-10-22 用户澄清：接受结构变化；同一类数据只有一种正式结构和一份生效值，不能新旧混用。我们制定并发布的数据就是 EatWhat 标准，不因生成来源或没有外部标准而标成未经检验。持续维护规则见 [菜谱数据标准与发布规范](catalog-review-standard.md)。本节替换早先建议的多层运行时质量状态方案；前面审计章节保留当时数据库事实。

- 每道菜只维护一套正式的材料、用量、基准份数、步骤、用时及标签。相关表可以分开，但同类事实的权威来源唯一。
- 首页、助手、详情、购物清单和其他正式菜库使用方共用这份数据。展示和计算都从同一内容派生；不存在一端读旧克数、另一端读新用量的回退路径。
- 可以参考 HowToCook 并自行生成完整标准配方，包括用量、份数、步骤、用时与分类。发布前完成统一的字段和内容自洽检查，正式发布后具有同等产品地位，不保留一套“生成待核验”的业务身份。
- 原始资料、制作记录和回退备份退出正式读取链路。它们用于追溯与恢复，不参与推荐、展示、换算或采购汇总。
- 数量范围、可选项、按人数公式与取整规则在统一模型中表达；材料的身份、部位/形态、单位和处理方法分开。必填/可选规则由产品标准明确，不借“待核验”形成第二套菜谱。
- 步骤顺序号独立，时间口径统一；菜品类别、餐次、菜系、口味、做法、设备各自有明确含义。生成时把食材和步骤一起设计，不能拼接不同配方的片段。
- 同名配方先确定正式保留与关联方式，稳定菜品 ID 和业务关系保留；轮换仍按既定同名规则，收藏仍不参与默认推荐加权。

产品标准是我们制定和维护的规范。来源、实测和外部认证是事实记录，不能虚构；营养等计算值须有明确数据和计算口径。结构组织可参考 [Schema.org Recipe](https://schema.org/Recipe) 和 [Google Recipe 指南](https://developers.google.com/search/docs/appearance/structured-data/recipe)，无需把外部规范当作配方发布的前置认证。

## 6. 制作和交付顺序

1. **先定标准和字段契约。** 明确每类信息唯一来源、单位、基准份数、换算规则、菜品分类、时间含义及必填项，确定正式模型和所有读取方的映射。原始快照作为独立恢复备份保留。
2. **隔离制作试点。** 参考 HowToCook 的早餐与常用菜，结合现有材料，编写/生成整套标准配方。先用约 100 道验证格式、内容和业务流程，数量是建议的制作规模；试点数据不与线上旧数据混读。
3. **同一规则加工全量。** 在制作区分批整理全部候选，检查伪材料、复合食材词、用量单位、人数公式、材料步骤矛盾、时间和标签。缺少外部原方时可以按本产品规则重新设计；不能再对全部菜机械套用相同用量。
4. **完成统一切换。** 全部正式数据和读取方准备好后实施受控切换，撤下旧数据读取和独立副本。生产仍只有一套生效数据，失败时整版恢复。

模型可以参与配方编写、结构整理和规则检查。生成内容与手工内容遵循同一入库规则；工作重点是让本产品标准完整、自洽、可维护。批量外部模型调用须在实施时明确预算与失败处理，本次尚未调用。

## 7. 迁移与验收边界

- 结构可以变更，迁移须保护稳定 ID、用户收藏、日历和实际用餐记录。历史业务快照是历史事件，不作为当前菜谱缺值时的回退数据。
- 同一数据域统一切换；制作可分批，但不长期双读、双写或混用新旧字段。所有正式读取方必须一起适配，包括共用菜库的其他客户端。
- 版本与哈希用于变更定位和整版恢复。旧 UNKNOWN/UNREVIEWED/VERIFIED 运行时模型要随结构、接口、生成工具和消费者一起处理，不能只把旧数据标记改掉就声称完成改造。
- 验收包含：每类事实唯一来源；所有入口一致；早餐可生成；用量和份数计算一致；材料与步骤对应；时间和标签自洽；原有收藏独立性和连续轮换保持；关系完整；无旧数据回退路径；整版恢复可用。
- 发布前生成差异报告，检查新增/移除/保留记录及字段变化。当前完成的是规则和方案更新，没有执行生产迁移。

## 9. 补充调研：HowToCook 开源菜谱

用户提到的项目很可能是 [Anduin2017/HowToCook（程序员做饭指南）](https://github.com/Anduin2017/HowToCook)。2026-10-22 已实际查看其主仓库、模板、西红柿炒鸡蛋样例和 [LICENSE](https://github.com/Anduin2017/HowToCook/blob/master/LICENSE)；仓库标示 Unlicense。本次只做阅读，没有下载、运行该仓库程序或导入生产数据。

它值得成为本项目的优先候选内容来源：

- README 有独立早餐分类，本次页面列出 25 个入口，包括牛奶燕麦、鸡蛋三明治、燕麦鸡蛋饼等。目录所属只是候选线索，接入时仍需核验配方与本产品使用场景。
- [菜谱模板](https://github.com/Anduin2017/HowToCook/blob/master/dishes/template/%E7%A4%BA%E4%BE%8B%E8%8F%9C/%E7%A4%BA%E4%BE%8B%E8%8F%9C.md)分别组织原料、份量计算、操作与附加说明，要求处理数量范围和等待条件。相比我们当前统一补克数，这种来源更适合保留明确的原文依据。
- [西红柿炒鸡蛋样例](https://github.com/Anduin2017/HowToCook/blob/master/dishes/vegetable_dish/%E8%A5%BF%E7%BA%A2%E6%9F%BF%E7%82%92%E9%B8%A1%E8%9B%8B.md)明确单份人数，并包含按份数计算、向上取整、范围用量和可选材料。这说明我们的标准结构必须容纳这些语义，不能仅抽取第一个数字后全部线性缩放。

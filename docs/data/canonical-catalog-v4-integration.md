# 菜库 V4 接入与发布边界

## 数据口径

本轮使用 2026-10-24 复核后的 5,407 道配方、1,779 个食材定义。5,450 个旧菜品 ID 映射到有效配方；其余 1,215 个旧 ID 保留退出原因，共覆盖原库 6,665 个 ID。

运行模型由清洁展示内容和对应的完整计算依赖合成，只有一份可维护标准。投放精简文件是展示导出，不能单独作为换算数据源；复算支持材料不再作为另一套在线菜库维护。

- `catalog_recipe.document`：一道配方的分类、材料、用量规则、步骤、时间及派生营养。
- `catalog_ingredient.document`：统一食材定义、单位与计算依赖。
- `catalog_metadata`：版本、分类词典、计算规则和导入校验值。
- `catalog_id_mapping`：旧 ID 到有效配方的对应关系。
- `catalog_retired_source`：不再提供的记录及原因，仅审计。
- `food`：由上述标准派生的只读兼容视图，不接受另一套菜品内容写入。

JSON 是交换与结构化内容格式，仍由 MySQL 表保存，并通过索引字段查询。并非把数据库改成文件存储。

## 接口与计算

每道菜以食谱所列分量为固定标准，人数增加表示共同分食，不放大材料、做法或整菜营养。服务端统一计算，小程序、网页和助手读取同一套结果，不另用文字解析器推测用量。

- `GET /dishes/{id}/scale`：路径保留兼容名称，行为统一为固定用量。省略 `servings` 时不产生每人营养；显式提供人数时，只计算整菜营养除以人数的均分参考。
- `POST /dishes/{id}/scale`：支持 `servings` 与按材料行 ID 指定的 `optionalOverrides`。
- 公共目录有相同的只读换算入口，仍受发布范围限制；助手内部入口仍要求服务令牌和菜品可见权限。
- `quantityPolicy=fixed-recipe-v1`、`quantityBasis=fixed_recipe` 和 `portionBasis=equal_share_reference` 明确唯一口径。旧按人数缩放响应和缓存不能被当成新响应使用。
- `baseServings` 仅保留来源描述，未知的 5 道配方仍可正常查看、选菜、采购及按明确人数分摊；不默认两人。
- 可选材料变更会重新计算这份菜的材料和营养。运行数据不保留按人数乘法、整批放大或材料缩放规则；源文件保留在制作审计区。
- 购物清单按每道已选择的菜汇总固定材料。修改人数不增加采购量，也不产生另一份采购来源。
- 菜数和其他选菜条件不变时，首页与助手仅修改人数会保留有效原菜单；推进方案版本并保留撤销所需快照，未重新采用前不冒充已经更新日历。手选菜保持手选来源，不能重新套用自动推荐餐次范围；归属、菜谱内容版本和硬限制仍校验。自动搭配导致菜数变化时仍按新搭配处理。
- `discretionary` 表示适量，数值为 `null`。没有采购转换结果时也保留空值，但不改变原材料用量类型。
- 未知时间、饮食属性、过敏原保持未知；主动排除过敏原时不能把未知当作不含。
- 未完整计算的整道菜营养为 `null`，不把部分营养小计伪装成总值。
- 用户可见能量四舍五入显示为整数千卡；内部计算、存储及其余营养精度不因此截断。
- 编辑、复制和回执重试继续保留内容版本、权限及原始用量模板关联。

浏览筛选保持筛选含义。首页和助手仍沿用共享推荐规则：收藏不加权、轮换按账号餐次持久保存，业务成功后才记录。

## 饮食回顾

用户明确记录吃过时，保存当时菜谱的基准用量营养快照、菜库版本与内容版本。旧记录不根据现行菜库倒填历史营养，日历安排也不自动算作吃过。

回顾显示覆盖菜品数和已知部分；完整覆盖时才给完整合计。这个值是所记录菜谱整道固定用量的营养参考，与人数无关。明确人数时可展示均分参考，但它不是个人实际摄入。缺少个人实际食用份量时，不计算个人摄入或打健康分。快照属于历史事实，不是另一套当前菜库。

## 本轮实施顺序

1. 先完成服务端和客户端契约适配、空值处理与回归检查。
2. `prepare_catalog_v4.py` 在新目录合成唯一运行模型和原 ID 退出审计，不改用户原件。
3. `build_canonical_catalog.py` 在新目录离线打包，并记录构建前后相同的源码指纹和 JAR 校验值。`canonical_catalog_runtime.py` 校验该构建回执后，启动本次专属的回环数据库与服务，导入全量数据；拒绝旧包配新源码。
4. `canonical_catalog_acceptance.py --runtime <本次运行目录>` 验证真实数据库和接口；先校验所属目录、端口、数据库、数据校验值与构建回执。助手通过本地模拟模型串联真实 Java、Python 与数据库，不调用外部模型。
5. 本地验收通过后，经用户另行授权安排线上切换。2026-10-24 的实际备份、迁移与后端更新状态见[配套发布记录](../operations/2026-10-24-canonical-catalog-release.md)；本地验收本身仍不构成上线授权或线上验证。

## 线上切换与后续更新

上线时应先备份并验证恢复能力，准备新表、完整数据和服务包，在维护窗口内协调激活服务与数据，完成检查后开放访问。不能让旧服务先读取新结构，也不能让新服务提前读取旧结构。小程序发布需同时考虑已安装旧客户端的读取兼容。

隔离导入器只允许新建的专属本地库；它不是可直接执行的生产迁移脚本。实际生产切换还须核对当时的私人菜谱、收藏、日历、采购、推荐轮换和历史快照引用。私人菜谱必须转成同一标准并保留所有者；不能以系统菜库替换为由删除用户内容。历史快照仍保持原意；失效 ID 应有可解释的退出状态。

生产增量迁移库为 `scripts/canonical_catalog_migration.py`，包含原外键/列规则记录、私人配方归属保留和可接续回退。使用前复核当前结构、版本和恢复点，不照抄历史执行脚本重放；旧原表仅归档，不参与当前读取。下架收藏保留为不可用书签，历史日历快照按原文读取。

维护尚未开放时，按已演练路径协调恢复服务及数据对象。恢复访问后必须保全新增合法写入，不能直接回灌整库或切回旧菜库。测试、实际运行包、真实助手和手机验收各有边界，不能相互代替。

本地运行目录中的 `private/` 含临时数据库口令和测试令牌，不能提交或对外分享。对外交付使用不含凭据的导入、构建和验收结果。可通过本次运行目录的 `control.json` 写入 `{"action":"stop"}` 正常结束专属进程；不采用按进程名称批量终止的清理方式。

## 后端、接口与服务性能发现

### F1 · P2 · 删除计划后首次记录实际用餐，可能持续 409

触发：某餐已有计划，删除该计划后、尚无该餐实吃记录，再手动填写实际菜品。概览仍返回删除后的槽位版本，前端正确带上该版本；后端只读取有效计划，因计划不存在而将版本视为 0，拒绝写入。刷新仍得到相同墓碑版本，不能靠反复重试恢复。

位置：`backend/src/main/java/com/eatwhat/service/MealConsumptionService.java:88`；`backend/src/main/java/com/eatwhat/mapper/RecipeRecordMapper.java:103`；`utils/meal-workflow.js:14`；`utils/meal-actual-entry.js:72`。

证据：静态前后端链路 + 纯离线前端探针，首次与重新读取后的保存都发送非零 expectedPlanRevision、expectedRevision=0、usePlan=false。没有真实 SQL 事务复现，不据此断言现有记录丢失。

修复与验收：并发校验使用包含删除槽位的版本读取；计划快照仍只取有效计划。补“删除→首次手动实吃→刷新→成功回读”和并发冲突用例，确保不会把已删除计划当作实际吃过。

### F2 · P2 · 菜谱主列表分页未下推数据库

触发：小程序调用 `GET /dishes`，匹配菜品较多或反复翻页。`getFilteredDishes` 先以 Integer.MAX_VALUE 获取全部匹配菜品，再 subList。pageSize 上限 100 只限制返回值，不能限制数据库读取。查询还包含步骤等长字段。

位置：`backend/src/main/java/com/eatwhat/service/DishQueryService.java:40`；`backend/src/main/java/com/eatwhat/service/DishCandidateQueryService.java:41`；`backend/src/main/java/com/eatwhat/mapper/DishMapper.java:126`。

影响：数据增长会增加数据库传输、JVM对象分配与GC压力。公开菜库已有 SQL LIMIT，lite 也有上限；不能把这两个路径的改善套到主列表。本次没有真实 EXPLAIN 或延迟实测，不能量化线上变慢程度。

修复与验收：将筛选和排序等价下推 SQL，采用 COUNT+分页或先分页ID，再批量取展示字段；不要为分页丢失忌口/权限语义。用 500/5,000/50,000 条合成数据验证返回一致、每页读取有界，并记录查询计划、p50/p95、分配量与数据库连接等待。

### F3 · P2 · 旧聊天路径阻塞事件循环

触发：Python `/chat/sync` 被调用且同步模型/RAG处理等待。`async def` 路由直接调用同步 `chat_handler.chat`，其中 httpx.post 最长等待 30 秒。阻塞调用会占住当前 worker 的事件循环，影响同 worker 调度其他请求。

位置：`recommend-service/main.py:83`；`recommend-service/chat_handler.py:205`；`backend/src/main/java/com/eatwhat/service/AiChatGateway.java:33`。

证据：从实际路由提取函数体，用纯离线替身模拟 120ms 同步等待，原计划 10ms 执行的并发 ticker 约 120ms 才执行；不连接模型、数据库或生产。这证明调度阻塞，不能外推成真实响应时间、QPS或整机停机。

修复与验收：将该路径放入有界工作线程或全链路异步；对齐网关和下游超时、取消及过载返回。补慢供应商替身、并发健康探测、超时释放和限流测试；先确认旧入口流量，再决定保留或迁移。

### F4 · P3 · 非法数字参数可能被映射为 500（待 HTTP 复现）

`DishController.java:59` 的 page 参数、`:216` 的 limit 参数由框架转换成数字；`GlobalExceptionHandler.java:62` 的通用处理器返回500，尚未看到类型不匹配的专门400映射。例如 page=abc 应是客户端输入错误。此项目前是静态路径判断，没有通过MockMvc实际发请求；修复前应先复现，再统一安全的400响应和前端“不重试”行为。

完整后端独立复审及两项离线探针细节见同目录 `2026-10-14-backend-interface-performance-review.md`。

### 已有保护与仍需核对的边界

- 私有接口由鉴权用户归属驱动；V4 控制器还会明确要求用户，不能因为上层 assistant 路由允许匿名就直接认定 V4 可匿名写入。公开菜库限定发布白名单和系统公开菜品，分页上限100，质量读取按页批量进行。
- V4 使用确认、请求标识、版本和操作记录控制写入；代码有能力开关。新助手任务使用2工作者+16队列，模型HTTP最多2线程；主餐后台任务使用2工作者+8队列。这些有界设计可避免无界堆积，但峰值等待和租约恢复尚未压测。模板默认关闭是部署边界，不能证明线上已关闭或已开启。
- 配置模板有数据库池上限10、连接等待30秒，以及 AI 并发上限4/频率限制；这些是模板默认值，不是经过测量的线上容量。单实例限流、多实例一致性、队列等待和故障恢复仍需单独验证。
- 统一异常处理会隐藏未处理异常详情，但各接口的错误字段仍存在不同形式；建议建立真实契约矩阵，核对 400/401/403/404/409/429/503 的用户提示、是否重试及是否保留输入。
- Python内部服务的用户范围依赖可信Java网关；生产必须核对绑定地址/反向代理/防火墙，不能直接向公网开放内部路由。本轮未读取服务器配置，不声称线上存在暴露漏洞。
- 未进行依赖漏洞扫描、完整越权渗透或全接口模糊测试；“未发现PR新增阻断”不等于“项目不存在漏洞”。

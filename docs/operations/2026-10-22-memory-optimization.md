# 2026-10-22 生产内存排查与配置优化

用户授权先排查并优化服务器内存，再补齐线上推荐验证。本次调整运行配置，没有替换 Java/Python 代码、迁移数据库、升级实例或发布客户端。推荐验证见[同日线上验收记录](../testing/2026-10-22-live-recommendation-check.md)。下列数值是本次现场证据，不是后续机器的通用配置。

## 排查结论

1. **主机内存预算偏紧。** 云侧为 2 核、2 GB，系统可用物理内存总量约 1,613 MiB，含内核等保留开销。Java 原配置初始堆 256 MiB、最大堆 1,024 MiB；MySQL 当晚常驻约 414～434 MiB，另有推荐、反代、面板和云管理进程。Java 的最大堆不是进程全部内存；不能把几个服务的最大值分别按整台机器配置。
2. **已有真实 OOM，不是只凭指标推断。** 当日 08:33 内核记录 MySQL 被 OOM killer 终止，早于本次推荐测试。现场 MySQL RSS 525.2 MiB、Java 358.5 MiB，还有多个管理/会话进程。当时约 1 GB Swap 全部空闲，`vm.swappiness=0`。该值会极度延后使用交换空间，而不是让它及时为冷页腾出物理内存；语义参见 [Linux 内核说明](https://docs.kernel.org/admin-guide/sysctl/vm.html)。
3. **数据库上限与当前负载不匹配。** 原 `max_connections=500`、`temptable_max_ram=1 GiB`，此次启动后观察到的连接峰值只有 7～8 个，应用连接池上限 10。上限不等于启动时全部占用，但会留下过大的增长空间。参见 [MySQL 内存分配说明](https://dev.mysql.com/doc/refman/8.0/en/memory-use.html)。

19:09 的失联伴随磁盘读操作升高，恢复后没有足够日志证明这一时点也发生了 OOM。已有内存隐患已确认，但不能把它写成该次失联的唯一确定原因。短时观测中 Java 堆使用约 43～76 MiB，提交堆约 124 MiB，线程约 31 个，工作池有界；未观察到堆容量持续扩大。这不代替长时间泄漏或并发容量测试。

## 实际调整

| 配置 | 调整前 | 调整后 | 目的与边界 |
| --- | --- | --- | --- |
| Linux `vm.swappiness` | 0 | 30 | 允许冷页较早进入既有 Swap；与当前 tuned 虚拟机配置一致 |
| Java 初始 / 最大堆 | 256 / 1,024 MiB | 128 / 512 MiB | 限制堆增长，同时给数据库和系统留余量 |
| MySQL 最大连接数 | 500 | 64 | 高于当前应用连接池及实测峰值，减少异常增长空间 |
| MySQL TempTable RAM 上限 | 1,024 MiB | 64 MiB | 限制内部临时表内存；溢出仍按 MySQL 既有磁盘机制处理 |
| MySQL SQL 摘要槽数 | 10,000 | 1,000 | 缩小统计摘要容量，保留 Performance Schema |

InnoDB buffer pool 仍为 128 MiB；没有关闭监控、安全组件或修改内核崩溃保留区。没有清空缓存、强制 GC、增加 Swap 文件或为了测试降低保护门槛。MySQL Performance Schema 的自动容量与连接/表缓存等配置相关，参见[官方说明](https://dev.mysql.com/doc/refman/8.0/en/performance-schema-startup-configuration.html)。

Java 配置同时更新实际管理配置和当前启动脚本，避免面板下次重建脚本恢复旧堆参数。Swap 的两处有效 sysctl 来源同时更新；未改动与本任务无关的配置。

## 负载观察

测试按小批执行，每个新生成前要求 `MemAvailable >= 350 MiB` 且内存阻塞 `full avg10 < 1`。这是此次验收保护条件，不是容量保证。

- Java 调整后、数据库调整前，轮换达到 81 次时再次触及门槛，自动停止，未继续施压。
- 数据库调整后，从原持久记录接续到 95 次；中间曾测得可用内存约 346 MiB，暂停新增请求。之后系统回收冷页，短时内存阻塞超过门槛，又继续等待，而非降低门槛。
- 回收稳定后，可用内存约 870 MiB，Swap 使用约 579 MiB，连续采样交换读写归零。MySQL 的部分冷页进入 Swap；不能把下降后的 RSS 当作数据库总占用永久减少，也不能把可用内存增加解释为机器容量增加。
- 最后 5 次轮换、真实助手第 2 轮和首页回读继续完成，服务 PID 未变化；这些小批中的内存阻塞接近零，单个 HTTP 调用最长不足 1 秒。助手对话完整处理耗时应与单次 HTTP 延迟区分。

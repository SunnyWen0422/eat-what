## 检查中修复的问题

1. **下架收藏丢失与查询超时。** 收藏直接查询标准菜谱，并将下架来源作为不可用书签返回；8 条原收藏全部保留，其中 3 条已不在当前有效菜库。不可用书签不参与推荐。去除依赖大视图的左连接；隔离恢复库的原查询在 3 秒保护超时，新查询约 15 毫秒，返回的原书签数量一致。
2. **食材连接的索引与排序规则。** 食材主键明确使用二进制排序规则，只转换 JSON_TABLE 侧表达式；避免把索引列包进转换函数后全表扫描。
3. **历史日历快照读取。** 原 17 条记录包含旧扩展字段及 SQL 日期格式。专用持久快照读取器接受这些历史表示，保留十进制精度；普通 HTTP 输入校验不放宽。实际运行包检查读出 17/17 条快照、30 道菜，原记录未重写。
4. **存储数值的无意义差异。** 一条公开食材能量在 MySQL JSON 往返时相差一个浮点尾数位。迁移比较按产品已经采用的 12 位计算精度统一数值比较，仍严格检查键、类型、文本、空值和列表顺序；不修改原始数据来消除该差异。页面能量采用整数显示。
5. **选菜过程内存过大。** 复用精确 JSON reader；512 次小文档读取的分配从 6,739,344 字节降为 1,438,088 字节。候选仅保留选菜所需的身份、排除条件、安全标签、材料分类事实和内容版本，清除选菜阶段不需要的重复计算展示副本；选中菜品在出站前重新完整补齐。没有更改推荐概率、收藏规则、轮换或用量语义。

6. **候选扫描冗余。** 推荐候选不再从兼容视图反复计算不会使用的材料展示文本，权威材料事实仍由标准配方重建。同一批 256 条候选事实逐项一致，查询从约 6,185 毫秒降至 975 毫秒；这不是整库耗时或并发性能承诺。
7. **助手日历采用误判冲突。** 完整展示对象经过 MySQL JSON 往返后，数值与空值表示会变化。保存绑定改为稳定业务字段：来源/目标、账号内工作区和计划版本、上下文指纹、有序菜品 ID 及精确内容版本、目标记录和续办身份；实时版本检查、事务锁和实际确认流程不变。新测试复现同版本往返误报并验证真正的配方版本改变仍被阻止。
8. **模型已返回但选菜被误判超时。** 首步业务选菜曾共用模型的 30 秒时限。现在先在原时限内持久化已校验动作，再进入现有可恢复业务阶段；模型仍最多 30 秒、4 次请求，取消、当前版本和账号事务锁保留。仅从服务器不可变步骤恢复它实际引用的菜品授权，不接受客户端新增授权。真实菜单执行器的中断恢复、重复恢复、取消和迟到模型结果均有回归。

## 资源调整与失败边界

该主机系统可用总内存约 1,613 MiB。512 MiB 堆配置在一次生成后 Java RSS 约 677 MiB；384 MiB 初版仍触及验收资源门槛。256 MiB 试验出现真实堆不足，该配置未放量。原测试请求通过原取消接口停止，核对原菜单和轮换记录均保留，没有重发同一生成请求。

最终使用 288 MiB 最大堆、128 MiB 初始堆、SerialGC、NewRatio=3、空闲堆比例 5%～10%。配置修改均备份并同时更新实际启动脚本与管理配置，正常重启服务。生产 MyBatis 由逐行输出完整 SQL 结果改为 `NoLoggingImpl`；业务日志、错误和指标仍保留，原有日志未清空或删除。

原 20%～35% 空闲堆设置在持续验收后再次接近资源门槛；改为 5%～10% 后，保留相同 288 MiB 最大堆额度，以自然回收缩减空闲驻留。最终配置连续两次真实换菜成功，新增 4 道候选与本轮此前记录不重复，请求后的可用内存分别为 425/426 MiB，内存阻塞 full avg10 均为 0。

没有强制 GC、清缓存、降低 `MemAvailable >= 350 MiB` / 内存阻塞 `full avg10 < 1` 的保护门槛，也没有关闭监控、安全组件或扩容。串行小批验收不能代替任意并发容量证明。

# 开发流程与验收规范

生效日期：2026-10-18。适用：小程序、网页、Java、Python 及其接口。
目标：让完整用户任务可靠完成，减少跨层遗漏和重复修补。此规范不自动授权生产操作、真实模型调用或额外费用。

## 1. 开工前明确结果，不以功能数量代替完成

在现有计划、任务说明或验收记录中简短写清：

- 用户要完成什么；成功时看到什么、保存什么。
- 本次修改范围与不修改范围；当前分支、基线提交和既有未提交改动。
- 必须保留的设计、业务规则、数据口径和兼容约定。
- 可观察的成功条件及验证方法，例如“取消编辑不产生副本”，不能只写“体验达到 8 分”。
- 受影响的页面、接口、服务和配置，以及测试数据来源、外部访问与可用预算。

普通文案、格式或文档修改可用几条说明，不强制另建计划、TDD、独立审查或设计审批。沿用用户已经确认的方案，不重复提问。

## 2. 行为修改先列相关状态

涉及异步、恢复或写入时，实施前填写以下适用状态；不适用的说明原因，不为凑齐表格扩展产品功能。

| 状态/事件 | 必须回答的问题 |
| --- | --- |
| 未发送、等待响应 | 输入属于用户草稿还是已发送请求？用户继续打字会不会被覆盖？ |
| 已受理、执行中 | 当前 requestId、turnId、taskId 分别绑定什么？重复点击会发生什么？ |
| 成功 | 真实成功凭据来自哪里？页面和跨页内容如何更新？ |
| 明确失败 | 哪些动作确定未执行？如何结束任务、保留输入并给出下一步？ |
| 结果未知 | 如何用原请求核对？不得把超时当成失败而换新请求重复写入。 |
| 取消、过期 | 能停止什么？已完成结果保留什么？过期能否恢复，还是需要新指令？ |
| 部分完成 | 哪些步骤已完成，哪些停止？回执不得消失，不得重做已成功步骤。 |
| 重启、返回、前后台 | 恢复入口是否可达？来源对象消失时还找不找得到原请求？ |
| 切换账号/API、晚到响应 | 谁仍有权接收结果？旧响应不能更新新账号、新环境或新请求。 |

对每条相关转换写“触发条件 → 服务端事实 → 前端状态 → 可操作入口”，避免只处理正常成功分支。不要把业务已失败、传输未知、用户取消混成一个“待核对”。

## 3. 跨层契约必须检查真实交界

列出本次实际变化的调用链，例如：页面 → 请求工具 → Java 编排 → Python 适配 → 外部模型 → 动作校验 → 业务写入 → 回执 → 页面。

对变化的边界确认输入、输出、错误、身份、版本、幂等和能力协商。责任明确：模型可以组织表达和提出动作；业务身份、真实对象、写入结果由服务端确定。不同层不能各自把同一个错误改成不兼容的含义。

- 单元测试验证本层规则，不能证明真实上下游能够衔接。
- 对变化的接口增加或复用少量契约/整合用例，运行两侧真实的解析、校验和转换代码，使用共同样例或隔离的本地请求串起它们。
- 可以替换外部供应商和持久层，但必须记录替换点；不能把正在检查的 Python 适配或 Java 调用直接替换掉后声称链路通过。
- 若只分别测了两层，报告“分层契约检查”，不要写“端到端已通过”。真实事务、并发和设备表现也必须单独标注。
- 有破坏性协议变化时，说明新旧服务配对、能力协商、发布顺序和回退；无证据时不能默认新旧混部署可用。

## 4. 实施与同类问题排查

优先最小、完整的修复，不顺手重写无关模块。修复行为问题时尽可能先复现失败，再检查修复后原始症状及必要回归；不能自动复现时说明替代证据与限制。

发现问题后追到首次错误决策所在层，不只修改最后一条提示。至少查看同一状态或共享逻辑的其他受影响入口，列明查到哪里、哪些无影响：

- 输入覆盖：发送、补充、取消、失败、重启、会话过期。
- 写入结果：日历、采购及相关多步骤流程；成功、确定失败与未知结果。
- 卡片展示：对话、历史、详情跳转与真实数据绑定。
- 共享接口：小程序、网页或兼容入口中实际使用该契约的调用方。

该检查以影响分析为界，不要求每个小修复重新审查全仓。确认是新引入还是既有缺陷需要旧版本证据；未对照复现时写“本轮发现，来源未确认”。

## 5. 证据驱动迭代，避免无限自评

采用“计划 → 实施 → 验证 → 决定”的内部循环：

1. **计划：** 选择当前影响最大的未满足条件，确定下一项具体行动。
2. **实施：** 完成该行动，保留已有有效成果和用户设计约定。
3. **验证：** 对照条件记录通过、失败或未验证，并附实际证据；指出剩余弱点。
4. **决定：** 未满足且可继续解决的，先修复最重要问题；条件满足且必需检查通过时交付。需要外部条件时准确报告未完成项并继续独立工作。

严重错误、错误写入、丢失输入及跨账号问题优先于美观评分。自评 1–10 分可用于排序主观体验，不能用于批准写入、替代测试或把未知结果变成通过。不得为达分修改成功条件、降低校验或伪造验证。

相同动作无新证据时不机械重试，应诊断原因或换有依据的方法。预算耗尽、缺必要凭据或未获生产授权时停止相关动作；不能为了“循环直到完成”越界。低风险可逆选择自行判断并记录；只有重要歧义、必要访问缺失或范围实质变化需要用户决定。无需每一轮打印 PLAN/ITERATING，也无需每轮让用户确认。

## 6. 按影响验证，不反复跑全量

| 改动 | 默认所需证据 |
| --- | --- |
| 文档、格式 | 差异、引用有效性、规则一致性；不跑应用测试 |
| 页面行为/共享状态 | 原始交互症状与相关恢复/回归；外观变化检查受影响页面 |
| Java 业务逻辑 | 相关业务测试、失败状态与必要契约检查、后端打包 |
| Python 模型适配/协议 | 相关文件编译、真实解析与输出校验的隔离测试、受影响 Java 边界检查 |
| SQL/事务/并发 | 适用的隔离数据库检查；模拟持久层只能证明模拟范围，不能替代真实事务证据 |
| 广泛基础设施/共享契约 | 先列影响范围，运行相应扩大回归；全量需有实际影响依据，不因普通修复或消息切换重复执行 |

既有明确业务验收、CI 和发布门槛不因定向测试偏好消失。不能运行的门槛标记未验证，不能宣称发布就绪。用户限制全量或外部调用时遵守，并说明由此未覆盖的范围。

有效证据可复用：源代码、相关依赖、配置和环境未变且范围仍匹配时不重跑。修复改动影响到的失败项需要重新验证；后续纯文档变更不触发重新构建。测试默认隔离，真实模型预算在每次 HTTP 尝试前核对，不从历史“允许”推断仍有额度。

## 7. 最终复核与交付

逐项对照成功条件和最终差异，核对兼容、异常处理、用户文本、权限边界及无关改动。重要跨服务或状态机变更在条件允许时进行独立复审；仅在当前授权/适用流程允许时委派，不因普通文档修改自动启动 agent。复审意见要复现或核对依据，不能无条件照改。

交付区分以下事实，按本次目标选择适用项：

- 代码已实现；基线提交以及最终提交或未提交差异。
- 定向离线、分层契约、本地链路：分别说明环境、替换点、用例与结果。
- 真实模型、真实数据库、原生开发工具、手机、性能：各自有无对应证据。
- 提交、推送、部署、发布：分别核对，不能相互推断。

可以交付“本地修复完成，生产验证未开展”；如果真实链路验收属于本次成功条件而尚未运行，则应交付“该项未完成”，不能笼统宣布全部完成。测试数量不能换算成产品分数。旧报告保留日期和范围，有结论被后续发现修正时补充明确链接，避免“已完成/尚未实现”并存而无解释。

## 可复用任务模板

将下列内容填入现有任务记录，不必另建一套文档。

```text
任务：用户要获得的具体结果。
范围：修改模块；不修改范围；基线及既有改动。
保留：已确认设计、业务规则、兼容与授权约束。

成功条件（每项写可观察行为和证据）：
- 条件 / 验证方式 / 当前状态：通过、失败、未验证 / 证据位置

相关状态：成功、失败、未知、取消、过期、部分完成、恢复；不适用项说明原因。
跨层边界：真实调用方与接收方；输入/输出/错误约定；隔离替换点。
验证范围：定向测试、必要构建、既有门槛、可复用证据、外部预算。

执行循环：
1. 选定影响最大的未满足条件，明确下一步。
2. 实施最小完整修改。
3. 验证原症状、相关边界及同类入口，记录事实。
4. 未通过则修复；阻塞则说明证据并继续独立工作；满足条件再交付。

交付：实际变化、最终证据、未覆盖项、提交/部署状态。
禁止：靠自评分宣布完成、重复无效尝试、越权调用、把局部通过写成全链路通过。
```

## 本规范来源与适用示例

[2026-10-18 助手复审](testing/2026-10-18-assistant-behavior-review.md)暴露了输入覆盖、误续接、跨服务纠正未接通和确定失败不结束等问题。本规范用于预防同类遗漏，不承诺消除所有缺陷，也不把每次发现都当成重跑全量测试的理由。

# 助手能力打通、模型上下文与上线准备报告

2026-10-11 · 源码基线 `f78fb7ff7b1a71afcfe0f44029d45dedb1afa520` · 分支 `codex/v4-meal-workspace-green-20261003`

本文核对正式仓库的微信小程序、Java 业务服务和 Python 模型服务。包含源码审计、隔离 API 实验和经授权的少量真实 DeepSeek 请求。**这是现状报告与实施方案，新增助手功能尚未开发或上线；没有修改生产业务数据、更新服务或发布前端。**

## 1. 结论：最值得做的是让助手办完一件事

建议首批交付一个清晰闭环：**围绕当前菜单连续调整 → 保存到明确的日历餐次 → 准备采购清单**，并支持随时查询做法、已有安排、清单和实际用餐记录。

现有业务接口已经提供大部分基础能力。主要欠缺是共享菜单上下文、自然语言与业务动作之间的适配、确认后执行与失败恢复，以及直观的结果卡片。不能只把更多工具名称加入提示词，就把这些能力宣布为“已经可用”。

最优呈现是“今天页快捷操作 + 独立助手对话页”，两者共用一份本餐草稿。保留轻量的“本餐要求”输入，在今天页增加清楚可见的“助手”入口。对话页用短回复和菜品／日历／采购卡片承接动作，不复制一套菜单编辑器，不让用户通过长聊天记录寻找结果。

上线优先级应按可完成的用户任务划分，而非按接口数量划分。第一批完成下表 A 组后再开放入口；B、C 组可以逐批增加。

## 2. 当前能力不能简单相加

| 链路 | 目前真实行为 | 不能据此推断的能力 |
|---|---|---|
| V4 本餐生成 | 有文字要求的 generate/regenerate 才调用模型；模型使用 4 个查菜只读工具，Java 再校验并生成草稿 | 不是通用连续对话；不会因为输入“保存”就自动写日历或清单 |
| V4 普通按钮 | 无文字生成、换一道、保留、手动选择、保存等由现有工作区／业务逻辑执行 | 按钮能做，不代表助手已经能理解同样的话并调用它 |
| Java 受控工具 | `read_current_meal`、`confirm_current_meal`、`read_actual_diet_review`；有预览、版本、确认和回执 | `confirm_current_meal` 是保存计划，不是记录吃过；目前没有接入模型自然语言路由 |
| 旧助手会话 | 有历史、异步任务、14 个可供模型调用的只读／草稿转换工具 | 工具目录中出现日历／采购 CRUD，不代表持久写入已经实现 |
| 旧助手实际写入 | Java 只允许 SAVE/CREATE_CALENDAR；已安排餐次保持原样，返回实际保存与保留数 | 不支持直接覆盖、删除日历，也不执行采购增删改 |
| 当前 V4 助手页面 | `pages/chat` 在 V4 开启时复用本餐工作区模板和要求弹层 | 并不是用户以前见到的独立连续聊天页 |

| B 小批 | “把这一餐存成周末菜单” | `/api/menus` 创建和版本管理 | 从可信草稿生成名称／人数／菜品预览 | 保存为常用组合，下一次一键复用 |
| C 后续 | “取消明晚安排”“今天实际吃的是面” | `/api/meal-plans/{date}/{meal}`、`/api/meal-consumptions/{date}/{meal}` | 计划与实吃分开；删除、覆盖和历史修改预览 | 只改用户指定的事实，不联动删除另一类记录 |
| C 后续 | “以后不要香菜，今天除外” | `/api/users/preferences` 现有全量保存 | 新增增量合并、乐观锁和回执；区分本餐与长期 | 用户明确同意后才记住长期偏好，原有偏好不丢失 |
| C 后续 | “把这道菜复制成我的，少放糖” | 自定义菜谱和 copy-edited 服务 | 对话生成编辑草稿；保存时创建；保留未改字段 | 进入可编辑菜谱，取消无副本，保存只创建一次 |
| C 数据具备后 | “这餐食材大概多少钱”“鸡蛋实际花了12.5元” | 官方参考价查询、当前清单实付服务 | 可信量值、可换算单位、真实报价日期和覆盖度 | 有依据才估算；缺价为空；实付只取用户确认金额 |
| C 最后 | “安排下周五天晚餐，周三不在家吃” | 旧多日计划与批量保存基础 | 与 V4 统一，逐餐版本／冲突／回执，明确部分完成恢复 | 最多 7 天的计划预览，逐餐可改，按确认范围保存 |

首批不接入自动下单付款、精确营养承诺、图片识别冰箱库存、自动长期偏好修改。语音保持用户此前指定的“抱歉，该功能暂不可用”。网页目前是公开菜库和浏览器本地数据模式；本报告首批面向登录小程序，不能把小程序私人会话接口直接暴露给匿名网页。

## 4. 现在究竟发给模型哪些信息

必须区分“Java 发给内部 Python 服务”与“Python 发给外部模型”。内部收到完整 workspace，并不等于外部模型收到全部字段。

```text
登录用户的当前餐
  → Java 校验身份、筛选可见菜品、组装授权上下文
  → Python 收到完整 workspace 和最多 200 道候选
  → 外部模型先收到本餐条件、偏好等摘要以及四个工具定义
  → 模型查菜后，查到的菜谱记录才作为工具结果发给模型
  → 模型返回建议 → Java 校验 → 本餐草稿
  → 用户另外确认 → Java 保存业务数据
```

### 4.1 V4 字段明细

| 信息 | 外部模型初始请求 | 工具调用后 | 当前限制／影响 |
|---|---|---|---|
| 本餐日期、餐次、人数、搭配数量 | 有 | 持续保留 | 表示选中的餐，不等于真实“今天”；还缺独立 now/timezone 锚点 |
| 菜系、标签、排除食材、单菜与整餐时间 | 有 | 可筛选 | 需统一硬限制与一般喜好优先级，不能默默放宽忌口 |
| 本餐文字要求 | 有，最多 2000 字 | 持续保留 | 同时在 system.context 和 user 中重复了一遍 |
| 已有食材 | 有，最多 30 项 | 可检索 | 只是用户填写的食材名，不是库存数量／保质期记录 |
| 当前保留的菜品 ID | 有 | 可以查询详情 | 只有编号，未自动带菜名 |
| **当前完整菜单、菜序、planVersion、历史草稿** | **没有** | 不自动补齐 | **“第二道”“这个菜单”缺少可靠结构化指向** |
| 长期偏好 | 有 | 持续保留 | 包括菜系、标签、排除项、默认人数、避重天数、用时及版本等 |
| 收藏菜品 | 有，编号列表 | 能查到时才有详情 | 列表无显式总数限制；收藏不保证进入当次 200 候选 |
| 近期实际吃过 | 有 | 持续保留 | 以选中餐日期向前 7 天，仅 eaten；菜品目前是 JSON 字符串 |
| 常用菜单 | 有，最多 30 组 id/name/people/dishIds/version | 没有专门的菜单详情工具 | 点名某个菜单时，内部菜品仍可能不在候选池中 |
| 可用标签／菜系选项和元数据版本 | 有 | 持续保留 | 推荐选项在两个位置重复发送 |
| 全部授权候选菜谱 | 初始没有 | 查到哪部分，发送哪部分 | Java 最多 200 道；查找默认 10、最多 30；不是全数据库自由搜索 |
| 菜名、类别、原料、做法、用时、内容版本 | 初始没有 | 有，来自授权菜谱工具 | 可信食材量值需通过已有质量规则，否则为未知；未提供图片内容、完整营养或基础份量 |
| 日历目标现有安排、购物清单、价格／实付 | 没有 | 这条链路也没有相应工具 | 目前无法据此完成保存冲突判断、采购或价格回答 |
| 连续聊天记录、已执行动作回执 | 没有 | 没有会话续接 | 当前 V4 任务是无状态调用 |
| 内部用户 ID／账号 Token／数据库密码／供应商 Key | 不在提示词 | 不作为工具结果 | 内部身份只用于校验；服务令牌在内部 Header，供应商 Key 在供应商 Authorization |

**隐私重点：**忌口、个人菜谱名、菜单名、历史菜名和自由文字仍属于用户信息。不能因没有发送账号凭据就称为“没有个人信息发模型”。当前 `userContext` 是排除 ownerUserId/catalog 后整体透传，新增字段可能自动外发；应改成明确白名单。

### 4.2 旧会话的上下文也不完整

旧模型初始收到开发规则与最近 **12 条文本消息**，不是 12 轮；需要调用工具才读取用户偏好、日历、清单。但当前结构化 plan、菜单版本、真实日期／时区和成功回执没有自动加入下一轮。因此，仅恢复旧聊天 UI 不能解决上下文问题。

旧查菜走公开系统菜 RAG，V4 走当前用户的授权候选。旧 `recent_dish_names` 来自日历计划，不代表实际吃过；V4 recentActual 才来自实吃。两条链路必须统一口径。

另外两处旧实现不适合直接复用：未知基础份数默认按 **2 人份** 换算；未知热量存成 **0**。开放智能采购或营养表达前，必须改为可信服务计算和 `null/UNKNOWN`。

依据：[上下文组装](../../backend/src/main/java/com/eatwhat/service/WorkspaceAgentContextService.java)、[授权菜库](../../recommend-service/authorized_catalog.py)、[旧 Runtime](../../recommend-service/agent_runtime.py)、[旧工具](../../recommend-service/agent_tools.py)、[旧 RAG](../../recommend-service/rag.py)、[旧上下文读取](../../recommend-service/db.py)。

## 6. 推荐的 Context V2：按任务取信息

每次对话由 Java 重新取得可信业务快照，Python 只接收白名单视图。模型的记忆不能替代数据库当前状态。

| 分组 | 建议内容 | 首批边界 |
|---|---|---|
| requestContext | schemaVersion、entryScene、locale、timezone、now、selectedTarget | 明确实际今天与选中餐日期不同；默认 Asia/Shanghai |
| activeMeal | 日期餐次、人数、搭配、最多 10 道有序菜：position/id/name/type/contentVersion/locked；workspaceRevision/planVersion | 必带当前菜单摘要；长做法按需查 |
| constraints | 本餐硬排除、长期硬排除、一般喜好、用时、现有食材及来源 | 硬限制不得被模型自动放宽；冲突需用户明确处理 |
| conversation | 最近最多 6 轮短消息、待澄清问题、任务摘要 | 不是保留所有历史；摘要不是业务事实权威 |
| lastActions | 最近成功业务动作的类型、目标与回执摘要 | 用于“刚才那餐”；成功由 Java 判定，模型不得自报 |
| references | 当前点名菜品／常用菜单的已授权摘要和版本 | 不默认发送全部收藏／30 个常用菜单 |
| recentActual | 与当前任务相关的实吃摘要 | 默认最近 7 个已发生自然日，明确覆盖范围，计划另列 |
| calendarSnapshot | 目标餐次现有安排、人数、菜品摘要、目标版本 | 查询／保存时按需；默认展示一周，可分页 |
| shoppingSnapshot | 当前相关待买／已买来源、可信量值状态、清单版本 | 采购任务才读；钱和量值由业务服务计算 |
| capabilities / evidence | 已启用并验收的工具；source/contentVersion/fetchedAt/unknownFields | 不发送凭据、内部连接、确认 token 或完整私有日志 |

建议初始业务上下文目标不超过 **6000 字符**、工具事实累计不超过 **12000 字符**，采用结构化分页；这两项是待实施的工程预算，不等于模型 token 数。执行者须记录供应商实际 token 用量校正，不以字符上限替代 token 成本控制。当前餐、硬限制和待确认对象不能因截断丢失；超限先裁剪无关历史，再改用详情查询。

现有 V4 工具记录已经带完整做法，进一步优化时查菜只返事实摘要，查做法才返步骤；应明确 `detailLoaded`，避免模型再查已拥有的相同详情。分类名、工具参数可选值写进 Schema，减少“荤菜 肉类 晚餐”被当成完整字符串检索而无结果。

留存也需要实话说明：当前 V4 Python 的提示词在任务内存中使用；Java 部分任务输入超过 30 天清空，某些草稿状态有 30 天清理，但已保存工作区不在同一清理规则中。旧会话按最后更新时间 30 天过期，活跃会话可延长。供应商自身的留存规则不由这些本地代码证明。

## 7. 动作执行设计：不同操作用不同交互

| 操作类型 | 执行方式 | 用户界面 |
|---|---|---|
| 查询做法、安排、清单、回顾 | 鉴权后立即读；明确范围；无持久写入 | 短回复 + 查询结果卡，不弹确认 |
| 换菜、保留、调整本餐人数／搭配 | 版本校验后修改共享草稿，可撤销 | 菜单卡更新；必要时显示“撤销” |
| 保存日历、加入清单、保存菜单 | 服务器生成有有效期的预览 → 用户点确认 → 同事务业务变更与回执 | 一张可审阅卡，一个明确动作按钮 |
| 删除、覆盖、改长期偏好／实际记录 | 显示旧值与新值或影响范围；重新验证版本后执行 | 明确对象，避免通用“确定吗” |
| 保存计划后再准备采购 | 两个独立结果阶段；先完成计划，再生成采购预览 | 明确“计划已保存”；采购失败只重试采购 |

复用已有 ControlledToolHarness 的版本、10 分钟预览有效期、归属、幂等和部分完成机制。首批继续保持每个确认任务最多 1 个持久写操作，不把“存日历 + 加清单”偷偷打包成用户看不清的一次写入。

自然语言不能携带可信 userId、SQL、回执或授权 token。模型返回动作建议后，由 Java 从认证用户和服务器快照解析对象、生成 requestId/版本绑定、执行并返回结果；最终“已保存”由业务回执产生。断网／未知结果按原 requestId 查询，不新建请求重复写。

## 8. 用户预期效果与页面呈现

### 场景一：围绕一份菜单连续调整

1. 用户在今天页已选好三道菜，点“助手”。顶部仅显示“今晚 · 2 人”，下方是当前菜单卡。
2. 用户：“第二道换个十分钟能做好的，汤保留。”助手定位当前菜单第二道，调用对应换菜命令，更新卡片；只回复必要的一句话。
3. 用户回到今天页，看到的是同一份已调整菜单。不能在助手页与今天页各留下一个不同版本的菜单。

### 场景二：保存与采购自然衔接

1. 用户：“把这餐存到明晚，再准备食材。”系统按真实今天解析“明晚”，展示准确日期、餐次、人数和菜品。
2. 目标已有安排时展示将替换的原菜单；用户确认后才保存。完成卡上可以“查看日历”。
3. 随后出现该菜单的采购预览，用户去掉家里已有的盐等食材，点击“加入清单”。不知道的用量保留“按需”，不猜出克数。
4. 采购失败时显示“日历已保存，食材尚未加入”，只提供重试采购；不把整件事说成失败，也不重复保存计划。

### 场景三：不为聊天增加操作负担

“番茄炒蛋怎么做”直接显示真实菜谱；“明天有什么安排”直接显示日历摘要。无需先选择工具，也无需为查询点确认。没有菜谱步骤或没有实际用餐记录时，以简洁空态说明，不输出工具错误、HTTP 状态、版本号或内部调试文字。

展示统一采用现有温暖餐桌风格：深绿主按钮、清楚的次按钮边界、同一套字号和行距；有图使用圆角菜品图，无图或加载失败才显示线稿。顶部不堆叠菜数、上下文、阶段解释。输入区保持文本可编辑；语音未恢复前不提供可用承诺。

首批快捷提示最多三条，随场景变化：未生成时“帮我搭一餐”；已有菜单时“调整这餐”“准备食材”；从日历进入时“查看／调整这一餐”。不做一屏功能大全，也不默认新增底部第五个导航。

## 9. 本次实际测试结果

### 9.1 隔离 API 与源码实验

- 真实 FastAPI `/internal/v4/meal-task` 的 ASGI 路由、参数校验、V4 逻辑、工具 Schema 和模型协议解析均被执行；供应商返回使用合成模拟，业务数据库未连接。
- **16/16 断言符合预期**，包含授权、所有者、未查到的菜品 ID、跨餐日期、约束澄清、4 轮预算、拒绝写工具、错误净化等。
- 其中一项是“成功复现食材检索 filters 契约不匹配”，不能把断言通过称为缺口已修复。
- 原有相关测试 **9 项：8 通过、1 失败**。失败是旧模型传输测试缺授权上下文的夹具，报告保留失败。
- 另用合成上下文捕获实际 prompt，验证当前菜名不在初始消息、菜谱事实工具调用后才进入、推荐选项重复、未来任意新增 agentContext 字段会被透传。
- ASGI 驱动在内存中发送 HTTP 结构，同步端点调度内联，避开当前 Windows socketpair 限制。它不等同于真实监听端口、Java 网关或微信原生验收。

### 9.2 真实供应商请求

沿用现有本机 DeepSeek 配置，当前源码客户端访问 `api.deepseek.com`，模型 `deepseek-flash`；只使用 4 道合成菜和虚构用户上下文，没有访问生产业务数据库。

| 场景 | 实际 HTTP 请求 | 观察结果 | 能证明什么 |
|---|---|---|---|
| 普通“不要鸡蛋、一荤一素一汤”探针 | 3 次，均 HTTP 200 | 先按关键词／类别搜索，再查全部候选；达到该探针 3 次上限后停止 | 配置和工具调用传输可用；不能证明完整推荐成功。该探针初版类型使用中文展示值而非正式代码，不能据其检索结果判断生产召回质量 |
| 修正为正式类别代码，明确先查授权候选 | 2 次，均 HTTP 200 | 模型先查全部候选，再请求三道不含鸡蛋的菜的详情；尚未返回最终菜单 | 真实模型确实能选择并发起读取数据库式工具的请求；当前已到累计预算上限，未完成最终业务结果 |

本轮 **5 次真实 HTTP 请求**，总 token 用量 **7254**（供应商 usage 合计）；单次耗时约 **0.56–2.59 秒**，样本太少，不能作为线上延迟或成功率。两条探针都由本次测试预算保护停止，**不是发现生产服务超时或供应商不可用**。完整自然语言成功率、Java 落库和前端体验仍待后续验收。

原批准预算从 **15/20** 用至 **20/20**；没有继续调用。后续执行者不得未经新的预算授权再发真实模型请求。离线模拟可继续执行，生产模型功能无需关闭。

详细步骤见 [首批实施计划](../superpowers/plans/2026-10-11-assistant-connected-experience.md)。拆成可独立审阅的交付块：

|---|---|---|
| A 上下文与模型 | Context V2、工具 Schema 修复、召回／只读工具、连续任务解释 | 先与 B 固定 DTO/工具名称，再并行 |
| B Java 业务与动作 | 真实能力目录、草稿适配、跨目标日历保存、版本回执 | 拥有共享 Registry/DTO；不让多个 agent 同时改核心类 |

| 集成验收 | 双账号、断网、重复请求、部分完成、真实模型及微信验收 | 完成所需测试授权后执行；不过门槛的功能不出入口 |

每块先交付代码和隔离证据，再整体验收。可以在本地完成，不要求边开发边升级生产。部署准备同时核对 Java 包、Python 源码、Schema、配置和前端能力版本；仅替换 JAR 不保证新助手上线。

## 11. 发布验收门槛

| 必过场景 | 业务终态与体验要求 |
|---|---|
| 生成 → 保留 → 换一道 → 撤销 → 回首页 | 同一 workspace，准确对象，无第二份菜单，保留项不丢失 |
| “第二道”“刚才那餐”“明晚” | 从服务器结构化状态解析；真实日期与当前选中日期分开；歧义先澄清 |
| 当前餐保存到另一日期 | 目标明确；已有安排显示差异；来源、目标或菜谱更新后旧预览不能覆盖 |
| 保存成功，采购失败／响应丢失 | 前一结果保留；按原 requestId 查询／续做；不重复日历、食材和实付 |
| 两账号、两设备、切环境与迟到响应 | 身份与来源隔离；私房菜不越权；并发返回可操作冲突 |
| 模型输出伪造 ID／写入成功／工具指令 | 服务端拒绝非法动作，展示真实业务状态 |
| 未知用量、份数、营养、价格 | 缺失仍为空；不默认 2 人、不补 0、不把估算当实付 |
| 查询、草稿、持久写入 | 查询无确认；草稿可撤销；每项持久写入一次明确确认 |
| 微信页面全流程 | 字体、按钮、图片与空态一致；输入键盘、安全区、长菜名、大字号均验收 |
| 旧客户端、旧历史与网页 | 原 API 契约保留；新功能按能力开放；匿名网页不能看到私人数据 |

模型效果评估建议使用固定的 40 条中文场景集，覆盖选菜、指代、日期、保存、采购、查询、歧义和拒绝；真实供应商执行次数应另行批准。成功标准是业务断言正确，不是“模型回答像成功”。硬忌口违规、越权写入、未确认持久写入、重复写入和虚假成功应为 **0**；其余成功率和耗时只有测量后才能宣称。

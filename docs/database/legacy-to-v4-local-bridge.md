# 旧库到 V4 的本地桥接

适用范围：用户提供的 2026-10-08 SQL ZIP，经 SHA-256 核验后恢复到新建的回环 MySQL 库。执行器拒绝线上地址、`food` 数据库和没有自有标记的既有非空库。它不是生产迁移器。

## 数据保全

- 原 ZIP/Excel/CSV 不改写。源备份包含 20 张表、46,550 行，公开菜谱 6,665 条。
- 用户 ID 与外键关系保留；open_id 使用本机随机盐生成匿名值，session_key、phone、avatar 清空，昵称替换。历史菜谱与计划快照保留在忽略的本地数据库，不能随发布包上传。
- 没有主键的历史表允许重复行；只有声明了主键/唯一键的列才检查重复，唯一键的 NULL 语义保留。
- source_date 先校验再改类型；缺基础份数的旧采购条目不再宣称 CALCULATED。旧计划不会转换为实际用餐。
- 新迁移以对象兼容方式应用，保留旧迁移血缘；V4 空库迁移里的 6 条演示早餐不进入全量库。
- 质量包必须有文件哈希、完整且唯一的公开菜谱 ID、原始内容 sourceHash，并与备份逐 ID 的 16 个公开内容字段一致；通过后才绑定 Java 原配方指纹。

## 启动与恢复

运行 `scripts/start_local_maturity.ps1`。当前工作目录 `.local-maturity-active/`，旧 `.local-maturity/` 和 failed 目录原地保留，禁止为了重试修改权限或删除原目录。

启动前检查源备份、质量包和迁移文件；初始化后、修改本机密码前写入忽略的 bootstrap.json。续跑保持数据库名、端口、匿名盐和密码；每张表的事务与恢复点一起提交。表数据依赖顺序始终按原 DDL 的外键图计算，不以“表已存在”代替父行已恢复。V6_10 临时过程仅在本机隔离库重建，重复执行其添加列/索引保护。

`runtime.json`、bootstrap.json 和 application-local.yml 含本机凭据，不能提交。`bridge-report.json` 与 `bridge-rehearsal.json` 只输出汇总证据。

## 已验证与限制

真实 MySQL 已完成全量导入；另建隔离测试库，在 users 数据恢复前、V6_10 存储过程调用前各注入一次中断，然后成功续跑并再次重复桥接。账户 85、计划 14、收藏 10、采购菜 24、采购项 81 的源数量保留，质量记录 6,665；实际记录未被迁移器虚构。

逻辑备份已恢复到另一新建隔离库，38表59,885行逐行摘要一致。Windows客户端必须显式使用 utf8mb4。此结果证明本地回退副本可恢复，不替代生产最新备份/增量回滚演练。开始真实使用后不要直接重放初始化桥接器；正常重启使用启动器的 serve 分支。

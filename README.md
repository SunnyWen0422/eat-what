# 吃什么 · EatWhat

2026-10-29 新增主料营养口径：调味料和辅料不参与营养计算，界面只在热量下方显示“仅参考”；无主料或主料数据不全不填总值。5,407 道全量复算后有 3,989 道主料营养完整，原配方不变。后端、数据及网页说明已于 2026-10-30 配套上线，小程序尚未发布；见[发布记录](docs/operations/2026-10-30-main-ingredient-nutrition-release.md)。验证边界见[本轮记录](docs/testing/2026-10-29-main-ingredient-nutrition.md)。

围绕“这一餐吃什么”完成选菜、调整、日历记录、采购和饮食回顾。项目包含微信小程序、独立网页版、Java 业务后端和 Python 推荐/模型服务。

> 本文描述当前开发分支源码（2026-10-30），各端上线范围以部署记录为准。小程序源码 `utils/config.js` 当前指向线上 HTTPS API，V4 开启；打开本地项目不等于使用本地数据库。服务端能力、配置及客户端版本需配套核对。

本地核心增强已实现并完成隔离验收：配置变化保留当前菜单，撤销仅恢复上一版菜单一次；助手语音改用微信官方插件，文字可编辑后发送；历史菜单按原配方复算营养，购物查询返回待买食材参考小计与覆盖范围。10 个自然对话场景经修复复验，实际模型调用 19/20 次。语音插件仍需管理员启用及真机验收，默认入口隐藏；后端与营养数据已按后续授权于 2026-10-30 配套上线，小程序仍需单独发版。接入见 [微信语音启用说明](docs/operations/wechat-voice-setup.md)，验证与发布边界见 [核心增强验收](docs/testing/2026-10-28-core-enhancement-acceptance.md)。

菜库采用统一结构：每道菜沿用食谱固定用量，人数只表示分食；购物量和菜谱营养参考不随人数放大。“适量”保留为空数值，营养无法完整计算时不填总值。能量向用户四舍五入显示为整数千卡，内部计算保留精度。接入方法见 [菜库 V4 接入说明](docs/data/canonical-catalog-v4-integration.md)，本地检查见 [固定用量验收](docs/testing/2026-10-24-fixed-recipe-local-acceptance.md)，后端与数据的线上更新、备份和验证状态见 [2026-10-24 发布记录](docs/operations/2026-10-24-canonical-catalog-release.md)。小程序与网页需分别发布。

本轮“保存即记录”、跨日首页和一次性历史归并的实现与本地证据见 [2026-10-25 统一记录验收](docs/testing/2026-10-25-unified-meal-records.md)。配套后端与记录迁移已上线，备份、数据保护及接口复查见 [统一记录发布记录](docs/operations/2026-10-25-unified-records-release.md)。小程序源码需重新编译，微信正式版未在本轮发布。

## 当前能力

| 模块 | 已有能力 |
| --- | --- |
| 今天 / 本餐工作区 | 日期与餐次、人数、荤素汤等搭配、筛选和临时要求、生成与调整菜单、手动选菜、草稿恢复 |
| 菜谱 | 搜索筛选、食材与做法、真实图片优先、收藏、个人菜谱、常用菜单；复制菜谱在编辑保存时创建 |

| 采购 | 按来源准备食材、汇总与按菜查看、已买状态、参考价格及独立实付记录、操作恢复 |
| 做饭与回顾 | 查看本餐做法、按已保存餐次回顾；不提供缺乏依据的营养摄入估算 |
| 饮食助手 | 读取菜谱与餐务上下文、自然语言调整菜单、菜品卡片、日历和采购办理、历史对话及相关页面交接 |
| 网页 | 独立 React 前端，共享公开菜库；个人计划、收藏、采购和备份保存在当前浏览器，不自动同步微信账号 |
| 管理 | 服务端管理员权限下的用户、菜品及相关维护入口；隐藏入口不替代身份验证 |

页面沿用温暖餐桌 A；涉及菜品卡片、助手及推荐采用轻透浮层 F。有真实图片时显示图片与圆角，缺图或加载失败时显示分类图标。

### 推荐策略：合口味，也能换新

首页与饮食助手共用 `balanced-v1` 服务端选菜策略；外部模型理解本餐意图，服务端负责候选、概率抽选与结果校验。

- 收藏不加权、不参与口味学习；仅明确要求从收藏挑选时限定候选范围。
- 本餐“想吃”优先回应，长期偏好适度加权；明确排除和必须满足的条件严格执行。“期望用时”属于偏好，不是保证。
- 合格候选按 75% 加权抽选与 25% 均匀探索混合选择，避免始终取排名最高的菜。
- 按账号、日期、餐次持久轮换；本餐推荐轮换与日历记录分别管理，近期记录用于避重，首页与助手共享状态。
- 行为学习仅使用新的有效展示、采用与单菜替换记录，达到门槛后缓慢生效，影响限于 0.8～1.2 倍；可清除学习记录，保留手填偏好、收藏及业务记录。
- 新语义通过能力协商启用；菜谱浏览保持筛选含义，独立网页不自动接入。

完整权重与边界见 [推荐策略](docs/recommendation-policy.md)。界面和交互遵循 [产品体验规范](docs/ui/product-experience-guidelines.md)。

### 助手的表达与执行

- `meal_reply.v2` 支持简短自然回答与卡片展示别名；真实菜品 ID、图片和详情仍绑定数据库对象，别名不修改原菜名。
- 协商 `direct_execution_v1` 后，明确的保存日历、加入采购指令直接经原有业务任务执行；历史预览保留原确认方式。必要信息缺失时仍需澄清。
- 处理中可以补充指令：先停止并核对旧请求，再结合最新状态继续；不是向供应商同一次推理内部注入消息。
- 参数不合规可在原调用预算内进行一次内部纠正；业务成功以实际回执为准，区分明确失败、结果未知和部分完成。
- 正式模型功能与“是否允许测试调用模型”是两件事。测试必须有有效授权和剩余额度，不能重复使用旧额度。

这些是源码能力，真实模型效果、原生体验与部署状态分别验收。详见 [助手协议与执行说明](docs/testing/2026-10-17-assistant-flexible-execution.md) 和 [当前线上复审](docs/testing/2026-10-25-production-catalog-audit.md)。

## 当前限制与数据规则

- 助手语音采用微信官方 WechatSI 插件，无需单独配置腾讯云密钥；未启用或插件不可用时隐藏入口，文字输入保持可用。识别文字不会自动发送。
- 缺失价格保持空缺，不猜测、不补零；用户实际填写的 0 元有效。参考价与实付分开。
- 最后一个食材来源移除时，删除对应实付；重新添加不恢复旧金额。仍有来源则保留。
- 保存到日历即记录，无需另点“吃过”。按北京时间统计至今天；未来菜单当日才计入，草稿不计入。配方参考营养不等于个人实际摄入。
- 图片可用性取决于实际字段、地址及加载环境；不使用虚构菜图，不全局关闭 TLS 校验。
- 质量、份量、时间或营养缺乏依据时保持未知，不伪造审核状态。
- 本地验证不等于线上验收；推送代码不等于更新服务器或发布小程序。

## 项目结构

```text
.
├── pages/、components/、utils/   # 微信小程序页面、组件、状态及 API
├── styles/、design/             # 主题与设计资产
├── web/                        # React / TypeScript / Vite 独立网页
├── backend/                    # Spring Boot 2.7 / MyBatis 业务服务
├── recommend-service/          # FastAPI 推荐与模型适配
├── scripts/、tests/             # 隔离运行、验证、迁移准备与回归
├── docs/                       # 设计、验收、发布与操作记录
├── AGENTS.md                   # Agent 工作规范与接手入口
└── DEVELOPER.md                 # 架构、环境和业务契约
```

数据库为 MySQL 8。构建 JDK 与 Java 字节码目标按 `backend/pom.xml` 核对；网页使用 Node.js 24.x，依赖以锁文件为准；Python 依赖见 `recommend-service/requirements.txt`。不要把本机虚拟环境、数据库、构建包或私有配置打进源码。

## 开发与启动

先读 [Agent 接手指南](docs/agent-handoff.md) 和 [开发者手册](DEVELOPER.md)。完整本机说明见 [本机验证](docs/testing/local-verification.md)；其中带日期的线上状态、端口和预算须重新核对。

### 微信小程序

使用微信开发者工具打开正式仓库根目录，核对 AppID、实际项目路径和 `utils/config.js` 的 API 来源。模拟器、手机真机、上传开发版、提审及正式发布是不同阶段。

已有隔离完整数据环境可通过下列入口管理；首次初始化需要自己的已审计备份和配置，不能把生产目标填进隔离运行器：

```powershell
./scripts/start_local_maturity.ps1
```

运行器默认复用保存的 JAR 快照。需要运行已验证的新包时显式选择：

```powershell
./scripts/start_local_maturity.ps1 -JarPath ./backend/target/eatwhat-backend-1.0.0.jar
```

若产物位于其他构建目录，应使用该候选的真实路径。启动前核对环境归属；新构建不会自动替换正在运行的服务。新隔离验收另见 `scripts/maturity_runtime.py`。

### 独立网页

```powershell
cd web
npm ci
npm run dev
```

默认不启用线上代理。已获准读取线上公开菜库时可使用 `npm run dev:online`：只代理指定公开 GET，不转发私人账号接口、Cookie 或写入。静态发布仍需要同源后端路由。见 [网页说明](web/README.md)。

### 后端与模型配置

以 `backend/src/main/resources/application.yml.example` 和 `recommend-service/.env.example` 理解配置字段，在私密配置中提供实际值。Java 业务、Python 普通入口、内部令牌、能力开关与数据库结构需配套，不使用隔离替身代替生产模型服务。

没有配置文件、依赖或结构时，克隆项目并不等于能直接启动完整业务。不要将示例配置覆盖到现有服务器，也不要对旧库直接执行初始化 SQL。
